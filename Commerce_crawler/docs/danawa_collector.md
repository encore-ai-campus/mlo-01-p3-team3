# 다나와 다중 카테고리 수집기

## 구현 범위와 기준

다나와 하나만 구현한다. 기본은 카테고리별 첫 목록 페이지이고, 해당 카테고리의 캡처한 POST 템플릿을 지정하면 페이지를 순회한다. 상품 갤러리 사진과 부족한 필드를 보강하기 위해 상세를 상품당 최대 한 번 요청한다. --listing-only는 상세 요청을 생략한다. 다른 판매몰·제조사 링크·이미지 파일·외부 JSON-LD 컨텍스트는 요청하지 않는다. 브라우저 자동화, 차단 우회, MongoDB 연동은 포함하지 않는다.

`config/danawa_categories.json`의 코드·이름·제한을 사용한다. 다음 이름은 2026-10-14 실제 목록 페이지 제목에서 확인했다. 코드는 문자열이며 8자리 고정 제약이나 0 채우기를 적용하지 않는다.

| 코드 | 페이지 제목에서 확인한 이름 | 상품 상한 |
|---|---|---:|
| 15241194 | 침대 | 2 |
| 15240504 | 책상 | 2 |
| 1523647 | 학생/사무용의자 | 2 |
| 15241240 | 식탁 | 2 |
| 15227279 | 선반 | 2 |

기본 전체 상품 상한은 10개, HTTP 요청 시도 상한은 15회, 요청 시작 사이 간격은 최소 1초, 요청 타임아웃은 20초다. 실패 요청도 예산에 포함한다. 자동 재시도와 리다이렉트 추적은 하지 않는다. 요청 제한은 개별 실행 기준이다. 재실행은 새로운 요청 예산을 사용한다.

카테고리별 제한은 해당 카테고리 안에서 중복 제거 후 선택한 상품 수다. 다른 카테고리에서 이미 선택한 상품도 해당 카테고리의 제한에 포함한다. 전체 제한은 `source + product_id`의 고유 상품 수다. 중복 상품은 상세 요청·최종 저장을 한 번만 수행하며, 발견된 카테고리와 각 목록 관측값을 모두 보존한다. 전체 상품 제한 도달 후 남은 목록 요청은 생략하되 이미 선택한 상품의 상세 보강은 요청 예산 안에서 수행한다. 생략된 카테고리는 실행 보고서에 남긴다.

## 기존 자료에서 재사용한 부분

첨부 `danawa_sample.py`에는 단일 카테고리 첫 페이지에서 최대 5개를 추출하고 CSV로 저장하는 구현이 있었다. 지정 프로젝트에는 별도의 카테고리 리스트 수집기가 없었다. `spec_text`는 기존 샘플에서 항상 빈 문자열이었다.

Session 방식, `#productListArea .dnw-catalog-item`과 `li.prod_item` 선택자, pcode 추출, URL 결합, 지연 이미지 속성 탐색, 목록 내 상품 ID 중복 제거를 재사용했다. 상품명은 현재 HTML의 `ProductListTitle`을 우선하고 구형 `prod_name` 및 기존 링크 탐색을 대체 경로로 둔다. 실제 검증에서 첫 이미지 링크가 '이미지 보기' 텍스트를 포함한다는 사실을 확인하고 회귀 테스트를 추가했다.

현재 목록 카드는 다른 구성의 상품 ID와 가격도 포함한다. 기본 가격은 선택한 상품의 pcode와 같은 링크에서 읽고, 다른 구성의 가격은 원본 `variant_prices`에 별도 보존한다. 상품 카드 전체에서 첫 '숫자 + 원'을 가격으로 단정하지 않는다. 2자리 연도 등록 표시는 `registered_month_text`에 보존하고 세기를 추측하지 않는다. 정확한 4자리 연도 등록월은 상세 페이지에서 보강한다.

## 코드 구조

- `product_collector/core.py`: 카테고리 설정 검증, 요청 예산·간격·타임아웃, 순차 수집, 중복 관리, 해시, 필드 확보 집계, 저장.
- `product_collector/danawa.py`: 다나와 목록·상세·JSON-LD 추출과 공통 필드 의미 매핑.
- `product_collector/reprocess.py`: 저장한 HTML에서 네트워크 요청 없이 재추출·재정규화.
- `product_collector/__main__.py`: 실행 인자와 종료 코드.
- `product_collector/pagination.py`: 카테고리별 POST 템플릿과 번호가 붙은 JSON 결과 레코드 파싱.
- `tests/test_product_collector.py`: 합성 HTML과 가짜 Session 기반 자동 테스트.

공통 수집 과정은 `Adapter` 프로토콜을 사용한다. 이번에는 `DanawaAdapter` 하나만 구현·검증했다. 다른 사이트에 적용할 때 요청 호스트 정책도 명시적으로 확장해야 한다. 무제한 다중 사이트 수집 기능을 구현한 것은 아니다.

## 원본과 정규화 저장 계약

각 실행은 `data/danawa/<job_id>/`에 다음 세 파일을 새로 만든다. 기존 실행을 덮어쓰지 않는다. 이 디렉터리와 로컬 의존성은 `.gitignore`에서 제외한다.

| 파일 | 내용 |
|---|---|
| `product_raw.jsonl` | 한 줄에 상품 하나. 식별자·수집 시각·작업 ID·버전·카테고리·원본 해시·보강 상태와 `payload` |
| `products.jsonl` | 공통 필드, 카테고리, 가격 종류, 판매처별 제안, 원본 연결 해시, 필드별 출처와 확보 상태 |
| `run_report.json` | 실행 종류·설정·카테고리별 결과·요청 로그·실패 이유·상품 수·필드 확보 집계 |

원본 `payload.listings[]`는 관련 상품 카드 HTML과 추출 문자열을 보존한다. 목록 HTTP 응답 전체를 보존한 것은 아니다. `payload.detail`은 응답 HTML, JSON-LD 스크립트 원문·파싱 결과, 선택 상품·식별 근거, 규격·제조·판매처 HTML과 추출 결과를 보존한다. 응답 헤더·쿠키·인증정보를 원본 저장에 포함하지 않는다.

해시는 추출 payload에서 수집 시각과 사용자 카테고리 설정을 제외하고 키 정렬 JSON의 SHA-256으로 계산한다. HTML 안의 광고·동적 URL·가격 등이 바뀌면 해시도 바뀔 수 있다. 공통 데이터는 `source + product_id`와 `raw_payload_hash`로 해당 실행 원본과 연결된다. JSONL은 실행별 스냅샷이며 첨부 명세서의 MongoDB 최신 스냅샷 갱신 동작과 다르다.

저장은 원본 → 정규화 → 보고서 순서다. 세 파일이 모두 있는 디렉터리를 완료 출력으로 취급한다. DB 트랜잭션이나 장애 복구형 저장소를 구현한 것은 아니다.

## 상세 보강과 JSON-LD

JSON-LD 여러 블록·배열·`@graph`를 탐색하며 `Product`를 pcode URL, `productID`, 다나와에서 확인한 `sku`, 또는 유일하게 일치하는 상품명으로 대조한다. 다른 pcode를 명시한 후보는 채택하지 않는다. `Offer`와 `AggregateOffer`를 구분하고 `@id`로 연결된 판매 제안을 해석한다. 순환 참조는 반복 처리하지 않는다. JSON-LD가 없거나 잘못되어도 HTML 추출을 계속하고 오류 원문을 보존한다. JSON-LD 외부 컨텍스트를 해석하는 일반 RDF 엔진은 아니다.

필드 우선순위는 다음과 같다.

- 상품명: 식별자가 확인된 상세 Product 이름 → 목록 이름.
- 제조사·모델·원산지·크기·무게: Product 명시 속성 → HTML 규격의 명시 항목. 제조사는 추가로 `.made_info`의 명시 제조사 값을 사용한다. 브랜드를 제조사로 대체하지 않는다.
- 등록월: 상세의 정확한 등록월 → 목록의 정확한 등록월. 날짜·시각으로 확장하지 않는다.
- 설명: Product description → 명시적인 설명 HTML의 텍스트. 규격 요약이 설명에 제공되면 그 요약만 확보한 것으로 본다.
- 규격: 표·상세 요약의 명시 이름/값·Product additionalProperty를 보존한다. 단위 환산이나 크기 차원의 공통 수치화는 하지 않는다. 합성 크기 전체는 원본/규격 배열에 남기며 `size_text`는 첫 명시 크기의 텍스트다.
- 이미지: 상품 갤러리에서 관측한 사진만 images에 넣고 목록 이미지는 listing_image_url로 분리한다. 같은 사진으로 대조된 JSON-LD 주소만 사용한다. 설명 이미지·임의의 JSON-LD 이미지 추가와 원본 해상도 추정은 하지 않는다. 다운로드는 별도 선택 기능이다. 기존 1.0 출력은 목록과 JSON-LD 이미지의 합집합이었다.
- 목록 표시 가격, 구성별 가격, JSON-LD 비교 집계 가격, 판매처별 가격은 각 원문과 종류를 분리한다. 단일 명시 금액만 숫자로 변환하며 가격문의·범위는 숫자로 추측하지 않는다. 소수 금액은 정밀도 보존을 위해 문자열로 저장한다.

상세 HTML의 판매처 제안은 판매처 이름, 다나와의 `cmpnyc` 코드, 링크, 상품 가격 속성, 배송비 속성, 배송 문구를 보존한다. 다나와에 표시된 제안이지 판매처 사이트에서 직접 검증한 재고·배송 정책이 아니다. `AggregateOffer.offerCount`는 판매 제안 수이며 재고나 최소 주문수량으로 매핑하지 않는다.

## 도매꾹 명세와 의미 대응

첨부 문서는 저장된 도매꾹 payload의 관측 명세다. 도매꾹 원문 모양으로 다나와 값을 위장하거나 공식 공통 계약으로 사용하지 않는다.

| 도매꾹 원문 항목 | 공통 필드/처리 |
|---|---|
| basis.no, basis.title | product_id, name. 출처를 함께 사용 |
| category.current, category.parents | 수집 카테고리와 관측 이름. 미관측 계층 깊이는 만들지 않음 |
| basis.dateReg | registered_month의 부분 대응. 정확한 등록 일시 미확보 |
| basis.keywords | keywords_text. 원문 키워드 표현을 보존 |
| price, priceCompare | listing_prices와 offers. 도매 가격과 비교 최저가를 동일시하지 않음 |
| thumb | images[].url. original/large 해상도를 추측하지 않음 |
| detail.manufacturer/model/country/size/weight | 명시값만 manufacturer/model/country_of_origin/size_text/weight_text |
| detail.infoDuty/safetyCert | 해당 표·고시가 추출되면 원본/규격에 보존. 현재 공통 고시·인증 코드 변환은 없음 |
| desc.contents.item | description과 원본 HTML. 상세 이미지 사용권을 추정하지 않음 |
| seller, deli, return | 관측된 offers별 판매처·배송·반품 정보만 보존. 판매자 사업자 정보는 추정하지 않음 |
| qty | 재고·최소 주문수량·주문 단위 미관측. 기본값 생성 안 함 |
| channel, benefits, event, popular, dialog, selectOpt 및 기타 코드 | 도매꾹 전용 의미를 만들지 않음. 관측된 다나와 데이터는 원본에 보존 |

누락 정규화 값은 `null`이다. `field_status`는 observed, detail_not_requested, detail_budget_exhausted, detail_request_failed, parser_unrecognized, not_found_in_extracted_content를 구분한다. 마지막 상태는 '추출 영역에서 찾지 못했다'는 뜻이며 페이지 전체에 없다는 보장이 아니다. 원문에 배열이 있고 하위 값이 일부 null인 경우는 배열 관측 여부와 개별 하위 값 확보 여부를 함께 봐야 한다.

## 실행과 검증

Python 3.10 이상 환경에서 `Commerce_crawler` 디렉터리 기준이다. 저장소 상위 루트에서 먼저 이 디렉터리로 이동한다:

```powershell
Set-Location 'C:\Users\Playdata\Documents\encore_MLops\3st_project\mlo-01-p3-team3\Commerce_crawler'
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements-collector.txt
.\.venv\Scripts\python.exe -m unittest discover -s tests -p 'test_*.py' -v
.\.venv\Scripts\python.exe -m product_collector
```

저장된 원문으로 재추출할 때는 다음 명령을 사용한다. HTTP 요청 없이 새로운 실행 디렉터리를 생성하고 원래 수집 시각과 원본 요청 로그를 보존한다.

```powershell
.\.venv\Scripts\python.exe -m product_collector --reprocess-from data/danawa/<이전-job_id>
```

환경에 따라 PATH에 Python이 없으면 Python 실행 파일의 전체 경로를 사용한다. 개발 검증에서는 제공된 Python 3.12 런타임과 프로젝트 로컬 `.local-deps`에 설치한 requests 2.34.2, BeautifulSoup 4.15.0을 사용했다.

기본 설정은 CLI `--categories`, `--total-limit`, `--max-requests`, `--interval`, `--timeout`, `--output`으로 변경할 수 있다. 양수 제한, 숫자 문자열 ID, 중복 카테고리, 유한 간격·타임아웃을 검사한다. 종료 코드는 정상 완료 0, 부분 결과/입력 오류 2다. completed는 파이프라인 완료를 의미하며 모든 상품 필드 확보나 정확한 재고 확인을 뜻하지 않는다.

2026-10-14 검증 결과:

- 합성 HTML 기반 자동 테스트 22개 통과. 5개 카테고리·10개 상품·15회 요청, 카테고리 간 중복, 총량·요청 제한, 타임아웃·403·리다이렉트, 상품명/구성 가격, JSON-LD 오류·참조·상품 불일치, 저장 연결과 네트워크 없는 재추출을 확인했다.
- 실제 다나와 요청은 목록 5회 + 상세 10회 = 총 15회. 모두 HTTP 200이며 카테고리별 2개, 고유 상품 10개를 확보했다.
- 초기 추출에서 현재 상품명 선택자와 JSON-LD 식별 방식의 차이를 발견했다. 원본 실행 `878e5fc0-fe81-4abe-b225-c0595a49755a`는 partial 결과로 보존했다.
- 수정한 추출기로 같은 저장 HTML을 HTTP 추가 요청 없이 재처리했다. 10개 상품 모두 상세 파싱 성공. 따라서 실제 요청 검증과 수정 후 오프라인 검증을 구분한다.
- 상품명·목록 금액·제조사·브랜드·등록월·규격 요약·JSON-LD 설명·이미지·판매 제안·키워드는 10/10건 확보, 크기는 8/10건 확보. 모델·원산지·무게는 0/10건이며 임의로 채우지 않았다. 이 결과는 해당 시점에 선택된 10개 상품에 대한 결과다.

## 카테고리 추가와 수집량 조절

카테고리는 5개로 고정되어 있지 않다. `config/danawa_categories.json` 배열에 새로운 항목을 추가하면 입력 순서대로 처리한다. category_id는 숫자 문자열, category_name은 문자열 또는 null, limit은 양의 정수다. 같은 코드의 중복 설정은 거부한다. 이름을 아직 확인하지 못했다면 null로 두고 실행 보고서의 observed_category_name과 제목을 확인한다.

카테고리별 limit만 늘려서는 다음 페이지로 이동하지 않는다. start_page/max_pages와 해당 카테고리의 POST 템플릿을 함께 설정한다. 새 카테고리를 넣어도 기본 전체 10개·요청 15회 제한은 그대로다. 전체 한도 도달 시 뒤쪽 카테고리가 생략될 수 있고 예산 소진 시 목록 데이터만 저장될 수 있다. total-limit/max-requests를 함께 조정하며 카테고리별 pages/status/reason과 상세 상태를 확인한다. 71개 별도 후보 설정은 config/danawa_categories_71.json에 있고 기본 설정은 5개다.

## 중복 처리의 범위와 확장 대안

현재 중복 제거는 한 번 실행하는 동안의 source + product_id 기준이다. 목록 안에서는 같은 ID를 한 번 선택하고, 서로 다른 카테고리에서 같은 ID가 발견되면 하나의 원본/정규화 상품에 카테고리와 목록 관측을 추가한다. 전체 한도로 아직 요청하지 않은 카테고리의 소속까지 알아내는 기능은 없다.

재실행은 새 작업 폴더를 만들므로 실행 간에는 같은 상품이 반복 저장될 수 있다. JSON-LD와 HTML의 같은 판매처 제안도 현재는 출처별로 보존하며 자동으로 동일 제안인지 병합하지 않는다.

향후 필요한 경우 다음 방식으로 확장할 수 있다. 아래는 대안이며 현재 구현된 기능이 아니다.

- 최신 상품 조회본: source + product_id로 upsert하고 원본 실행 이력은 별도 보존한다.
- 변경 판정: 상품의 의미 있는 정규화 필드를 비교한다. payload_hash는 HTML의 광고·동적 URL까지 영향을 받으므로 동일 제품 판정이나 가격 변경만 판단하는 해시로 사용하지 않는다.
- 서로 다른 ID의 동일 제품 후보: 제조사·모델·크기·옵션·구성으로 후보를 만들고 검토한다. 이름이나 이미지가 비슷하다는 이유만으로 합치지 않는다.
- 이미지 파일 중복: 다운로드 기능을 추가한 뒤 파일 해시로 저장 중복만 제거한다. 파일 중복이 상품 중복을 뜻하지 않는다.
- 도매꾹/다나와 연결: 원본은 각각 보존하고 별도 매칭 자료에 두 출처 ID·근거·검토 상태를 기록한다. 현재 수집 결과에는 이 연결이 없다.

## URL이 바뀌지 않는 페이지 전환: 확인 상태와 후속 구현 기준

최초 문서 작성 때는 페이지 전환이 미확인 상태였다. 이후 사용자가 전체 Payload·Request Headers를 제공했고, 같은 URL에 POST 본문의 page를 변경하여 Python에서 의자 8·9페이지를 각각 30개씩 수집했다. 현재 start_page/max_pages, --start-page/--max-pages, --pagination-template을 지원한다. 구현·실제 검증·갤러리 변경은 [페이지와 갤러리 문서](pagination_and_gallery.md)를 따른다.

사용자가 페이지 버튼 클릭 후 관측한 요청 목록은 다음과 같다. 이 목록은 사용자 제공 근거이며 크롤러에서 직접 요청 본문·응답을 확인한 기록은 아니다.

| 관측된 경로 | 현재 판단 |
|---|---|
| finance-tip/?uiCategory=481 | 이름상 금융 안내 후보. 목록 갱신 여부 미확인 |
| special-price/ | 이름상 특가 보강 후보. 목록 갱신 여부 미확인 |
| product-color/?productCodes=... | 상품별 색상 보강 후보. 전환 전후 ID 변화는 간접 단서 |
| list/?cate=1523647 | 목록 갱신 후보. 페이지 제어값이 어디에 있는지는 미확인 |

응답 200이나 2.1kB라는 크기만으로 list/가 상품 목록 요청인지 판단하지 않는다. 2·3페이지 전환에서 전체 Request URL, Method, Query String, Payload, 필요한 헤더, Response/Preview를 비교해야 한다. 공유 자료에서는 쿠키·인증 토큰을 제거한다. Fetch/XHR에서 설명되지 않으면 Network의 All에서 다른 요청 유형과 미리 로드된 데이터도 확인한다.

확인된 요청이 상품 목록 HTML/JSON을 반환한다면 같은 요청 조건을 Session에서 재현하고 다나와 어댑터가 해당 응답을 해석하도록 확장한다. 별도 API나 사전 데이터로 처리할 수 없을 때만 브라우저 자동화를 검토한다. 단순히 page=2를 붙이거나 경로만 보고 POST로 가정하지 않는다.

다중 페이지 구현 시 필요한 제어는 다음과 같다.

1. 카테고리별 시작 페이지와 최대 페이지 수를 추가하고 실제로 확인된 페이지 번호/오프셋/커서를 사용한다.
2. 페이지가 바뀌어도 source + product_id로 중복 제거한다. 같은 상품이 반복되면 추가 저장하지 않는다.
3. 카테고리 상품 한도·전체 상품 한도·전체 요청 한도와 상세 보강 예산을 함께 적용한다. 브라우저 방식이면 페이지 전환 수와 브라우저 내부 HTTP 요청 수를 구분해 한도를 설계한다.
4. 다음 페이지 없음, 빈 목록, 반복된 상품 ID 목록, 커서 반복, 요청/파싱 실패 시 해당 이유를 기록하고 종료한다. HTTP 200의 파싱 실패를 정상적인 마지막 페이지로 단정하지 않는다.
5. URL 변화 대신 응답 상품 ID 목록과 페이지/커서 상태로 전환을 검증한다. 새로 추가된 상품이 없으면 무한 반복하지 않는다.
6. 테스트에는 1→2페이지, 겹치는 상품, 반복 응답, 마지막 페이지, 페이지 한도, 요청 한도, 상세 예산 소진을 포함한다.

위 비교 절차는 다른 카테고리의 POST 템플릿을 확보할 때 적용한다. 이후 기본 5개 각각의 1→2페이지를 실 검증하고 카테고리별 템플릿과 테스트를 남겼다. [검증 기록](five_category_pagination_validation.md)을 따른다. 일반 페이지·상품·요청 한도와 반복/빈 응답 종료는 구현했고, 커서 방식·브라우저 자동화는 구현하지 않았다.

## 출력 필드와 BRD의 관계

필드별 경로·타입·가격 의미·누락 상태·BRD 정보 대응은 [출력 필드 명세](data_fields.md)를 따른다. BRD가 요구한 주요 정보 일부를 보존했지만 이 수집기의 JSONL 구조·selector·요청 한도는 이번 대화에서 합의한 구현 기준이다. 이용 조건·포함/제외/검토 대기·추천 가능 여부는 현재 출력에서 확보 또는 구현되지 않았다. 선택 이미지 다운로드와 파일 연결 검증은 [이미지 내재화 문서](image_localization.md)를 따른다.
