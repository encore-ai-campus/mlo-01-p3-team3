# RoomPick 대화 맥락 — 데모 구현 및 행동데이터 확장

- 정리일: 2026년 10월 14일
- 대상 프로젝트: `roompick/`
- 목적: 이 대화에서 이어온 요구사항·설계 결정·구현·검증·문서화 맥락을 다른 GPT에 전달한다.
- 활용 방식: 이 문서와 관련 문서·소스코드를 함께 제공하는 프로젝트 맥락 자료다. 문서 작성만으로 GPT 모델이나 스케치 AI 모델을 실제 학습시킨 것은 아니다.
- 근거: 현재 대화 내용, 프로젝트의 변경 이력과 문서, 정리 시점에 확인한 소스코드.

## 1. 다음 GPT가 먼저 알아야 할 핵심

RoomPick은 비회원 사용자가 자신의 공간 사진 위에 그림·텍스트·도형으로 원하는 인테리어를 표시하고, 상품 검색 후 배치 결과를 확인하는 Django 웹 데모다. 화면은 초기 화면 → 스케치 편집 화면 → 결과 화면으로 나뉜다.

현재 결과는 텍스트 단어 규칙과 샘플 가구 그래픽으로 만드는 모의 결과다. 실제 스케치 AI 인식, 실시간 상품 검색, 생성형 이미지 합성은 연결하지 않았다.

**사용자가 가장 강하게 지정한 조건은 ‘이미 구현한 기능과 화면 동작이 바뀌면 안 된다’이다.** 행동데이터 확장은 기존 그리기·부분 지우기·사진 편집·Undo/Redo·검색·결과 조절 흐름을 유지하면서 별도로 붙였다.

데이터는 세 종류를 구분해야 한다.

| 구분 | 의미 | 위치 |
|---|---|---|
| 기존 행동 이벤트 | 어떤 기능을 사용하고 어떤 편집을 완료했는지 | SQLite의 `SketchEvent` |
| 새 스케치 원본 | 원본 좌표·시간·포인터 상태·편집 대상·재생 가능한 상태 변화 | IndexedDB 및 `data/sketch_raw/*.json` |
| 서버 실행 로그 | HTTP 요청·응답 상태와 서버 오류 | Django 서버 실행 터미널; 선택적으로 별도 로그 파일 |

행동 이벤트가 존재한다고 새 원본 파일이 저장됐거나 학습용 정답 데이터가 준비됐다고 판단하면 안 된다. 한 번의 버튼 동작에 여러 이벤트가 발생할 수 있으며, 이벤트 수와 스케치 수는 다르다.

## 2. 프로젝트 배경과 기존 데모의 구현 이력

사용자는 실습의 `game_server`에서 애플리케이션 행동데이터를 Python 명령으로 터미널에서 관찰한 경험이 있다. RoomPick에서도 브라우저 행동이 실제로 기록되는지 VS Code 터미널에서 확인하고, 이후 수집 정책과 학습용 데이터 기준을 정리하려고 했다.

현재 대화에서 상세 수집 확장을 시작할 때 RoomPick의 기존 화면·편집 기능과 행동 이벤트 수집 코드가 이미 존재했다. 최초 데모부터 여러 차례 수정한 설명은 [데모 변경 이력](데모_변경이력.md)에 기록돼 있다. 그 기록에 근거한 기존 구현 이력과, 이 대화에서 직접 진행한 상세 원본 수집 확장을 아래처럼 구분한다.

| 기존 구현 단계 | 주요 요구와 결과 |
|---|---|
| 최초 구현 | 사진 위 Canvas, 펜·지우개·정규화 좌표, 익명 방문 ID, 행동 이벤트 수집을 구성. 당시에는 카메라 요청과 카테고리·샘플 가구 선택 UI도 있었음 |
| 1차 수정 | 카메라·사전 카테고리 선택을 제거하고 사진 드롭, 텍스트·도형, 지우개 범위 표시를 추가. 상품 검색·모의 합성 결과·다운로드 흐름 구성 |
| 2차 수정 | 초기·편집·결과 페이지 분리. 사진 위 직접 텍스트 입력, 결과에서 가구 조절, 검색 완료 작업 잠금과 새 작업 재시작 구성 |
| 3차 수정 | 사진 자르기·채우기·외곽선 선택·복사/붙여넣기와 재시작 3종 구성. 여러 표시를 한 상품 입력으로 묶음 |
| 4차 수정 | 사진·스케치 통합 Undo/Redo, 픽셀 범위 부분 지우기, 내부 요소 독립 편집, 펜 자동 연결·명시적 그룹, 선택 선 두께 조절과 상품 안내 카드 3칸 구성 |
| 이번 대화의 수집 확장 | 기존 행동 이벤트 유지, 초기 시작 클릭 추가, 별도 스케치 원본 수집·검증·불변 JSON·IndexedDB·전송/복구 연결 |

과거 단계의 기능 설명을 현재 기능으로 혼동하지 않아야 한다. 예를 들어 현재는 카메라 버튼, 사용자 가구 카테고리 선택, 작업 중 스케치 PNG 다운로드, 별도 사진 복귀 버튼이 없다. 사진 복귀는 통합 Undo/Redo로 처리한다.

문서 파일명에 붙은 ‘3차’와 변경 이력의 ‘4차 수정’, 원본 계약의 `roompick-sketch-1.0.0`은 서로 다른 구분이다. 파일명만으로 기능 단계나 데이터 계약 버전을 추정하지 않는다.

## 3. 현재 서비스 화면과 기능

### 3.1 초기 화면

- 서비스 소개와 이용 단계 안내.
- ‘내 공간 꾸미러 가기’를 누르면 스케치 편집 화면으로 이동.
- 로그인 없이 이용.
- 실제 AI·상품 검색이 아닌 데모라는 안내.
- 초기 접속은 기존 `home.viewed`, 시작 버튼 클릭은 이번에 추가한 `button.clicked`로 기록.

### 3.2 스케치 편집 화면

- 사진 파일 선택·드래그 앤 드롭·교체·자르기.
- 사진 업로드 전에는 사진 입력을 안내.
- 마우스·손가락·터치펜으로 펜과 지우개 사용.
- 지우개는 사진이 아닌 선·텍스트·도형·채우기의 해당 픽셀 범위를 부분적으로 지움.
- 펜·지우개·도형 크기와 색상 설정, 입력 중 글자 크기 설정.
- 사진 위 직접 텍스트 입력, Enter 완료·Shift+Enter 줄바꿈·Esc 취소·더블클릭 수정.
- 사각형·타원·직선·화살표 및 연결 영역 채우기.
- 외곽선·채운 영역·텍스트 선택, 이동·크기 조절·선 두께 수정.
- 영역 선택·그룹화·그룹 해제, 접촉한 펜 획의 자동 연결.
- 복사·붙여넣기·선택 삭제·모두 지우기.
- 사진 업로드·교체·자르기·스케치 공통의 최근 20단계 Undo/Redo.
- 같은 탭·작업 URL·저장 버전 조건이 맞으면 sessionStorage 편집 이력 복원.
- 상단·하단 상품 검색 버튼은 같은 동작. 사진과 입력 내용을 검사한 후 모의 결과 생성.

현재 소스에서는 10MB·2,500만 픽셀 이하의 JPG·PNG·WebP를 검사하고, EXIF 회전 적용 및 최대 변 2048픽셀 JPEG 변환을 수행한다. 일부 휴대폰 JPEG가 MPO로 판독되는 경우 첫 사진을 사용하는 코드도 확인했다. 이는 정리 시점의 현재 소스 상태이며, 해당 MPO 수정 과정을 이 대화에서 직접 수행했다고 의미하지 않는다.

### 3.3 결과 화면

- 업로드 사진 위 샘플 가구 그래픽과 모의 예측 문구 표시.
- 생성된 가구 선택·이동·크기 조절.
- 조작 완료 시 서버 배치와 합성 PNG 자동 갱신.
- 저장 실패 시 마지막 서버 저장 배치로 복원.
- 최종 저장 배치가 반영된 PNG와 작업 데이터 JSON 다운로드.
- 추천 상품 카드 3칸은 안내 자리이며 실제 상품 사진·판매 링크는 없음.
- 결과 URL 새로고침 시 저장된 결과 유지.

| 재시작 버튼 | 사진 | 편집 내용 | 처리 |
|---|---|---|---|
| 처음부터 다시 그리기 | 유지 | 비움 | 새 작업 |
| 스케치 수정하기 | 유지 | 검색 당시 입력 복원 | 새 작업; 결과 배치 변경을 원래 스케치에 역적용하지 않음 |
| 다른 상품 검색하기 | 비움 | 비움 | 새 사진을 올릴 새 작업 |

재시작 시 이전 결과를 덮어쓰거나 삭제하지 않는다. 방문 ID는 유지하고 작업 ID는 새로 생성한다. 검색 완료된 원래 편집 작업은 잠기므로 수정은 재시작 기능을 사용한다.

별도 결과 생성 중 페이지는 없다. 스케치 화면에서 처리 상태를 표시한 뒤 결과 화면으로 이동한다. 현재 그림·텍스트·도형·채우기는 전체를 하나의 상품 입력으로 처리한다.

## 4. 사용자가 전달한 원본 수집 설계

사용자는 스케치 인식·분류 AI를 위한 좌표 데이터 수집·학습 아키텍처 설계안과 `collector.js` 예제를 첨부하고, 설명 및 FastAPI 서버 예제도 전달했다.

전달받은 설계의 핵심은 다음과 같았다.

- Canvas와 Pointer Events로 원본 좌표와 시간 수집.
- CSS 크기와 DPR을 구분하고 좌표계·시간 원점을 명시.
- 획과 Undo/Clear/Erase 등 편집 작업을 분리.
- 삭제·취소 전 원본을 유지하고 최종 유효 상태를 별도 표현.
- 브라우저 IndexedDB 초안, 정상 제출 후 서버 원본 JSON 저장.
- 입력 구조·시간·이벤트 정합성 검증과 동일 샘플 중복 제출 처리.
- 원본 불변 저장과 Curated·Features 등 학습 데이터의 분리.
- 이후 원본에서 이미지·좌표 시퀀스를 생성하고 CNN·GRU·Transformer 등을 검토.

참조 수집기는 `sun` 라벨을 제시하고 별도 동의·Submit 버튼으로 업로드하는 예제였다. IndexedDB는 `sketch-demo-v1/drafts/current`, 서버는 별도 FastAPI `/api/sketches`와 `raw/<sample_id>.json`을 사용하는 구성이었다. 참고 패키지의 검증·전처리·학습 설명은 RoomPick에 자동으로 구현돼 있던 기능이 아니다.

사용자는 예제와 저장 경로가 같을 필요는 없으며, 이 원본 수집 기준으로 실제 데이터가 쌓이도록 기존 데모에 연결하기를 요청했다.

## 5. 대화에서 확인한 기존 수집 기준

처음에는 사용자가 기존 데이터 수집 여부를 모르고 있었다. 코드·DB 조회로 `SketchEvent` 수집이 이미 존재함을 확인한 후, 상세 원본 기준과 차이를 설명했다.

기존 기준은 ‘기능 사용과 편집 완료’였다.

- 펜·지우개는 점을 모아서 완료 시 `stroke.completed` 한 건으로 기록.
- 기존 표시용 좌표는 0~1로 제한하고 반올림하며, 가까운 점은 생략.
- 완료 획의 좌표·필압·도구·색상·두께·입력 장치는 보관.
- 취소 이벤트에는 일부 정보만 남고 취소 경로 전체는 없음.
- 이동·크기 조절은 완료 후 상태를 기록하며 모든 드래그 경로를 기록하지 않음.
- Undo/Redo/Clear는 행동 종류를 기록하지만 대상 원본과 재생 관계가 충분히 명시되지 않음.
- 미전송 이벤트는 localStorage에 보관하고 UUID로 중복 처리.
- 결과 화면 버튼·가구 이동·크기 조절·다운로드·재시작은 이미 기록.
- 초기 화면 방문 기록은 있었지만 시작 버튼 클릭은 별도 수집되지 않았음.

‘행동 로그가 쌓임’과 ‘학습에 적합한 원본 데이터가 준비됨’은 별개라고 설명했다. 정식 수집 정책이 미확정이어도 개발자가 테스트 데이터를 생성하고 전달·저장·중복·좌표를 검증하는 단계는 진행할 수 있지만, 실제 이용자 수집·학습 사용에는 목적·범위·동의·보관·라벨 기준을 결정해야 한다.

기존 DB 이벤트 수 2,725건, 이후 조회 2,737건은 당시의 조회 스냅샷이다. 현재 누적 건수나 실제 사용자 수, 서로 다른 스케치 개수로 사용하면 안 된다. 이 기록만으로 테스트와 실제 이용 기록도 구분할 수 없다.

## 6. 이번 대화의 진행 순서와 결정

| 순서 | 사용자 요청·질문 | 진행 결과 |
|---|---|---|
| 1 | 첨부 방식으로 기존 RoomPick에 실제 수집 연결 | 기존 코드·데이터를 확인하고 별도 원본 수집 연결 범위를 제안 |
| 2 | 구현된 기능은 절대 바뀌면 안 됨 | 기존 화면·편집·검색 동작 유지 조건을 최우선으로 적용 |
| 3 | Django 플랫폼에서도 VS Code 명령으로 확인 가능한가 | 브라우저 → Django API → SQLite → 터미널 조회 구조와 명령 설명 |
| 4 | 정책이 미확정인데 생성 확인을 먼저 해도 되는가 | 개발용 수집 검증과 운영·학습 정책 확정을 구분 |
| 5 | 현재는 어떤 행동 기준인가 | 기존 행동 이벤트와 첨부 원본 기준의 차이 설명 |
| 6 | 원본 기준을 반영하면 무엇이 달라지는가 | 화면 기능 유지, 점별 시간·취소 경로·편집 대상·최종 상태 추가로 설명 |
| 7 | 먼저 화면별 기능 구현 리스트 작성 | 초기·스케치·결과·공통 기능과 미구현 범위 66개 항목 정리 |
| 8 | 기능 리스트를 docs 파일로 저장 | 문서 생성. 현재 이름은 `3차_페이지_기능구현리스트.md` |
| 9 | 기존 기준에서 확장 반영했다고 문서 작성하고 데모에 적용 | 별도 원본 수집·API·저장·검증·초기 클릭 연결과 수집기준 문서 반영 |
| 10 | 토큰 부족으로 작업이 멈췄는지 확인 후 이어서 진행 | 남은 검증·문서 링크·마무리를 확인하고 이어서 완료 |
| 11 | 파일 구조와 파일 역할, 확인 명령 설명 | 현재 코드 기준 설명과 DB·JSON·IndexedDB·서버 로그 조회 방법 제공 |
| 12 | 경로는 roompick부터, 파일 역할은 한 줄로 | 트리의 각 파일 옆에 한 줄 설명하는 형식으로 정리 |
| 13 | 구조 설명과 명령 안내를 각각 파일로 저장 | 관련 문서 두 개 생성 |
| 14 | 대화의 전체 맥락을 다른 GPT에 전달할 문서로 정리 | 현재 문서 작성 |

첫 연결 제안 단계에서는 설계 확인을 요청했고, 사용자가 기능 목록을 먼저 검토한 뒤 구현과 문서화를 명시적으로 요청했을 때 반영을 진행했다. 향후 GPT는 이를 미승인 아이디어와 완료된 구현으로 혼동하지 않는다.

## 7. 첨부 예제를 그대로 적용하지 않은 이유

| 참조 예제 | 현재 데모와의 차이 | 적용 결정 |
|---|---|---|
| 별도 FastAPI 서버 | 현재 Django 서비스와 API가 이미 존재 | Django 수집 API 추가; 별도 FastAPI 서비스·의존성 추가 안 함 |
| sun 프롬프트 라벨 | 현재는 사진 위 자유 스케치 | `label_id=null`, `label_status=unverified` |
| 별도 Submit 버튼 | 기존 사용자 검색·이동 흐름 유지 조건 | 검색 성공·작업 변경·페이지 종료 등으로 자동 제출 |
| 동의 체크 예제 | 현재 운영·학습 동의 정책 미확정 | 강제 동의 UI를 추가하지 않고 미완료 정책으로 명시 |
| 전체 획 지우개 | 데모는 픽셀 범위 부분 지우기 | 기존 `cuts` 마스크를 유지하고 원본 경로·대상 ID만 연결 |
| Undo/Clear 중심 | 사진 복귀·Redo·이동·크기·복사·텍스트·도형도 있음 | 시작 문서·변경분·최종 문서로 재생 가능하게 확장 |
| 고정 캔버스 | 기존 데모의 반응형·화면 크기 변화 유지 필요 | 화면 크기를 강제로 고정하지 않고 경로·변경 점의 CSS 크기 보관 |
| 예제의 JSON Schema | RoomPick 문서 형식과 편집 동작을 표현해야 함 | `roompick-sketch-1.0.0` 계약과 Python 검증 적용 |

따라서 ‘첨부 설계의 핵심 원칙을 현재 기능에 맞게 확장 반영했다’가 정확한 표현이다. 참조 collector/server와 파일·필드·프로토콜이 그대로 호환된다고 설명하면 안 된다.

## 8. 현재 행동데이터·원본 수집 구조

### 8.1 기존 행동 이벤트 경로

```text
초기·편집·결과 화면의 기능 실행
  → events.mjs의 이벤트 큐
  → POST /api/projects/<project_id>/events/
  → views.py의 입력·소유권·중복 검증
  → db.sqlite3의 SketchEvent
  → manage.py 조회 또는 export_sketch_events 출력
```

약 1.5초 주기, 일부 동작 직후, 온라인 복귀 시 전송하고 종료 시 sendBeacon을 시도한다. 기존 이벤트 상세값은 `payload`, 브라우저 기록 시각은 `payload.client_time`, 서버 기록 시각은 `event_time`이다.

초기 시작 링크에는 `button.clicked`의 `button=start-sketch`, `page=home`을 추가했다. 링크의 기존 이동 동작은 유지한다. 결과의 이동·다운로드 등의 기록은 기존 구현을 유지하며, 결과 이동 경로 전체를 새 원본 포인터 시퀀스로 추가한 것은 아니다.

### 8.2 새 원본 경로

```text
펜·지우개 원본 포인터 + 기존 편집 동작 관찰
  → collector.mjs의 별도 수집 구간
  → IndexedDB 초안
  → 구간 종료 시 outbox
  → POST /api/projects/<project_id>/samples/
  → raw_samples.py의 원본·재생 정합성 검증
  → data/sketch_raw/<sample_id>.json
```

원본 수집은 기존 편집 문서의 좌표·필압 처리나 그리기 결과를 변경하지 않는다. 실패는 별도 하단 수집 상태로 표시하고 기존 편집 안내를 덮어쓰지 않는다. 원본 API도 기존 Project의 문서·저장 버전·검색 잠금을 변경하지 않는다.

원본 단위는 ‘같은 탭·프로젝트에서 편집한 구간’이다. 하나의 정답 객체나 하나의 버튼 행동과 같은 단위가 아니다.

| 종료 사유 | 값 |
|---|---|
| 검색 성공 | `search` |
| 사진 교체·자르기·사진 복원 등 프로젝트 변경 | `project_changed` |
| 페이지 이동·종료·새로고침 | `page_exit` |
| 작성자가 종료한 초안 복구 | `recovered` |
| 원본 수집 한도 종료 | `capture_limit` |

### 8.3 핵심 원본 필드

| 구분 | 중요 필드와 의미 |
|---|---|
| 식별 | sample_id, project_id, writer_id, result_id, schema_version |
| 라벨·품질 | 라벨 null/unverified, Raw 품질 pending, capture_status complete/limited |
| 공간 | 정규화 좌표계, CSS 캔버스 크기, DPR, 원본 사진·작업 크기 |
| 원본 획 | stroke_id·수집 순서·펜/지우개·색상·CSS 두께·입력 장치·종료 사유 |
| 원본 점 | 반올림·범위 제한 전 x/y, 상대 t, down/move/up/cancel, source, in_bounds, 가능한 필압·기울기 |
| 편집 | op_id·type·t·client_time·대상 획/요소 ID·document_patch |
| 연결 | event_id는 기존 행동 이벤트, source_stroke_id는 원본 펜·지우개 경로와 연결 |
| 상태 | initial_document, final_document, final_active_stroke_ids, duration_ms, undo_count |

상대 시간 원점은 해당 구간의 첫 펜·지우개 down이다. 이전 동작의 상대 t는 0이며 절대 시각·상세값은 기존 행동 이벤트로 확인한다. 새로고침 후 새 브라우저 시간 원점을 이전 원본에 이어 붙이지 않는다.

최종 획 ID는 최종 문서에 남은 펜 획의 ID다. 실제 가시 영역을 판단하려면 부분 지우기 마스크와 채우기·텍스트·도형도 함께 해석해야 한다. 모의 추천 결과 PNG는 스케치 분류용 학습 PNG가 아니다.

### 8.4 브라우저 보관과 서버 저장

| 위치 | 역할 |
|---|---|
| localStorage `roompick.events.<visitor_id>` | 기존 미전송 행동 이벤트 |
| sessionStorage의 작업 이력 | 현재 탭의 편집 상태와 Undo/Redo 복원 |
| IndexedDB `roompick-sketch-v1`, 버전 2, drafts | 작성 중 원본과 탭 식별 정보 |
| 같은 DB의 outbox | 아직 서버 성공 응답을 확인하지 못한 원본 |
| 같은 DB의 failed | 자동 재시도에서 분리된 HTTP 상태·오류; 원본은 outbox에 유지 |
| `db.sqlite3` | Project·SketchEvent·Composition |
| `media/rooms/`, `media/results/` | 기존 사진과 모의 합성 결과 |
| `data/sketch_raw/` | 별도 불변 원본 JSON; 첫 정상 제출 시 생성 |

원본 초안은 동작 완료 및 작성 중 약 1초 간격으로 보관한다. 전송은 스케치 화면에서 약 5초 주기·온라인 복귀·다음 접속 시 재시도한다. 이미 확정 보관된 작은 outbox만 종료 시 beacon을 추가 시도하며, 호출만으로 성공 처리하지 않는다.

## 9. 정합성·복구를 위해 보완한 사항

원본 검증은 UTF-8 JSON, NaN/Infinity 금지, 필드·버전·UUID·좌표·시간·포인터 순서·in_bounds·중복 ID를 확인한다. 시작 문서에 변경분을 재생해 최종 문서·대상 ID·Undo 횟수와 같은지도 검사한다.

서버 파일은 임시 파일 기록·flush/fsync 후 같은 파일 시스템의 hard link로 확정한다. 원본을 덮어쓰지 않는다. 같은 sample_id·같은 정규화 JSON은 HTTP 200 중복 성공, 같은 ID·다른 내용은 409로 거부한다.

코드 리뷰에서 발견한 다음 문제를 보완했다.

| 문제 | 보완 |
|---|---|
| 413/422 등의 한 샘플 오류가 뒤의 정상 전송을 막음 | 영구 입력 오류는 failed로 분리해 원본을 유지하고 뒤의 샘플 전송 계속 |
| HTML 404에 HTTP 상태가 전달되지 않아 재시도 큐를 막음 | JSON·비JSON 오류 모두 HTTP 상태 유지 |
| 수집이 서버 계약보다 커져 거부됨 | 원본 수집 한도 사전 종료, limited/review 표시; 기존 편집 계속 |
| 복제 탭이 다른 탭의 활성 초안을 확정함 | 원본별 Web Locks 소유권으로 복구 제한 |
| 시간 제한 응답만으로 탭 종료를 판단함 | 응답 지연 추정 대신 실제 독점 잠금 사용 |
| 잠금 전 읽은 오래된 초안이 확정 outbox를 덮어씀 | 잠금 안에서 drafts/outbox를 다시 읽고 이미 확정한 샘플 제외; 확정 쓰기까지 잠금 유지 |
| beacon이 로컬에 확정되지 않은 버전을 먼저 보냄 | 로컬 outbox 확정이 확인된 샘플만 beacon 대상 |
| 지우개 원본과 대상 요소의 연결이 불명확함 | source_stroke_id와 대상 ID·변경분을 명시적으로 연결 |

localhost/HTTPS 등 Web Locks 지원 환경에서만 작성 중 초안의 자동 복구를 한다. 일반 LAN HTTP에서는 작성 중 초안을 보관하고 자동 확정하지 않는다. 정상 구간 종료·outbox 재전송과 기존 편집 상태 복원은 이 제약과 구분된다.

| 한도 | 서버 제출 한도 | 브라우저 수집 종료 기준 |
|---|---|---|
| JSON 크기 | 4MiB | 약 3MiB |
| 원본 획 | 1,000 | 900 |
| 원본 점 | 100,000 | 90,000 |
| 편집 작업 | 1,000 | 950 |

한도에 도달하면 마지막 기록 상태를 저장하고 이후 원본이 미수집된다고 표시한다. 새 작업·새로고침에서 새 구간을 시작할 수 있다. 장시간 무손실 연속 수집을 위한 연결 구간·청크 전송은 구현하지 않았다. limited 샘플을 이후 검색 시점의 전체 문서라고 해석하면 안 된다.

품질 pass/review는 서버 응답이며 Raw의 pending을 덮어쓰지 않는다. 잘못된 구조는 quarantine으로 거부하고 서버 Raw에 저장하지 않는다. 별도 Curated 인덱스는 없다. pass는 라벨 정답·동의·학습 사용 승인 또는 모든 종류의 품질 검사를 보장하지 않는다.

## 11. 검증 결과와 증거의 범위

수집 확장 완료 당시 이 대화에서 확인한 결과는 다음과 같다. 이 문서 작성 요청에서는 서비스 테스트를 다시 실행하지 않았으므로 최신 변경분까지 같은 결과라고 단정하지 않는다.

| 검증 | 당시 결과 |
|---|---|
| 기존 서버 테스트 기준선 | 29개 통과 |
| 원본 확장 후 Django 전체 테스트 | 37개 통과 |
| 기존 계산·추가 원본 JavaScript 테스트 | 17개 통과 |
| Django 시스템 검사 | 문제 없음 |
| 기존 Edge 화면 회귀 | 사진 교체·자르기·통합 Undo/Redo·새로고침·부분 지우기·그룹·검색·결과 다운로드 등 통과 |
| 추가 Edge 수집 검증 | 초기 클릭·기존 결과 행동·지우개/취소/Undo/Redo/Clear·전송 실패·재전송·복제 탭·거부 샘플 뒤 정상 전송·실제 원본 내용 비교 통과 |

검증용 Django 서버는 별도 임시 DB·미디어·Raw 저장소를 사용했다. 실제 프로젝트 DB와 사진을 테스트 데이터로 덮어쓰지 않았다. 브라우저 검증 과정에서 임시 저장소의 원본 JSON 생성과 원본 경로 연결을 확인한 뒤 테스트 서버를 종료했다.

초기 테스트의 Windows 임시 폴더 접근 제한과 Edge 임시 프로필 제한은 샌드박스 밖에서 승인된 테스트 실행으로 해결했다. 일부 추가 테스트는 작업 URL 변경과 동일 원본 재전송의 HTTP 200을 실제 계약에 맞게 보정했다. 실패·보정 후 최종 통과까지 확인했으며, 초기 실패 결과만을 최종 상태로 취급하지 않는다.

별도 임시 저장소의 파일 생성은 실제 `data/sketch_raw/`에 사용자의 데이터가 쌓였다는 증거가 아니다. 정리 시점에 실제 원본 폴더는 없음을 확인했다. 첫 정상 제출 이후 파일이 생성되는 구조이며, 앞으로 직접 브라우저에서 행동해 DB·파일·전송 응답을 함께 확인해야 한다.

실제 스마트폰·태블릿, 장시간 고부하 편집, 디스크 장애, 브라우저 강제 종료의 완전한 복구, 공개 운영 환경은 검증하지 않았다. 모바일 뷰포트와 브라우저 터치 자동화는 실기기 검증과 다르다.

## 12. 데이터·로그 확인의 맥락

사용자는 실습처럼 브라우저 행동을 VS Code 터미널에서 확인하고 싶어 했다. 현재는 Kafka 소비자가 아니라 Django DB를 조회하는 구조다. 기존 export 명령도 Kafka 전송·offset·published_at을 변경하지 않는다.

모든 안내는 VS Code PowerShell의 현재 폴더가 `roompick`인 상태를 기준으로 한다. 사용자 요청에 따라 구조 트리와 조회 문서에 상위 작업 폴더부터 시작하는 경로 지정을 하지 않는다.

확인 순서는 초기 시작 클릭 → 사진 업로드 → 펜·지우개·Undo → 검색 → 결과 이미지 이동·다운로드 → DB 최근 이벤트·원본 파일·HTTP 응답이다.

```powershell
# 기존 행동 이벤트 수
python manage.py shell --no-imports -c "from sketch.models import SketchEvent; print(SketchEvent.objects.count())"

# 전체 기존 이벤트 출력
python manage.py export_sketch_events

# 정상 원본 제출 이후 파일 확인
Get-ChildItem -LiteralPath .\data\sketch_raw -Filter *.json
```

원본이 없으면 F12 → Application → IndexedDB → roompick-sketch-v1에서 drafts/outbox/failed를 확인한다. 서버 로그의 events/ 200과 samples/ 201 또는 동일 원본 200은 서로 다른 저장 성공이다.

별도의 Django 로그 파일 저장 설정은 없으며 현재 로그는 서버 실행 터미널에 출력된다. `lan-firewall.log`는 방화벽 스크립트 실행 기록으로 행동 이벤트나 Django 로그가 아니다. 필요하면 기존 서버를 종료하고 Tee-Object 방식으로 `roompick-server.log`를 생성할 수 있으며 명령 문서에 안내했다. 해당 안내만으로 이 대화에서 실제 로그 파일이나 서버를 실행한 것은 아니다.

## 15. 다음 GPT에게 적용할 작업 원칙

1. 기존 사용자 기능과 화면 흐름을 유지하는 조건부터 확인한다. 수집 개선을 이유로 지우개·Undo/Redo·검색·재시작을 다른 동작으로 교체하지 않는다.
2. 문서보다 최신 소스가 달라졌으면 차이를 밝힌다. 역사 설명·당시 테스트·현재 구현·후속 계획을 구분한다.
3. 기존 Django 구조와 의존성을 활용한다. 별도 FastAPI·Kafka·학습 모델을 이미 있는 것으로 가정하지 않는다.
4. Raw와 편집 문서·기존 이벤트·모의 결과를 구분한다. source/target ID와 부분 지우기 마스크를 확인한다.
5. 라벨·동의·품질·학습 준비 상태를 임의로 확정하지 않는다. 모의 추천을 학습 정답으로 취급하지 않는다.
6. 기존 DB·사진·결과·원본을 삭제하거나 초기화하지 않는다. 검증은 별도 저장소를 사용한다.
7. Windows PowerShell에 맞는 명령을 제공하고 manage.py가 있는 roompick에서 실행하도록 안내한다.
8. 파일구조 요청은 roompick부터 시작하며 파일별 기능은 한 줄로 설명한다. 긴 기능 목록과 확인 명령은 별도 문서로 구분한다.
9. 질문·검토용 초안을 요청하면 먼저 대화에 작성하고, 파일 생성 요청이 오면 docs에 저장한다.
10. 코드 수정 후에는 해당 테스트와 기존 기능 회귀를 확인한다. 실기기·강제 종료·장기 편집을 실제로 확인하지 않았으면 미검증으로 남긴다.

## 16. 이번 맥락 정리의 변경 범위

이번 요청에서는 현재 문서를 추가하고 관련 문서·코드·경로를 읽어 정합성을 확인했다. 앱 기능·DB·사진·원본·서버 설정은 변경하지 않았으며, 서비스나 테스트 서버를 새로 실행하지 않았다. 완료된 구현을 다시 만들거나 과거 원본 시간을 복원하지 않았다.
