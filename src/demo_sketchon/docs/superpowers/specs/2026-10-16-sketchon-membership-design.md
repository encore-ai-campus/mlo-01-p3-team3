## 1. 목적과 확정된 요구사항

현재 사진·Canvas·모의 합성·추천 기능을 유지하면서 회원 기능을 확장한다. 비회원은 계속 이용할 수 있고, 회원은 생성 결과를 프로젝트로 저장하고 나중에 수정·비교하며 추천 가구를 찜할 수 있다.

| 항목 | 이번 범위 |
| --- | --- |
| 인증 | 아이디·비밀번호·닉네임 자체 가입/로그인, 모든 페이지 우측 상단 로그인/로그아웃 |
| 로그인 유지 | 서버 세션 유지, 뒤로가기·앞으로가기 시 현재 계정 상태와 회원 UI 반영 |
| 비회원 생성 제한 | 서버가 확인한 IP별 한국 시간 하루 3회, 자정 초기화 |
| 횟수 계산 | 성공한 새 공간 생성만 차감; 실패·동일 요청 재전송·다운로드·배치 변경은 제외 |
| 회원 생성 | 이번 데모는 생성 횟수 제한 없음 |
| 비회원 작업 연결 | 로그인 시 현재 브라우저 익명 방문 ID의 아직 계정에 속하지 않은 작업·결과를 계정에 연결 |
| 프로젝트 저장 | 회원에게만 결과 저장 버튼 표시, 저장 당시 입력·배치·이미지를 버전으로 보존 |
| 수정 | 저장본을 복원해 편집·재생성하고 같은 프로젝트에 다음 버전 저장; 이전 버전 보존 |
| 비교 | 본인의 저장 이미지 두 개 나란히 비교; 같은 프로젝트 버전 또는 다른 프로젝트에서도 선택 가능 |
| 찜 | 회원에게 추천 카드 찜/해제, 마이페이지 찜 목록 제공 |
| 가구 사양 비교 | 다음 단계; 이번에는 실제/가상 사양을 만들어 비교표를 제공하지 않음 |
| 광고 | 오른쪽 작은 보조 카드 자리만; 무작위·개인화 노출·광고 제공자 연결은 다음 단계 |
| 문서 | 프로젝트 README·docs/ver2 현재판 갱신, 문서별 변경 요약 목록 제공 |

실제 AI·판매상품 연결은 계속 모의다. 회원 기능을 넣었다고 맞춤 광고 모델이나 실제 광고 노출이 구현됐다고 설명하지 않는다. 기존 docs/ver1 문서는 보존하고 현재판은 docs/ver2로 유지한다. 문서 버전과 기능 변경 단계는 별개이며 이번 기능은 변경이력의 8차로 정리한다.

## 2. 접근 방식과 선택 이유

검토한 방식은 다음과 같다.

1. **Django 기본 인증 + 작업에 계정 연결 필드 추가 (선택)**: 현재 Django·SQLite와 같은 서비스에서 구현하며 기존 owner/Raw ID를 보존한다. 로그인·해시 비밀번호·세션 처리를 프레임워크에 맡긴다.
2. 익명 owner 문자열을 계정 ID로 교체: 코드량은 적을 수 있지만 과거 Raw.writer_id와 Project.owner의 일치, 브라우저 큐·과거 이벤트 연결을 깨뜨릴 수 있어 사용하지 않는다.
3. 외부 인증/별도 회원 서비스: 소셜 인증·이메일 검증·추가 서비스 의존성이 현재 자체 가입 데모 범위를 넘어 이번에는 사용하지 않는다.

UI에 버튼만 숨기는 방식으로 권한을 구현하지 않는다. 작업·사진·결과 PNG·Raw 제출·추천·품목 수정·저장본·찜 API를 같은 계정 접근 기준으로 묶는다.

## 3. 화면과 이동

### 공통 헤더

- Home·편집·결과·로그인·가입·마이페이지에서 기존 검정 Sketch · On 로고를 유지한다.
- 비회원: 오른쪽에 로그인 링크. 가입 링크는 로그인 페이지에서도 제공한다.
- 회원: 닉네임·마이페이지 링크·로그아웃 버튼. 로그아웃은 CSRF 보호 POST로 처리한다.
- 편집·결과의 기존 생성 버튼·단계 안내와 겹치지 않게 우측 동작을 묶는다. 작은 화면에서는 간격·불필요한 안내를 줄여 가로 넘침을 막는다.
- 미인증 상태로 회원 페이지 URL/API에 직접 접근해도 본인 기록을 볼 수 없다. HTML은 로그인으로 안내하고 API는 인증 필요 응답을 반환한다.

### 로그인·가입

- 로그인: 아이디·비밀번호, 가입 이동 링크, 실패 안내, 원래 화면으로 돌아가기.
- 가입: 아이디·닉네임·비밀번호·비밀번호 확인. 비밀번호는 Django 검증·해시 보관을 사용하고 평문/해시를 행동 로그에 저장하지 않는다.
- 이메일·전화번호·소셜 로그인·비밀번호 찾기·계정 탈퇴는 이번 범위에 넣지 않는다. 회원정보 화면은 아이디 조회·닉네임 변경·현재 비밀번호 확인 후 비밀번호 변경을 제공한다.
- 가입 성공은 자동 로그인 후 원래 화면으로 복귀한다. next는 같은 서비스의 허용 경로만 사용한다.
- Home에서 로그인하면 회원 상태 Home으로, 편집/결과에서 로그인하면 해당 작업/결과로 복귀한다. 별도 회원용 Home을 복제하지 않고 같은 화면에 회원 기능을 표시한다.
- 편집 중 로그인 이동 전 현재 문서·설명을 저장하고 Raw/이벤트 보관을 시도한다. 명시적 저장이 실패하면 스케치를 잃고 이동하지 않도록 안내하고 현재 편집을 유지한다.

### 마이페이지

공통 왼쪽 메뉴는 **회원정보 / 인테리어 찜 목록 / 프로젝트 내역**이다. 모바일에서는 메뉴를 가로 탭 또는 접을 수 있는 메뉴로 바꾼다.

| 페이지 | 구성 |
| --- | --- |
| 회원정보 | 아이디, 닉네임, 가입 정보, 닉네임 수정·비밀번호 변경 |
| 프로젝트 내역 | 저장 프로젝트 카드·제목·최근 버전·저장 시각, 버전 목록·이미지 보기·수정·비교 |
| 프로젝트 비교 | 선택한 본인 저장본 두 개, 이미지·프로젝트명·버전·저장 시각을 나란히 표시 |
| 인테리어 찜 목록 | 저장한 가구 이미지·이름·모의 표시·찜 해제, 저장 원본 결과 연결 |

아직 프로젝트나 찜이 없으면 시작 동작을 제공하는 빈 상태를 표시한다. 사양 비교는 다음 단계임을 안내할 수 있으나 작동하지 않는 큰 비교 버튼을 중심 기능처럼 노출하지 않는다.

### 결과 페이지 추가 동작

- 회원에게만 **프로젝트에 저장** 버튼을 기존 이미지 다운로드·재시작 영역에 추가한다.
- 첫 저장은 프로젝트 제목을 입력하고 v1 생성. 저장한 프로젝트에서 이어온 결과는 같은 프로젝트의 다음 버전으로 저장한다.
- 비회원 DOM에는 저장/찜 버튼을 만들지 않고 서버에서도 저장 요청을 차단한다.
- 배치 저장·생성·회원 전환 처리 중에는 저장 버튼을 비활성화한다. 마지막 서버 저장 배치를 저장본으로 사용한다.
- 기존 이미지 내려받기·세 재시작·모서리/수치 크기 변경·추천 기능은 유지한다.

## 4. 광고 자리: 이번에 확정한 배치

실제 노출은 구현하지 않고 공통 작은 광고 placeholder만 둔다.

- PC 편집·결과: 기존 우측 설명/물체 패널 아래에 작은 카드. 별도 세 번째 큰 열을 만들지 않고 Canvas 폭 100%·사진 비율·편집/결과 사진 크기 일치를 유지한다.
- Home: 대표 사진 우측 구성의 아래쪽에 작은 보조 카드로 배치해 주요 시작 버튼·큰 이미지보다 강조하지 않는다.
- 마이페이지: 좌측 메뉴·본문 구성에서 본문 우측 보조 위치에 둔다. 새 로그인/가입 화면은 입력 폼 옆 작은 자리로 같은 스타일을 사용한다.
- 카드 높이는 PC 약 80~110px, 너비는 기존 우측 영역 안쪽으로 제한한다. 작은 `광고 영역` 표기와 연결 준비 안내만 제공한다. 스티키/화면 덮기/자동 팝업은 사용하지 않는다.
- 모바일: 본문 또는 해당 패널 아래로 이동하고 화면 오른쪽에 고정하지 않는다. 핵심 입력·결과 버튼을 가리지 않는다.
- placeholder 렌더링은 AD_IMPRESSION이나 PRODUCT_IMPRESSION을 생성하지 않는다. 상품 추천 카드와 광고 자리를 구분한다.

## 5. 데이터 모델

### 계정과 익명 기록

Django 기본 User를 사용하고 닉네임은 first_name을 닉네임 용도로 검증해 사용한다. 별도 이메일·프로필 테이블은 이번에 필요하지 않다. auth·필요한 세션/미들웨어·컨텍스트 프로세서·비밀번호 검증 설정을 추가한다.

Project에 nullable account FK를 추가한다. 기존 owner는 익명 방문 기록의 원래 값으로 유지한다. 기존 Raw 스키마·writer_id·파일 내용·이벤트 UUID·쿠키·브라우저 저장소 키를 회원 이름으로 일괄 바꾸지 않는다.

| 요청 상태 | Project 접근 조건 |
| --- | --- |
| 비회원 | account가 비어 있고 owner가 현재 익명 방문 ID인 작업 |
| 회원 | account가 현재 User인 작업. 로그인 시 아직 미연결인 현 브라우저 작업을 우선 귀속 |
| 다른 회원 | owner 문자열이 우연히 같거나 같은 브라우저를 써도 다른 account의 작업은 거절 |

회원이 다른 브라우저에서 만든 작업은 기존 owner가 해당 작업의 원래 방문 ID로 남는다. 그 작업의 Raw 수집 writer는 접근이 허용된 Project.owner를 기준으로 맞추고, 현재 브라우저 방문 ID와 계정 ID를 별개로 취급한다. 이를 기존 데이터의 소유권 검사를 생략하는 우회로로 사용하지 않는다.

로그인 시 현 익명 ID에 연결된 account=null 작업만 해당 계정에 귀속한다. Raw 파일을 고쳐 쓰지 않고 Project 관계로 계정에 연결한다. 이미 A 계정에 속한 작업을 B 계정으로 재귀속하지 않는다. 해당 브라우저의 프로젝트 전체 연결과 사용자가 프로젝트 내역에 명시적으로 저장하는 행위는 구분한다. 로그인만으로 과거 결과가 모두 프로젝트 카드로 자동 저장되는 것은 아니다.

로그아웃은 회원 인증 정보를 폐기하고 기존 비회원 식별 연속성을 유지하더라도 account가 지정된 작업에는 접근하지 못한다. 뒤로가기 캐시가 계정 화면을 다시 보여주지 않도록 인증 재확인과 비공개 응답 캐시 제어를 함께 적용한다.

### 비회원 IP 사용량

GuestGenerationUsage: client_ip(GenericIPAddress), usage_date(KST 날짜), successful_count, 갱신시각. `(client_ip, usage_date)` 유일 제약을 둔다. IP는 인증 ID나 사진 소유권으로 쓰지 않는다. 동일 IP여도 다른 브라우저의 작업을 서로 열 수 없다.

서버의 실제 연결 IP를 정규화해 사용하고 임의의 X-Forwarded-For 헤더를 믿지 않는다. 현재 직접 Django 연결을 기준으로 하며, 향후 리버스 프록시를 붙일 때 신뢰 프록시·클라이언트 IP 정책을 별도로 설정한다. IP 사용량 기록을 위해 IP를 저장하되 모든 정적 리소스 접속을 별도 방문 추적 테이블로 확장하지 않는다.

### 프로젝트 내역과 버전

현재 Project는 화면의 작업 단위이고 새로 저장할 프로젝트 내역은 사용자 라이브러리 단위이므로 별도 모델로 분리한다.

- SavedProject: UUID, user FK, title, 생성·갱신 시각.
- SavedProjectVersion: UUID, SavedProject FK, version_number, source Composition 참조, source_result_version, request_id, 저장 스냅샷 JSON, 별도 PNG 파일, 저장 시각.
- 스냅샷에는 입력 문서·요청 설명/스타일·현재/최초 배치·편집 사진 크기·참조 정보를 포함한다. 원본 업로드 파일은 기존 참조를 보호하고 별도로 복제하지 않는다.
- Project에 nullable saved_project 참조를 두어 저장본에서 이어온 편집·사진 교체·자르기·생성 결과를 같은 라이브러리 프로젝트와 연결한다. 기존 Project/Composition ID는 유지한다.
- `(saved_project, version_number)` 유일 제약과 저장 request_id의 멱등 처리를 적용한다. 중복 클릭/응답 재시도로 같은 버전이 둘 생기지 않게 한다.
- 저장 당시 Composition.version을 검사하고 PNG 복사본과 snapshot을 같은 저장 결과로 확정한다. 배치 변경과 경합해 서로 다른 이미지/좌표가 저장되지 않도록 잠금·조건 검사를 한다.
- 버전 PNG를 원본 Composition.image 경로만 참조해 저장하지 않는다. 원본 결과의 배치가 나중에 바뀌어도 저장본은 그대로 남는다.

프로젝트 저장 파일 경로는 예를 들어 `media/saved_projects/`로 분리하고 전용 소유권 검사 endpoint로만 제공한다. 저장 실패 시 새 파일을 정리하고 기존 버전은 그대로 둔다. 비교는 인증된 자신의 버전 UUID 두 개만 허용한다.

### 찜

WishlistEntry: UUID, user FK, stable_item_key, 표시용 상품 snapshot, 원본 RecommendationRun/항목 참조, 저장 시각. user와 stable_item_key를 유일하게 한다.

현재 모의 추천은 product_id=null이고 recommendation_item_id가 추천 실행마다 달라진다. 따라서 mock의 품목+샘플 variant로 안정된 식별 키를 제공해 같은 가구를 다른 결과에서 다시 찜해도 중복되지 않게 한다. live 연동 시 실제 product_id를 사용한다. 클라이언트가 보낸 상품명·이미지를 그대로 믿어 찜하지 않고 서버가 소유한 추천 실행의 항목을 조회해 snapshot을 만든다.

마음에 들어요(PRODUCT_SELECTED)와 찜은 별개다. 기존 반응 기능을 찜으로 몰래 바꾸지 않는다. 찜은 새 버튼과 API·이력으로 추가하며 사용자에게는 저장/해제 상태를 보여준다. 사양 필드는 아직 실제 데이터가 없으므로 임의의 실물 치수를 넣지 않는다.

## 6. 생성 3회 제한과 동시성

1. 생성 요청의 소유권·입력·request_id·revision·잠금 검사.
2. 같은 request_id로 이미 성공한 동일 입력이 있으면 기존 결과 반환. 이미 3회인 경우도 재전송으로 한 번 더 차감하거나 거절하지 않는다.
3. 비회원은 서버 IP와 현재 KST 날짜의 횟수를 확인한다. 3회면 429와 제한 설명·로그인 이동·다음 초기화 시점을 반환한다. 회원은 이 제한을 적용하지 않는다.
4. 모의 합성을 계산하고 DB 트랜잭션에서 제한 행을 조건부로 갱신한다. 최초 행 생성 경합도 유일 제약/트랜잭션으로 처리한다.
5. 새 결과 저장·작업 잠금·성공 횟수 증가를 같은 트랜잭션에 묶는다. 다른 동시 요청이 마지막 횟수를 먼저 사용하면 새 결과를 성공 처리하지 않는다.
6. DB/파일 저장 실패는 카운터 증가·결과 생성·작업 잠금을 되돌리고 생성된 미확정 파일을 정리한다. 화면 재시도 가능 상태를 유지한다.

제한 행을 증가시킨 뒤 프로젝트 조건부 잠금에 실패한 경우도 트랜잭션 전체를 되돌린다. 중간 단계에서 오류 응답만 반환해 앞선 카운터 증가가 커밋되는 구현을 허용하지 않는다. 같은 요청의 동시 실행 경합은 저장된 동일 결과를 재조회해 입력 일치와 권한을 확인한다.

합성 계산을 트랜잭션 밖에서 하더라도 최종 반영 직전 카운터를 다시 검사한다. UI에 표시한 잔여 횟수를 유일한 검사 기준으로 사용하지 않는다. 다운로드·결과 배치 이동·추천·저장·찜은 생성 횟수에서 제외한다. KST 날짜별 행을 사용하므로 서버 재시작이나 쿠키 초기화로 횟수가 초기화되지 않는다.

같은 NAT/Wi-Fi의 비회원은 IP별 3회를 공유할 수 있다. IP 변경·VPN을 동일인 판별로 막는 기능은 요구 범위에 없다. 이 제약과 실제 제한 기준을 사용자·문서에 명시한다.

## 7. 브라우저 뒤로가기·계정 전환

- 로그인 상태는 서버 세션이 기준이며 화면의 boolean만 바꾸는 방식은 사용하지 않는다.
- 공통 회원 상태 API/헤더를 두고 pageshow, 특히 BFCache 복원과 다른 탭 복귀 시 현재 인증 상태를 확인한다.
- 로그인으로 돌아온 비회원 화면은 회원 헤더·저장/찜 권한·갱신된 CSRF를 반영한다. 로그인 페이지가 히스토리에 남아 있더라도 이미 인증됐다면 원래 화면 또는 회원 상태 화면으로 안내한다.
- 편집 화면의 로그인 전 입력은 명시적 저장 또는 검증된 임시 복원으로 보존한다. 모든 pageshow에 무조건 reload하여 미저장 그림을 지우지 않는다.
- 계정이 달라졌거나 로그아웃된 경우 이전 회원의 화면/작업은 권한 재확인 전 숨기고, 소유권을 잃은 편집을 새 계정에 저장하지 않는다.
- 이전 회원 전용 pending 요청·추천 응답·찜 상태를 새 회원 화면에 섞지 않는다. 계정 변경 시 진행 요청을 무효화하고, 옛 작업의 Raw/이벤트는 원래 작업/작성자 ID를 유지해 서버에서 검증한다.
- 공유 브라우저의 owner 값만으로 A 회원의 내역을 B 회원에게 넘기지 않는다. 비공개 이미지·saved API·추천/사진 endpoint 모두 같은 원칙을 적용한다.

## 8. API·파일 변경 범위

## 10. 검증 및 수용 조건

### 인증·소유권

- 가입·중복 아이디·잘못된 비밀번호·로그인/로그아웃·닉네임/비밀번호 변경·CSRF·외부 next 거절.
- 각 페이지의 비회원/회원 헤더 전환, 뒤로/앞으로 이동·BFCache·다른 탭 로그인/로그아웃 후 상태 확인.
- 기존 비회원 작업 연결과 익명 ID 유지, 다른 브라우저의 본인 계정 기록 접근.
- 같은 브라우저 A 로그아웃→B 로그인 후 A의 작업·사진·결과·Raw·저장본·찜·추천에 접근할 수 없음.
- 비회원 저장/찜 버튼 미노출뿐 아니라 직접 API 호출도 거절.

### 제한·동시 요청

- 같은 IP 성공 1~3회·4회 거절, 다른 IP 독립, KST 자정 경계·서버 재시작·쿠키 변경 후 기준 유지.
- 실패와 중복 request 재전송 비차감, 회원 무제한·다운로드/배치 비차감.
- 마지막 1회 남은 상태의 동시 다른 생성 요청에서 한 건만 성공.
- 동시 같은 request 재전송에서 결과/카운터 중복 증가 없음, 헤더로 IP 위조 불가.
- DB·파일 저장 실패 시 카운터·잠금·미확정 파일 정합성.

### 저장·찜·비교

- v1 저장·수정 복원·재생성·v2 저장, v1 PNG/입력/배치 불변, 저장 중 배치 변경 경합·중복 클릭.
- 사진·스케치·설명·스타일 복원, 제목·버전 목록·본인 이미지 두 개 비교, 다른 사용자 UUID 거절.
- 찜 추가·해제·새로고침 유지·다른 결과의 같은 mock 상품 중복 방지·다른 회원 격리.
- 모의 상품의 사양·가격을 실제 데이터로 만들어내지 않음, 광고 자리에서 실제 노출 이벤트가 발생하지 않음.

### 기존 기능·데이터·UI

- 기존 Django/Node 회귀와 격리 DB의 PC/모바일 생성·Raw 전송·사진/편집/결과 이력 검사.
- migration 전 DB·미디어·Raw 백업, 이전 PK·파일 해시·Raw 내용 보존과 신규 필드 기본값 확인.
- 오른쪽 광고 카드가 Canvas 폭·사진비율·기존 패널·저장/다운로드 버튼을 침범하지 않음.
- 320/390px 모바일과 PC에서 로고·공통 로그인/로그아웃·마이페이지·비교 화면 넘침 확인.
- docs/ver2의 내부 링크·PowerShell 예제 문법·문서별 업데이트 요약 확인.

이 검사는 구현 후 실제 결과를 확인해 기록한다. 설계 시점에는 통과·적용·마이그레이션 완료라고 표기하지 않는다.

## 11. 실행 순서와 적용 경계

설계 검토 → 구체적인 구현계획·검증 단계 작성 → 사용자 구현계획 검토 및 현재 대화에서 실행 방식 선택 → 데이터 백업·격리 테스트 → 인증/소유권·quota → 저장 버전·찜 → UI·광고 자리 → 전체 회귀·문서 → 대상 DB migration 및 공유 서버 반영 순서로 진행한다.

저장 대상 경로는 현재 도구의 기본 쓰기 허용 범위 밖이므로 설계·코드 저장에는 해당 경로의 쓰기 권한이 필요하다. 문서 작성 승인을 앱 기능·DB 변경 완료로 해석하지 않는다. 기존 서비스 경로와 실행 명령을 확인한 뒤 해당 서버만 반영한다.
