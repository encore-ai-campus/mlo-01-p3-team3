# 서버 계측 기록과 개선 계획 (2026-10-23)

크롤 완료 유한 배치 경로를 실제 서버(Spark Master·Worker 3대, Garage Delta, Kafka, Mongo, 서비스 MySQL)에서 처음 끝까지 돌린 기록이다. 원본 수치는 [verification/server_batch_20261023.json](verification/server_batch_20261023.json)에 있다. 측정 절차는 운영자 작업 폴더의 `/v2-server-deploy` 스킬이다([서버 이전](server-migration.md) 참고).

## 환경

| 항목 | 값 |
|---|---|
| 릴리스 | manifest `553f421b…` (기준 HEAD `af29b21` + Kafka producer 수정). 100건 첫 시도는 `14e5fa33…`, canary는 `5c86d2ca…` |
| Master | 2 vCPU, 3.4 GB, 디스크 여유 7 GB |
| Worker | 3대 × 2 vCPU, 3.4 GB. Spark 설정은 Worker당 1코어, **총 3코어**(운영 프로필과 동일) |
| Kafka | 검증 topic `pj3-pipeline-verify-…`, **파티션 1개**, 보존 1일·2 GB, 메시지 최대 약 1 MB. 운영 topic은 쓰지 않음 |
| Delta | `s3a://pj3-data/direct-v2/finite-v1` (새 네임스페이스, 측정 시작 시 비어 있음) |

| 정책 | epoch 34 window에서 승인된 카테고리 매핑 42개와 규칙. 유효 기간 필드는 제거(v2는 관측 수집 시각 기준으로 판정하므로 그대로 두면 전부 `QUALITY_WAIT`). 이미지·비교 링크 필수 아님 |

## 입력

서비스 DB에 **아직 없는 상품**만 골랐다. 원천 65,498개 상품 중 관측 1건·승인 카테고리 해당이 47,112개, 그중 미게시가 45,197개였다. 이미지 상태가 있는 것부터 순서대로 3개(canary), 100개(두 번째 시도), 다음 100개(세 번째)를 썼다. 같은 상품을 다시 게시하면 기존 행을 갱신하게 되어 "신규 게시 경로"를 잴 수 없기 때문이다. 드라이버는 게시 직전에 입력 상품이 DB에 없는지 확인하고, 하나라도 있으면 쓰지 않는다.

epoch 34(v1)와 같은 상품으로 재지 않았으므로 v1과의 직접 비교는 아니다. v2 Delta 테이블이 비어 있던 점도 다르다.

## Spark 분석

처리 단계 Spark 앱(100건 초기): 실행 354초, 작업(job) 184개, task 446개, 실행기 실제 작업 합계 546초(3코어에 분배). Silver 정제·저장 구간에서만 작업 64개, Gold 52개, Kafka 읽기·검증 39개였다. 작업 수는 AQE가 셔플 단계마다 작업을 나누므로 action 수보다 많다.

- **고정 비용이 지배적이다.** 같은 입력을 다시 돌려 정규화를 재사용하고 서비스 쓰기가 0건이어도 처리 349초, 게시 73초로 거의 같았다.
- **Delta 쓰기 단계 1회가 20~34초.** 이 시간은 `write()` 호출 전체로, 저장 전 계산·검증 작업·파일 쓰기·로그 처리가 섞여 있다. 순수 로그 커밋 비용이 아니다. 100행을 bucket 128개로 분할해 쓰므로 작은 파일이 100개 안팎 생기고, canary 3행도 22초였다. 파일 수·커밋·계산 중 무엇이 지배적인지는 분리 측정하지 않았다(가설).
- **게시 89초 중 MySQL은 12초.** Spark 세션 7초를 빼면 약 70초가 남는다. Gold 결과(파일 100개 안팎)를 읽어 Driver로 가져오는 시간과 게시 요청 구성이 섞여 있고, 둘을 나눠 측정하지 않았다.
- **자원은 놀았다.** Master load 0.4, Worker CPU 약 90% 유휴. 실행기 작업은 3코어에만 분배됐고, 그 시간의 상당 부분도 Garage I/O 대기다.
- 3건 → 100건에서 처리 148초 → 354초, 실행기 작업 72초 → 546초. 상품당 약 2초가 늘고 나머지는 고정 비용이다.

## 확인된 것과 주의할 것

- 신규 상품만 게시, 무변경 재실행은 정규화 재사용과 서비스 쓰기 0건, 감사 통과. 이전 세션이 고친 Mongo 일괄 저장 중복 경로(복합 키)도 실제 Mongo에서 통과했다.
- **이미지 연결이 0건이다.** 103개 상품 모두 `product_images`가 만들어지지 않았다. 2026-10-24에 Mongo를 읽기 전용으로 확인해 보니, 측정에 쓴 관측 200개(B안 100, Spark 100. canary 3은 미확인)는 10-15 07:12–07:26 크롤 구간에서 이미지 파일을 내려받지 않은 관측이었다. 원천 이미지 참조 428개는 모두 `acquisition_state=UNAVAILABLE`이고 sha256이 비어 있다. 이미지 상태 슬롯도 모두 저장 위치·체크섬 없이 `UNCONFIRMED`(revision 1)다. 그래서 Gold가 쓸 이미지가 없었다. 게시 조건에 이미지가 필수가 아니라서 이미지 없이 게시됐다.
  - 같은 관측에는 나중에 이미지를 붙일 수 없다. 이미지와 함께 다시 수집하면 체크섬·위치가 이전 값과 달라져 수집 단계가 `IMAGE_STATE_IDENTITY_CONFLICT`로 거부한다. 이미지를 받은 새 크롤 관측이 들어와야 새 이벤트로 처리된다.
  - 이 측정은 이미지 게시(`assets`, `product_images`) 비용을 포함하지 않는다. 컬렉션에는 `AVAILABLE` 이미지가 있으므로, 다음 측정은 이미지가 있는 구간에서 키를 고른다.
  - 측정 상품을 서비스 MySQL에 게시한 것은 잘못이었다. 측정용 게시 상품 203개(canary 3, Spark 100, B안 100)는 삭제하기로 했다. 이후 측정은 서비스 DB에 게시하지 않는다.
- 무변경 재실행의 게시 결과가 `PUBLISHED`로 표기된다. 저장된 영수증을 돌려주기 때문이며 INSERT 0건으로 쓰기가 없었음이 확인된다. 표기를 `REUSED`로 구분하면 읽기 쉽다.
- v1 epoch 34는 활성화를 빼고 18분 33초였다. 상품·테이블 상태가 다르므로 "2배 이상 빠르다"는 방향만 참고한다.

### 실행 순서

1. **1단계(설정만)**: A1·A2·A3 적용, 500건 측정. 기준: 처리 시간, 코어 사용, 메모리 부족 없음. 결과는 아래 "1단계 시도 결과": A1은 데몬 설정 때문에 불가, A3는 효과 없음.
2. **2단계(코드)**: B1·B2·B3·C1. 새 네임스페이스에서 500건 재측정. 기준: 쓰기당 10초 이하, 작업 수 절반, 무변경 재실행의 쓰기 0 유지.
3. 결과를 보고: B4·B5·C2·D1(1,000건).
4. 필요하면: B6·C3·C4.

1~2단계 후 100건 처리는 150~230초, 게시는 30~50초로 추정한다. Garage 쓰기 비용이 파일 수에 비례하는지 커밋 수에 비례하는지에 따라 폭이 넓다. 임시 경로에 파일 100개와 3개로 같은 100행을 써서 비교하면 5분 안에 가릴 수 있다.

### 1단계 시도 결과 (16:44, 500건)

- **A1은 앱 설정으로 불가능하다.** Spark Worker 데몬이 `SPARK_WORKER_CORES=1`, `SPARK_WORKER_MEMORY=1g`로 떠 있어 실행기당 2코어 요청을 어느 Worker도 받지 못했다. 처리 앱은 16:48:40에 떴지만 실행기가 하나도 등록되지 않고 "Initial job has not accepted any resources"로 20분 대기했다. SIGINT로 중단했고 job `91444d2d…`는 `RECOVERY_REQUIRED`, lease는 반납됐으며 MySQL에는 쓰지 않았다. 두 번째 vCPU를 쓰려면 Worker 데몬 재설정·재시작이 필요한데, 이는 운영 파이프라인과 공유하는 변경이라 별도 승인이 필요하다. 드라이버 기본값은 1코어·총 3코어·분할 6으로 되돌렸다.
- **A3(in-flight 5)은 효과가 없었다.** 500건 85 MB 발행이 126초(0.67 MB/s)로 100건 때(0.63 MB/s)와 같다. 병목은 클라이언트 파이프라이닝이 아니라 브로커 쪽(파티션 1개·복제·TLS)이다. 입력 등록도 98초로 건당 0.2초가 그대로다.
- 위 계획표의 A1·A3는 이 결과로 효과를 낮춰 본다. 자원 활용은 Worker 데몬 변경(A1′)과 Kafka 파티션(C4) 또는 Kafka에 원문 대신 참조만 싣는 변경으로 넘어간다.

## 설계 질의와 판단

계측 중 나온 질문과 그 판단 근거를 남긴다. 추정은 추정으로 표시했다.

### 1~2단계를 하면 고정 비용이 그만큼 줄어드나

방향은 맞지만 "100건 처리 358초 → 150초"는 측정이 아니라 추정이다. 358초의 구성과 1~2단계로 줄어드는 정도는 이렇다.

| 구성 | 시간 | 1~2단계 효과 |
|---|---|---|
| Delta 쓰기 단계 7회(100행에 20~34초씩, 계산 포함) | 150~200초 | 파일 수가 원인이면 대부분 감소(B1). 내부 구성은 미분리 |
| Driver 검증 작업·Delta 로그 왕복(작업 184개) | 60~90초 | 일부 감소(B2·B3). 작업당 스케줄링 0.3~1초는 남음 |
| 실행기 실제 작업(546초를 3코어에 분배) | 100~180초 | 코어 확대 시 절반. 상당 부분이 Garage I/O 대기라 그만큼은 안 줄 수 있음 |
| Spark 세션 기동 | 7~13초 | 그대로(B5는 3단계) |
| Kafka 1파티션 읽기 | 수~십수 초 | 그대로(C4는 4단계) |

Garage 쓰기 비용이 **파일 수**에 비례하는지 **커밋 횟수**에 비례하는지가 아직 분리되지 않았다. canary 3행 쓰기가 22초, 100행이 29초였다는 점은 커밋당 고정 비용이 크다는 쪽 증거다. 현실적인 범위는 1~2단계 후 100건 처리 150~230초, 게시 30~50초다. 같은 100행을 임시 경로에 파일 100개·3개로 각각 써서 비교하면 5분 안에 가릴 수 있다.

### 배치 크기는 조정 가능한가

100은 파이프라인 제한이 아니라 계측 입력을 100개로 고른 것이다. 운영에서는 크롤 한 번의 변경분이 한 배치이고, 상한은 설정이다.

| 지점 | 현재 값 | 성격 |
|---|---|---|
| `batch_limits.max_events` | 10,000 (최대 100,000) | 배치당 이벤트 상한 |
| `batch_limits.max_input_bytes` | 512 MB | 배치당 입력 바이트 상한. 관측 평균 170 KB라 약 3,000건 |
| `pending_bytes` / `pending_batches` | 1 GB / 3 | 대기 중 배치 합계 |
| 게시 묶음 100상품·32 MB, Outbox 묶음 200건·8 MiB | 내부 분할 | 배치 크기 제한이 아님 |
| 내보내기 도구 키 수 | 10,000 | 재생 도구 상한 |

이 서버의 실질 상한: 입력 바이트(약 3,000건), Kafka topic 보존 2 GB(10,000건이면 거의 가득), Master 디스크 여유 7 GB, 분할 수 3(큰 배치는 6~12 필요). 3건 148초·100건 354초에서 고정 비용 약 140초, 상품당 약 2초로 보면 1,000건은 처리 약 35분·게시 약 10분이다(외삽).

### 100건이 다 Bronze에 들어가야 Silver로 가나

지금은 그렇다. 단계마다 배치 전체를 한 번에 처리하고 Bronze 완료 기록이 커밋돼야 Silver가 시작된다. 그러나 "적재된 행부터 Kafka로 다음 단계에 밀어 넣는" 방식은 권하지 않는다. 비용이 행 수가 아니라 **커밋 수**에 붙으므로(정규화는 관측당 11 ms, Bronze 100건 92초의 대부분은 커밋·검증 왕복) 행 단위 전달은 커밋을 행 수만큼 늘려 v1의 "100건에 append 30회" 문제로 돌아간다. 설계가 상시 consumer와 streaming checkpoint를 뺀 것과도 충돌한다.

기다리지 않게 하는 방법은 세 가지이고 모두 설계 안에 있다.

1. **배치 안: Bronze 저장을 임계 경로에서 떼기.** Silver가 Bronze를 Delta에서 다시 읽지 않고 같은 프로세스 메모리의 행으로 바로 시작한다. Bronze Delta 쓰기는 스레드로 보내고, Silver 완료 기록은 Bronze 기록 커밋 뒤에만 쓴다(C1의 확장).
2. **배치 사이: 단계별 writer 파이프라인.** Bronze는 `input_index`, Silver는 `normalized_history`, Gold는 자기 스냅샷, 게시는 MySQL에 쓴다. 테이블이 다르므로 배치 n+1의 Bronze, n의 Silver, n−1의 Gold, n−2의 게시를 동시에 돌려도 "테이블당 writer 하나"가 지켜진다(설계 §6 상태 축). `process` 잠금을 단계별로 나누고 `batch-work --phase bronze|silver|gold|publish`가 필요하다. 처리량은 가장 느린 단계 기준이 된다.
3. **배치를 작게, 자주.** 100건마다 2)에 흘린다.

Bronze 100건 92초의 구성과 줄일 수 있는 폭(추정):

| 구성 | 지금 | 조치 | 후 |
|---|---|---|---|
| Kafka 읽기 + 검증 3회 + Python 검증 UDF | ~40초 | B2·B3 | ~8초 |
| 분류(Executor) | ~10초 | 분할 6 | ~5초 |
| Bronze 스냅샷 커밋(파일 ~100개) | 29초 | B1 | 5~8초 |
| 입력 색인 append + 메타데이터 | ~13초 | B1·B2 | 3~5초 |
| 합계 | 92초 | | 약 20초 |

이 서버의 제약: Driver 하나가 768 MB라 2코어·3.4 GB Master에서는 Spark 앱 2개가 한계다. 4단계 완전 병행 대신 "Bronze+Silver 앱 하나, Gold+게시 앱 하나"가 현실적인 첫 단계다. Kafka 1파티션 0.65 MB/s도 파이프라인 병목이 된다.

### 100건이 ms~s 단위여야 한다면, 구조 변경으로 가능한가

**ms는 불가능하고, 초 단위(100건에 5~20초)는 구조를 바꾸면 가능하다.** 지금 구조(단계마다 Spark 작업과 Delta 커밋)로는 안 된다.

데이터 자체의 바닥(100건 17 MB, 측정값 기준):

| 일 | 바닥 |
|---|---|
| 17 MB 네트워크 이동(LAN) | 1초 미만 |
| 정규화 100건(관측당 11 ms) | 약 1초 |
| Gold 계산 100건 | 1초 미만 |
| 객체 저장소에 파일 몇 개 쓰기 | 2~5초 |
| MySQL 100상품 일괄 INSERT | 1~2초 |

"건당 ms"는 맞지만 복제·TLS·내구 저장이 끼는 100건 묶음은 한 자릿수~십수 초가 바닥이다. 지금 수백 초인 이유는 데이터가 아니라 구조다.

| 구조 비용 | 100건에서 | 성격 |
|---|---|---|
| Delta 쓰기 단계 7회 × 20~34초 | 150~200초 | 계산·파일 쓰기·로그 처리 포함, 내부 구성 미분리 |
| Spark 작업 184개의 스케줄링·로그 왕복 | 60~90초 | 검증·존재 확인마다 작업 하나 |
| 단계마다 Delta 재읽기 | 수십 초 | Silver가 Bronze를, Gold가 Silver를, 게시가 Gold를 다시 읽음 |
| Spark JVM 기동 ×2~3 | 15~40초 | 명령마다 새 세션 |
| Kafka 발행 17 MB | 27초 | 파티션 1개·복제·TLS에서 0.65 MB/s |
| MySQL 7,000문장 | 12초 | 상품별 SELECT/INSERT |

초 단위로 가는 구조는 두 가지다.

| 구조 | 내용 | 100건 바닥 추정 |
|---|---|---|
| A. Spark·Delta 유지, 재구성 | 세션 하나에서 Kafka를 한 번 읽고 Bronze→Silver→Gold를 메모리로 이어 계산. Delta 쓰기는 비동기 스레드, 단계 기록은 쓰기 뒤. 검증 묶기·파일 수 축소·MySQL 일괄·게시까지 같은 세션 | 15~30초. 작업당 스케줄링 0.3~1초가 열 개 안팎 남고, 비동기 Delta 커밋도 다음 배치 전에는 끝나야 함 |
| B. 100건 규모는 Python 단일 프로세스 (README §10 비교 후보 B) | Master의 Python이 Kafka 100건 → 정규화 → Gold → 파일 lake(또는 JVM 없는 `deltalake`) → MySQL 일괄. Spark는 대규모 초기 적재·재계산용으로 유지 | 5~10초. 전체 원천 11 GB(65,498 × 170 KB)도 시간 단위 배치로 감당 |

둘 다 Kafka 발행은 따로 풀어야 한다. 파티션 확대(C4, ACL 승인 필요) 또는 **Kafka에 원문 대신 불변 원천 참조만 싣고** 처리 측이 Mongo에서 `$in`으로 묶어 읽는 방식이다. 설계가 허용하는 envelope이고, Worker에 pymongo가 없어 원문을 실었던 선택을 되돌리는 것이다. B안(Master의 Python)에서는 자연스럽다.

측정된 데이터 양(배치 17 MB, 전체 11 GB)으로는 B안이 요구에 맞고 A안은 그 2~3배다. B는 "대용량 도구 유지"라는 설계 방향을 100건 규모에서 바꾸는 결정이므로 프로토타입 측정 후 정한다.

### 사용자 데이터가 들어오고 동접 수십 명이면

사용자 데이터는 이 배치 경로로 들어오지 않는다. 설계상 세 경로가 따로 있다.

| 경로 | 성격 | 지금 구조 | 수십 명 동접 |
|---|---|---|---|
| 상품 자료 준비(이 문서의 계측) | 오프라인 주기 배치, 사용자가 기다리지 않음 | v2 유한 배치 | 영향 없음 |
| 사용자 요청 → 추천 | 온라인, 수 초 응답 | Django + **SQLite** 작업 원장 + 별도 워커. `MAX_PENDING=8`, 워커 풀 4, 해석 모델 동시 2·분당 10회 | **지금은 안 됨** |
| 사용자 행동(노출·클릭·선택) | 비동기 이벤트, 집계는 나중 | 이벤트 → Kafka → Bronze/Silver/Gold → 일별 집계 | 됨. 양이 작고 사용자가 기다리지 않음 |

사용자 요청 경로가 안 되는 이유는 계산이 아니라 두 상한이다. 외부 AI 호출 제한(동시 2·분당 10회, 30명이 한 번씩 요청하면 마지막 사람은 3분 대기)은 API 할당량에 맞춘 의도적 제한이라 할당량을 늘리지 않으면 그대로다. SQLite 단일 DB와 대기 8건은 로컬 시연 설정이며 설계는 MySQL·Kafka 작업 계약으로 옮기도록 되어 있다.

가장 빠른 구조는 **온라인과 오프라인을 완전히 분리하고 사용자 요청에는 Spark·Delta를 끼우지 않는 것**이다.

1. **사용자 요청(수 초):** Django는 MySQL 원장에 접수만 하고(HTTP 202), Python 워커 N개가 Kafka 요청 topic에서 처리한다. 워커는 상품 벡터·카탈로그를 메모리에 올려 두고 순위는 CPU로 ms 단위에 계산한다. 상품 게시가 끝나면 버전 번호로 알리고 워커가 새로 읽는다. 응답 시간은 외부 AI 호출(2~10초)이 결정하므로 동접 N에 필요한 것은 워커 수가 아니라 **API 할당량**이다(예: 50명이 2분에 한 번이면 분당 25회). 워커는 동시 API 호출 수만큼(4~8개).
2. **사용자 행동(비동기):** Kafka에 이벤트만 쌓고 집계는 상품 경로와 같은 유한 배치로 시간 단위. 이벤트는 KB 단위라 파티션 1개로도 수십 명은 충분하다.
3. **상품 자료(분 단위):** B안으로 배치당 5~10초. 자원은 사용자 경로와 나눠 Application 서버(`app-01`)에 워커, Master에 배치를 둔다.

확인할 것: `app-01`은 IP만 확인됐고 접속·설치 상태 미확인. 서비스 MySQL을 사용자 요청·상품 게시·행동 집계가 함께 쓰므로 게시 트랜잭션(지금 100상품 11초)을 짧게 끊어야 한다(B6도 도움).

### Spark Worker 데몬 코어 변경의 효과

현재 Worker 3대의 데몬은 `SPARK_WORKER_CORES=1`, `SPARK_WORKER_MEMORY=1g`이다. VM은 각 2 vCPU·3.4 GB, 실행 중 사용 약 770 MB(여유 약 2.6 GB). 코어 2·메모리 2g로 바꿔 실행기당 2코어·1.5 GB를 쓰는 경우:

| 항목 | 효과(100건 측정 기준 추정) | 근거 |
|---|---|---|
| 처리 단계 | 358초 → 270~320초 (10~25%) | 실행기 작업 546초가 3코어에 분배돼 실행기 몫이 약 180초. 코어 2배면 이 몫이 절반이 되지만 상당 부분이 Garage I/O 대기라 이상치(90초)보다 작다. 처리의 절반 이상은 Driver 쪽 스케줄링·Delta 로그 왕복이라 코어와 무관 |
| 500~1,000건 | 30~40% | 배치가 커질수록 실행기 몫 비중 증가 |
| 메모리 1.5 GB | 큰 배치의 디스크 넘침 감소 | 768 MB는 500건 이상에서 캐시가 넘칠 수 있음 |
| B안 | 효과 없음 | Spark 미사용 |

위험: 데몬은 v1 운영 파이프라인과 공유하며 재시작 시 실행 중 앱이 끊긴다(현재 v1은 정지 상태). v1 프로필 `total_cores=3`이라 6코어가 되면 v1·v2가 동시에 뜰 수 있다. Worker 2 여유가 가장 적어 2g가 빠듯할 수 있다. 변경은 Bastion ansible role의 인프라 작업이라 담당(신성민) 요청이 필요하다. Spark 경로(A안)에는 해 볼 만하지만 효과는 제한적이며, B안 결과를 먼저 보고 결정한다.

## B안 프로토타입 (`server-python` 모드)

Spark 없이 Master의 Python 프로세스 하나로 같은 계약을 처리한다. 코드는 `batch_bootstrap.py`(모드·설정 검증), `adapters/kafka_batch.py`의 `KafkaRangeReader`(manifest offset 범위만 읽기, group·commit 없음), `adapters/batch_local.py`(Bronze·Silver 원천 일괄 조회, 정규화 재사용 선판정·일괄 저장), `application/outbox.py`(`wire_payload=False`면 Kafka에 참조만)다. Lake는 Master 로컬 파일 lake이고 게시는 기존 MySQL 게시기다. 계측 드라이버는 `start publish N python`으로 이 모드를 쓴다.

Lake가 Master 로컬 디스크라 다른 서버와 공유되지 않는다. 계측용이며, 운영 경로로 쓸지는 설계 문서의 Bronze 보존 계약("Delta")을 바꿀지와 함께 결정한다.

### 1차 시도 (17:27, 100건)

| 단계 | Spark 경로 100건 | B안 |
|---|---:|---:|
| 몽고 내보내기 | 6.5초 | 17.4초 |
| 입력 등록 | 20.4초 | 46.5초 |
| Kafka 발행 | 27.5초 (원문 17 MB) | **10.8초** (참조만) |
| 처리 | 358초 | 실패 |

Kafka 읽기에서 `KAFKA_READ_GROUP_AUTHORIZATION_FAILED`로 멈췄다. 이 principal에는 consumer group ACL이 없고(인계 문서 6절), librdkafka는 `group.id`가 있으면 assign 전용 읽기에서도 group coordinator를 찾는다. Java 클라이언트를 쓰는 Spark는 같은 계정으로 문제가 없었다. `group.id`를 빼고 coordinator 측 오류는 읽기를 막지 않게 고쳤다(다른 읽기 오류는 코드로 중단). job은 `RECOVERY_REQUIRED`, MySQL에는 쓰지 않았다. 내보내기·입력 등록이 Spark 경로 때보다 느렸던 원인은 다음 측정의 단계별 계측으로 확인한다. 재측정 결과는 이 절에 추가한다.

2차(17:37)는 confluent-kafka가 `group.id` 없는 consumer를 거부해(`ValueError`) 입력 등록 단계에서 멈췄다. 읽기 도구를 Kafka 실행기 시작 시점에 만들었기 때문에 Kafka를 쓰지 않는 단계까지 실패한 것이다. `group.id`를 되살리고(commit 없음, coordinator 오류는 건너뜀) 읽기 도구는 첫 읽기 때 만들도록 고쳤다.

서비스 DB 상품 3,424 → 3,524, 100개 모두 `ACTIVE`, 감사 `AUDIT_OK`. Kafka 읽기에서 group 권한 오류를 건너뛰고 지정 offset으로 정상 읽혔다. 이미지 연결은 이번에도 0건이다.

**남은 시간의 대부분은 계산이 아니라 제어 원장(Mongo) 왕복과 중복 읽기다.** 순수 계산(분류·정규화·Gold)은 합쳐 2초 남짓이다.

| 남은 비용 | 시간 | 원인 | 조치 | 기대 |
|---|---|---|---|---|
| Silver 원천 재읽기 | 12.6초 | Bronze가 같은 프로세스에서 이미 읽은 17 MB를 다시 읽음 | Bronze에서 읽은 원천을 같은 job의 Silver에 넘김 | −12초 |
| 정규화 결과 저장 | 13.0초 | 데이터(정규화 결과)를 제어 원장 Mongo에 majority·journal로 씀 | 정규화 결과는 lake(Silver)에 두고 원장에는 키만 | −12초 |
| 게시의 비SQL 시간 | 약 28초 | **미측정.** 후보: lake 읽기·요청 구성, MySQL 연결·트랜잭션·commit, 서비스 행 대조, Mongo 결과·영수증 저장 | 구간별 계측 후 결정 | 미정 |
| MySQL SQL | 15초 | 상품당 SELECT 45·INSERT 25 | B6 일괄 INSERT | −10초 |
| 입력 등록 | 25초 | 이벤트마다 원천·식별·Outbox 기록과 읽기 대조 | 종류별 `insert_many`와 묶음 대조 | −15~20초 |

위 조치를 모두 하면 크롤 완료 → 영수증은 약 30~40초로 추정한다. 5~10초까지 가려면 명령마다 새 프로세스(Python 기동·Mongo 연결)로 나뉜 등록·발행·처리·게시를 한 프로세스로 잇고 Mongo 원장 쓰기를 단계 경계에서만 하도록 줄여야 한다.

### Spark가 B안보다 이득이 되는 규모

B안 122초는 비교 구현의 실측값이다. 중복 조회가 남아 있고 lake가 Garage Delta가 아닌 Master 로컬 파일이라 저장 내구성 조건이 달라, Spark를 뺀 비용의 하한으로 쓰지 않는다.

처리 358초 → 41초의 차이로 측정된 것은 Delta 쓰기 단계(150~200초, 계산 포함), 약 184개 Spark job, Gold(52 job, 60초 대 0.7초)다. 각 job의 고정 비용과 Python↔JVM 직렬화의 몫은 분리하지 않았다. B안 lake는 복제되지 않는 Master 로컬 디스크라는 점은 차이로 남는다.

배치 크기별 측정을 고정 비용과 건당 비용으로 나누면 다음과 같다.

| | 고정 비용 | 건당 비용 | 근거 |
|---|---|---|---|
| Spark 경로 | 약 140초 | 약 2.1초 | 측정: 3건 148초, 100건 354초. 실행기 시간 건당 약 5.5코어초 |
| B안 (현재) | 수 초 | 약 0.4초 | 측정: 100건 41초. 원천 재읽기·정규화 결과 저장이 26초 |
| B안 (남은 비용 정리 후) | 수 초 | 약 0.1초 | 추정: 원천 읽기 65 ms + 계산 20 ms + 쓰기 |

Spark 경로는 고정 비용뿐 아니라 건당 비용도 5배 이상 크다. 후보 원인은 170 KB 행의 Python 경계 직렬화, Kafka 검증 세 번, 단계마다 Delta 재읽기이며, 건당 2.1초 중 각각의 몫은 측정하지 않았다. 3코어 병렬로 이를 메우지 못하므로 **현재 코드로는 어떤 배치 크기에서도 교차점이 없다.**

메모리 한도(추정):

| | 한도 | 이유 |
|---|---|---|
| B안 (현재) | 배치당 약 2,000~3,000건 | 배치 원천을 한 번에 메모리로 읽는다. 170 KB JSON이 Python 객체로 0.5~0.9 MB가 되고, Master 여유는 약 2.6 GB |
| B안 (100건 단위로 나눠 처리하면) | 사실상 없음 | 메모리는 일정, 시간만 건수에 비례 |
| Spark 경로 | 약 3,000~5,000건부터 디스크로 넘침 | 실행기 768 MB × 3에 Kafka 결과·중간 결과 캐시(1,000건 170 MB, 10,000건 1.7 GB) |
| 공통 상한 | 약 3,000건 | 입력 바이트 상한 512 MB, Kafka 보존 2 GB |

Spark를 B1~B3과 세션 하나로 잇는 구조로 고친 뒤라야 교차점이 생긴다. Spark 고정 60초·건당 0.03~0.05초(3코어), B안 고정 10초·건당 0.1초로 가정하면 약 700~1,000건이고, Worker 데몬 6코어면 조금 앞당겨진다. 모두 가정에 기반한 추정이다. 정리 후 B안이면 1,000건 약 2~7분, 원천 전체 65,498건 약 2~7시간으로 추정하며, 현재 Spark 경로는 전체 약 38시간이다.

판단: 주기 배치는 B안을 100건 단위로 나눠 처리하고, Spark는 건당 계산이 무거워질 때(이미지 처리·임베딩), 규칙 변경으로 원천 전체를 재처리할 때, 데이터가 한 대를 넘을 때의 후보로 보류한다. 위 추정은 B안 500건 측정으로 건당 비용의 선형성과 메모리 사용량을 실측해 확인한다.

## 후속 정리 대상

- 실패한 job들(`91444d2d…` 500건, B안 1차)이 대기 슬롯을 차지한다. `batch-recover` 또는 `batch-backlog --rebuild`로 정리한다.
- 측정용으로 게시된 203개 상품은 이미지 연결이 0건이다. 원천 이미지 상태 확인이 필요하다.
- 서버 측정 디렉터리의 오래된 릴리스(`5c86d2ca`, `14e5fa33`, `553f421b`, `4521fb71`)와 첫 배포 `release/`는 정리 대상이다. 삭제 전에 확인한다.
