# 서버 계측 기록과 개선 계획 (2026-10-23)

크롤 완료 유한 배치 경로를 실제 서버(Spark Master·Worker 3대, Garage Delta, Kafka, Mongo, 서비스 MySQL)에서 처음 끝까지 돌린 기록이다. 원본 수치는 [verification/server_batch_20261023.json](verification/server_batch_20261023.json)에 있다. 측정 절차는 운영자 작업 폴더의 `/v2-server-deploy` 스킬이다([서버 이전](server-migration.md) 참고).

## 입력

서비스 DB에 **아직 없는 상품**만 골랐다. 원천 65,498개 상품 중 관측 1건·승인 카테고리 해당이 47,112개, 그중 미게시가 45,197개였다. 이미지 상태가 있는 것부터 순서대로 3개(canary), 100개(두 번째 시도), 다음 100개(세 번째)를 썼다. 같은 상품을 다시 게시하면 기존 행을 갱신하게 되어 "신규 게시 경로"를 잴 수 없기 때문이다. 드라이버는 게시 직전에 입력 상품이 DB에 없는지 확인하고, 하나라도 있으면 쓰지 않는다.

epoch 34(v1)와 같은 상품으로 재지 않았으므로 v1과의 직접 비교는 아니다. v2 Delta 테이블이 비어 있던 점도 다르다.

## Spark 분석

처리 단계 Spark 앱(100건 초기): 실행 354초, 작업(job) 184개, task 446개, 실행기 실제 작업 합계 546초(3코어에 분배). Silver 정제·저장 구간에서만 작업 64개, Gold 52개, Kafka 읽기·검증 39개였다. 작업 수는 AQE가 셔플 단계마다 작업을 나누므로 action 수보다 많다.

- **고정 비용이 지배적이다.** 같은 입력을 다시 돌려 정규화를 재사용하고 서비스 쓰기가 0건이어도 처리 349초, 게시 73초로 거의 같았다.
- **Delta 쓰기 1회가 20~34초.** 100행을 bucket 128개로 분할해 쓰므로 Garage에 작은 파일이 100개 안팎 생기고, 커밋마다 로그 왕복이 붙는다. canary 3행도 22초였으니 커밋당 고정 비용도 크다. 파일 수와 커밋 수 중 무엇이 지배적인지는 아직 분리 측정하지 않았다.
- **게시 89초 중 MySQL은 12초.** Spark 세션 7초를 빼면 약 50초가 Gold 결과(파일 100개 안팎)를 읽어 Driver로 가져오는 시간이다.
- **자원은 놀았다.** Master load 0.4, Worker CPU 약 90% 유휴. 실행기 작업은 3코어에만 분배됐고, 그 시간의 상당 부분도 Garage I/O 대기다.
- 3건 → 100건에서 처리 148초 → 354초, 실행기 작업 72초 → 546초. 상품당 약 2초가 늘고 나머지는 고정 비용이다.

## 확인된 것과 주의할 것

- 신규 상품만 게시, 무변경 재실행은 정규화 재사용과 서비스 쓰기 0건, 감사 통과. 이전 세션이 고친 Mongo 일괄 저장 중복 경로(복합 키)도 실제 Mongo에서 통과했다.
- **이미지 연결이 0건이다.** 103개 상품 모두 `product_images`가 만들어지지 않았다. 원천 이미지 상태가 `AVAILABLE`이 아닌 것으로 보이며 별도 확인이 필요하다. 게시 조건에 이미지가 필수가 아니라 게시는 됐다.
- 무변경 재실행의 게시 결과가 `PUBLISHED`로 표기된다. 저장된 영수증을 돌려주기 때문이며 INSERT 0건으로 쓰기가 없었음이 확인된다. 표기를 `REUSED`로 구분하면 읽기 쉽다.
- v1 epoch 34는 활성화를 빼고 18분 33초였다. 상품·테이블 상태가 다르므로 "2배 이상 빠르다"는 방향만 참고한다.

### 실행 순서

1. **1단계(설정만)**: A1·A2·A3 적용, 500건 측정. 기준: 처리 시간, 코어 사용, 메모리 부족 없음. 이 문서 작성 시점에 진행 중이다.
2. **2단계(코드)**: B1·B2·B3·C1. 새 네임스페이스에서 500건 재측정. 기준: 쓰기당 10초 이하, 작업 수 절반, 무변경 재실행의 쓰기 0 유지.
3. 결과를 보고: B4·B5·C2·D1(1,000건).
4. 필요하면: B6·C3·C4.

1~2단계 후 100건 처리는 150~230초, 게시는 30~50초로 추정한다. Garage 쓰기 비용이 파일 수에 비례하는지 커밋 수에 비례하는지에 따라 폭이 넓다. 임시 경로에 파일 100개와 3개로 같은 100행을 써서 비교하면 5분 안에 가릴 수 있다.

### 1단계 시도 결과 (16:44, 500건)

- **A1은 앱 설정으로 불가능하다.** Spark Worker 데몬이 `SPARK_WORKER_CORES=1`, `SPARK_WORKER_MEMORY=1g`로 떠 있어 실행기당 2코어 요청을 어느 Worker도 받지 못했다. 처리 앱은 16:48:40에 떴지만 실행기가 하나도 등록되지 않고 "Initial job has not accepted any resources"로 20분 대기했다. SIGINT로 중단했고 job `91444d2d…`는 `RECOVERY_REQUIRED`, lease는 반납됐으며 MySQL에는 쓰지 않았다. 두 번째 vCPU를 쓰려면 Worker 데몬 재설정·재시작이 필요한데, 이는 운영 파이프라인과 공유하는 변경이라 별도 승인이 필요하다. 드라이버 기본값은 1코어·총 3코어·분할 6으로 되돌렸다.
- **A3(in-flight 5)은 효과가 없었다.** 500건 85 MB 발행이 126초(0.67 MB/s)로 100건 때(0.63 MB/s)와 같다. 병목은 클라이언트 파이프라이닝이 아니라 브로커 쪽(파티션 1개·복제·TLS)이다. 입력 등록도 98초로 건당 0.2초가 그대로다.
- 위 계획표의 A1·A3는 이 결과로 효과를 낮춰 본다. 자원 활용은 Worker 데몬 변경(A1′)과 Kafka 파티션(C4) 또는 Kafka에 원문 대신 참조만 싣는 변경으로 넘어간다.

### 100건을 초 단위로 처리하려면

데이터 자체의 바닥은 100건(17 MB)에 한 자릿수~십수 초다(이동 1초 미만, 정규화 1초, 객체 저장 2~5초, MySQL 일괄 1~2초). ms 단위는 복제·TLS·내구 저장이 끼는 묶음 처리에서는 불가능하다. 지금 수백 초인 이유는 구조다: 단계마다 Delta 커밋(7회), 작업마다 로그 왕복, 단계 사이 Delta 재읽기, 명령마다 JVM 기동, Kafka 1파티션 0.65 MB/s, 상품별 SQL.

| 구조 | 내용 | 100건 바닥 추정 |
|---|---|---|
| A. Spark·Delta 유지, 재구성 | 세션 하나에서 Bronze→Silver→Gold를 메모리로 이어 계산, Delta 쓰기는 비동기 스레드, 검증 묶기·파일 수 축소·MySQL 일괄·게시까지 같은 세션 | 15~30초 |
| B. 100건 규모는 Python 단일 프로세스 (README §10 비교 후보 B) | Master의 Python이 Kafka 소비 → 정규화 → Gold → parquet/`deltalake` 쓰기 → MySQL 일괄. Spark는 대규모 초기 적재·재계산용으로 유지 | 5~10초 |

둘 다 Kafka 발행 27초/100건은 따로 풀어야 한다. 파티션 확대(C4) 또는 **Kafka에 170 KB 원문 대신 불변 원천 참조만 싣고** 처리 측이 Mongo에서 `$in`으로 묶어 읽는 방식(설계가 허용하는 envelope)이다. 후자는 Worker에 pymongo가 없어 원문을 실었던 현재 선택을 되돌리는 것이며, B안(Master의 Python)에서는 자연스럽다. 배치 안에서는 Bronze 저장을 비동기로 돌려 Silver가 기다리지 않게 하고, 배치 사이에서는 단계별 writer(`BRONZE_COMMITTED → SILVER_COMMITTED → …`)로 파이프라인을 만들면 처리량은 가장 느린 단계 기준이 된다. 이 서버는 Master 메모리상 Spark 앱 2개가 한계다. A/B 선택은 설계 방향("대용량 도구 유지")을 100건 규모에서 바꿀지의 결정이므로 B안 프로토타입을 100건으로 재 본 뒤 정하는 것을 권한다.
