## 판단과 근거

- **고정 비용은 단계 수와 S3 왕복이었다.** 10/23 3건 배치도 148초였고 CPU는 34초뿐이었다. 상품 단위 단일 패스로 Spark job이 로컬 20건 기준 154개→33개가 됐다.
- **이력 읽기는 파일 수와 읽는 범위가 지배했다.** 1MB 미만을 읽는 데 task 47초(작은 파일 약 200개). 100개 상품이 bucket 16개를 거의 다 건드려 bucket으로 걸러도 사실상 전체를 읽었다. 상품 색인으로 처음 보는 상품은 읽지 않게 했다.
- **코어 증설은 지금 효과가 작다.** 실행기 3개(`203656`)도 2개와 같은 시간이었다. 3슬롯이 모두 바쁜 시간 41%, CPU/실행 31%. 인프라 요청은 하지 않는다.
- **동시 제출은 코어가 부족하면 효과가 없다.** 원문 쓰기를 처리와 겹치자 원문 쓰기 task 대기 124.8초, 상품 패스 대기 189.0초(`202619`). 원문은 게시에 필요 없으므로 게시 뒤에 쓴다.

## 현재 한계 (2026-10-26)

같은 코드로도 측정마다 5~10초 흔들리므로 효과는 2회 이상 측정으로 판단한다. 남은 시간의 대부분은 Delta 커밋 1회당 S3 왕복(약 5초, 처리 경로 2회·게시 뒤 1회)과 Kafka 읽기다. 쓰기 겹치기는 3코어 경합으로 한계에 왔다. 더 줄이려면 커밋 횟수 자체를 줄이는 구조 변경(예: 이력과 색인 통합)이나 저장소 응답 개선이 필요하다.
