**VM 네트워크.** Spark Master·Worker, Kafka, Mongo, Garage, MySQL 15대 모두 가상 NIC가 `pcnet32`(링크 10Mbps 에뮬레이션, MTU 1500)다. 단계마다 CPU는 거의 놀고 이동량만 ~10~12MB/s로 묶였다(Kafka 읽기 190MB 18.5초, 원문 S3 쓰기 191MB 15.3초). VMXNET3로 바꾸면 VM 간 처리량이 크게 늘 것으로 보나, VM 재시작과 인터페이스 이름 변경이 따르는 인프라 작업이라 아직 하지 않았다.

**코어 속도.** 같은 Python 작업(약 108KB JSON 300개 해석·직렬화·해시)이 서버 Worker 0.31초, 작업 PC 0.43초. 서버 코어가 느려서 생기는 차이는 없다.

**로컬 비교 실행.** 같은 코드(`SparkBatchProcessor`)·실제 Delta(zstd)·`132203`의 입력 1000건과 정책·`spark_partitions` 6을 Linux 컨테이너(`apache/spark:4.1.3`, CPU 3, 메모리 5GB)에서 돌렸다. 원장은 파일(`FileBatchStore`), 브로커는 메모리(범위를 로컬 JSON으로 JVM에 넘김), 게시는 파일(`FilePublisher`)로 대체했다. Windows에서 직접 돌린 실행은 Python 작업자를 재사용하지 못하고(상품 처리 38.6초) NTFS 작은 파일 쓰기가 느려 기준으로 쓰지 않았다.

**네트워크가 병목이라는 근거.**
- 데이터를 옮기는 단계가 모두 ~10~12MB/s에서 멈추고, 그동안 태스크 CPU는 거의 논다. `125434`의 Kafka 범위 읽기는 190MB에 18.5초였고 태스크 실행 41초 중 CPU는 6초였다. 파티션당 fetch를 1MiB에서 16MiB로 키워도 그대로였다. `130647`의 원문 S3 쓰기는 191MB에 15.3초, CPU 1.5초였다. Kafka 송신, Mongo 원천 저장, 게시용 Gold 수신도 같은 속도대였다.
- 15개 VM의 가상 NIC가 모두 `pcnet32`다. 링크 10Mbps를 에뮬레이션하는 옛 어댑터라 패킷마다 가상화 비용이 크다.
- 서버 코어는 느리지 않다. 같은 Python 작업이 Worker에서 0.31초, 작업 PC에서 0.43초였다.
- 데이터 이동을 거의 없앤 로컬 Linux 실행은 약 93초, 서버는 약 132초였다. 차이는 데이터 이동 단계(Kafka 읽기·검증, Delta 쓰기, Gold 수신, 마무리)에 몰려 있다.
- 같은 코드라도 서버 측정이 회차마다 크게 흔들린다. A/B 4회 동안 원천 Mongo 저장이 63~91초, Kafka 읽기·검증이 26~47초였다. 이동 대역폭이 공유 인프라 상태에 따라 달라지기 때문으로 보며, 이 때문에 5초 안팎의 코드 개선은 서버에서 확인할 수 없다.
- 해결책은 VM NIC를 VMXNET3로 바꾸는 것이다. VM 재시작과 인터페이스 이름 변경이 따르는 인프라 작업이라 하지 않았고, 근거만 남긴다.

**결론.** 데이터 이동을 없애도 1000건은 약 93초다. NIC 개선으로 기대할 수 있는 몫은 게시 완료까지 30~40초(실제 Mongo·MySQL 왕복 개선분은 더해질 수 있음)와 다음 배치를 늦추는 마무리 약 12초다. 남는 시간은 CPU에 묶인 Python 처리(이벤트당 ~190KB JSON resolve, 상품별 Gold 계산, 게시 행 생성)라, 10초대가 목표라면 Python 처리를 JVM으로 옮기거나 이벤트에서 쓰지 않는 필드를 줄이거나 코어를 늘려야 한다.

## Executor Python CPU 줄이기 (2026-10-26)

**방법.** `spark.python.profile`과 cProfile로 실제 1000건의 resolve·상품 처리를 함수별로 쟀다. Python CPU의 절반이 같은 ~190KB 원문을 정렬 직렬화(`canonical`)하고 해시(`digest`)하는 데 쓰였다. 출력이 한 바이트라도 바뀌면 저장된 해시와 어긋나므로, resolve와 상품 처리의 전체 출력(513MB)이 바꾸기 전과 바이트 단위로 같은 변경만 받는다.

**반영 (`b8424ee`).** 같은 원문을 반복 검증·직렬화하던 부분만 없앴다.
- 상품 처리에서 resolve가 이미 통과시킨 원문의 `validate_raw`를 생략했다.
- resolve는 intake가 확인한 `document_hash` 재확인을 생략했다(`payload_hash` 일치 뒤에만).
- raw·갤러리 해시는 한 번만 계산한다.
- 저장된 raw 텍스트의 해시로 바로 검증한다.
- v1이 쓰는 기본값은 그대로다.

같은 PC의 Python 처리 시간은 132→94.6초(−28%), 컨테이너 상품 처리는 11.8→8.9초다.

**넣지 않음: orjson.** 실제 1000건의 `canonical` 호출 502,521번이 모두 같은 바이트였고, Python 처리 시간은 94.6→74.8초였다. 그래도 넣지 않는다.
- 실수 표기가 다르다. 표준 json은 `1e-07`, orjson은 `1e-7`이나 `0.0000314159`로 쓴다.
- NaN을 표준 json은 거부하지만 orjson은 `null`로 받아들인다.
- 두 차이 모두 출력만 보고 걸러낼 수 없다.
- 지금 원천에는 실수가 없지만, 들어오는 순간 서버마다 해시가 달라지거나 값이 바뀐다.
- 넣으려면 모든 호스트(v1 적재 포함)에 orjson을 설치하고, 원천을 다시 적재하고, intake에서 NaN을 엄격히 거부해야 한다.

## 판단과 근거

- **고정 비용은 단계 수와 S3 왕복이었다.** 10/23 3건 배치도 148초였고 CPU는 34초뿐이었다. 상품 단위 단일 패스로 Spark job이 로컬 20건 기준 154개→33개가 됐다.
