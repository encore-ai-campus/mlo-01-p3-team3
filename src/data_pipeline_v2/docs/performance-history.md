# v2 유한 배치 성능 개선 이력 (2026-10-23 ~ 10-26)

크롤 완료 유한 배치(NiFi → Kafka → Spark → Delta → MySQL 게시)의 시간을 줄이려고 바꾼 내용을 한곳에 모은 문서다. 측정마다의 원자료는 [10/23 기록](server-measurement-20261023.md)과 [10/25~26 기록](server-measurement-20261025.md)에 있고, 이 문서는 그 기록에서 **무엇을 바꿨고 효과가 얼마였는지**만 추려 정리한다. 방침은 `AGENTS.md`의 "v2 유한 배치 성능 개선 방침"이다(Kafka·Spark 주 경로 유지, 설계 변경 허용, 결과 동등성·무결성·복구 위험은 계속 지적).

## 요약

| 기준 | 처음 | 마지막 | 비고 |
|---|---:|---:|---|
| 100건, 크롤 완료→게시 | 495초 (10/23 `160736`) | 약 40초 (`021811`) | 약 1/12 |
| 100건, 상주 처리기 둘째 배치 처리 | 358.4초 | 19.9초 (`102705`) | |
| 1000건, 크롤 완료→게시 | 약 246초 (`105122`) | 약 132초 (`132203`) | 같은 코드도 측정마다 ±15초 이상 흔들림 |

- **남은 병목은 네트워크다.** 15개 VM의 가상 NIC가 `pcnet32`라 데이터 이동이 ~10~12MB/s에 묶이고, 그 속도가 측정마다 흔들린다. 데이터 이동을 거의 없앤 로컬 Linux 실행은 1000건 약 93초였다. 근거는 [측정 기록의 네트워크 절](server-measurement-20261025.md#네트워크와-로컬-비교-2026-10-26-1000건)에 있다.
- **그다음은 Executor의 Python CPU다.** 원문 JSON 해석·직렬화·해시와 레거시 Silver 정규화가 대부분이다. 저장된 해시와 바이트가 같아야 해서, 출력을 바꾸지 않는 범위에서만 줄였다.

## 남은 과제

1. **VM NIC를 VMXNET3로 전환.** 인프라 작업이라 하지 않았다. 30~40초는 검증하지 않은 기대치이며, 측정 편차도 함께 줄 것으로 본다.
2. **Executor 코어·병렬도 실험.** 코어 3개 대 6개를 비교한다. 큰 상품은 한 태스크에 몰리므로 코어에 비례하지 않는다. `SPARK_WORKER_CORES`·`cores.max`·`spark_partitions`와 프로세스 메모리(JVM heap + Python RSS)를 함께 봐야 한다.
3. **상품 처리 단일 패스의 JVM 부분 이식.** Scala `mapPartitions`로 옮긴다. 정렬 압축 JSON, 원천 해시용(공백 포함), Gold용(키 비정렬) 세 직렬화 계약과 바이트 동등성 시험 장치가 먼저다.
4. **운영 확인 필요.** MySQL03 복제가 10/24부터 멈춰 있다([측정 기록의 서버 상태 변경](server-measurement-20261025.md#서버-상태-변경)).

## 측정 방법과 도구

- **배포·측정:** `.agents/skills/v2-server-deploy/scripts/deploy.sh`
  - `build` → `push` → `install` → `pick-keys N 이름` → `push-driver` → `start publish once serve`
  - 측정 대상은 검증용 DB `pj3_products_validation`에 게시하고, 서비스 DB는 쓰지 않는다.
- **분석:**
  - `report [stamp]`: 명령별 시간과 단계 span
  - `timeline`: Spark job 순서. 바꾼 쓰기가 의도한 위치에서 도는지 측정마다 확인한다
  - `resources`: 메모리·캐시·spill
- **A/B:** `use-release <해시>`로 이전 릴리스와 번갈아 돌린다. 이전 릴리스는 `start ... noprecompact`로 측정 전 압축을 건너뛴다. 새 상품이 4000개 이상 남아 있는지 먼저 확인한다.
- **초기화:** `reset-measurement plan|apply`로 측정용 MySQL(TRUNCATE), Mongo `pipeline_v2_*`, v2 레이크, 오래된 결과를 지운다. 새 상품이 부족해지거나 Master 디스크가 찰 때 쓴다.
- **로컬 비교:** 서버와 같은 코드·입력을 Linux 컨테이너(`apache/spark:4.1.3`, CPU 3)에서 돌린다. Windows 직접 실행은 Python 작업자를 재사용하지 못해 기준으로 쓰지 않는다.
- **출력 동등성:** CPU 최적화는 실제 1000건의 resolve·상품 처리 출력 전체를 바꾸기 전과 바이트 단위로 비교해 같을 때만 반영한다.
