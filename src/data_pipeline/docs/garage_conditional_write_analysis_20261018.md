# 조건부 PUT 실패 원인 분석 — 2026-10-18

## 결론

설치된 Garage v2.4.1의 S3 PUT 처리 구현은 현재 파이프라인이 기대하는 `If-None-Match: *` 기반 기존 객체 보호를 제공하지 않는다. 실행 중인 바이너리 버전, 공식 v2.4.1 소스, 조건부 헤더가 포함된 실제 요청의 덮어쓰기 결과가 일치한다. 일반 PUT 성공이나 S3 호환 표시는 이 기능의 보장을 뜻하지 않는다.

## 확인 근거

1. Object01 바이너리 `/opt/pj3/garage/2.4.1/garage --version`은 `garage v2.4.1`이다.
2. NiFi boto3 1.40.72에서 `before-send.s3.PutObject` 이벤트로 인증 헤더를 제외하고 해당 조건 헤더만 확인했다. 실제 전송 직전에 `If-None-Match: *`가 존재했다. SDK가 인자를 누락한 경우가 아니다.
3. 조건부 요청에 HTTP 200이 반환됐고, 이후 두 HTTPS endpoint에서 다른 본문이 관측됐다. 응답 코드만 확인한 추정이 아니다. [추가 진단 JSON](verification/garage_20261018/nifi-header-diagnosis.json).
4. Object01의 실제 `/etc/pj3/garage/Caddyfile`은 TLS 종료 후 `reverse_proxy 127.0.0.1:3900`만 지정한다. 조건부 헤더를 제거/변경하는 설정은 없다. 배포 모듈의 설정 템플릿도 일치한다. 프록시에서 패킷을 수집하거나 backend loopback으로 직접 PUT을 한 것은 아니므로 헤더 전달 전 구간을 캡처한 결과라고 표현하지 않는다.
5. 공식 v2.4.1의 [PUT 구현](https://github.com/deuxfleurs-org/garage/blob/v2.4.1/src/api/s3/put.rs)은 handle_put에서 조건부 헤더를 판정하지 않고 save_stream으로 저장한다. save_stream은 기존 객체를 읽어 새 버전 시각을 계산하고 저장하며, 존재 여부를 이유로 해당 PUT을 거절하는 분기가 없다. [S3 라우팅](https://github.com/deuxfleurs-org/garage/blob/v2.4.1/src/api/s3/api_server.rs)은 PutObject를 해당 handle_put으로 전달한다.
6. 같은 버전의 [GET/HEAD 구현](https://github.com/deuxfleurs-org/garage/blob/v2.4.1/src/api/s3/get.rs)에는 별도의 조건부 조회 처리가 있다. 조회의 If-None-Match 지원을 업로드의 조건부 쓰기 지원으로 해석하면 안 된다.

따라서 현재 가장 직접적인 원인은 backend PUT의 조건 검사 부재다. 프록시 헤더 설정만 추가해도 backend에 없는 원자적 저장 조건이 구현되지는 않는다. 이번 분석은 해당 버전·경로에 대한 것이며 이후 Garage 버전의 기능을 판정한 것은 아니다.

## 현재 코드에 미치는 영향

S3Objects.ensure는 GET/SHA256 확인 → 없으면 조건부 PUT → 다시 GET/SHA256 확인 순서다. 순차적으로 이미 저장된 같은 바이트를 전달하면 GET에서 재사용하므로 정상 동작한다. 하지만 GET과 PUT은 하나의 원자적 연산이 아니다. 둘 사이에 다른 작성자가 같은 키를 저장하면 현재 저장소는 후속 PUT을 허용할 수 있다. 업로드 후 검사는 이미 발생한 덮어쓰기를 되돌리는 수단이 아니다.

실제 이미지 키와 인계 청크는 SHA256 기반이다. 정상 코드가 서로 다른 바이트에 서로 다른 키를 배정하므로 평상시 충돌 가능성은 줄어든다. 그렇더라도 키를 강제로 재사용한 쓰기, 외부 작성자, 오류 상황에서도 불변성을 보장한다는 요구를 충족하지는 않는다. 이번 충돌 시험은 이 보호 능력을 확인하기 위해 다른 바이트를 같은 전용 키에 쓴 것이다. 운영 이미지가 이미 손상됐다는 증거는 아니다.

Delta의 로그 커밋 안전성은 별도 문제다. 이 실패만으로 모든 Delta 실행이 불가능하다고 단정하지 않으며, 사용할 LogStore/동시 작성자 조정 방식과 장애 시 커밋 보장을 따로 검증해야 한다. 일반 S3A 파일 입출력만으로 Delta를 인수할 수는 없다.

## 해결 방향

- 원래 계약을 유지하려면 원자적 조건부 쓰기를 실제로 보장하는 저장소 버전/구성을 확인하고 동일 충돌 시험을 통과시킨다. 근거 없이 버전만 올리거나 기존 클러스터를 재설치하지 않는다.
- Garage를 유지하면서 애플리케이션에서 조정하려면 모든 작성자에 대한 키별 소유권·fencing·불변 이름·원장 및 장애 복구 계약을 다시 설계해야 한다. 단순 GET/HEAD 추가나 시간차 재시도, 일반 프록시의 HEAD 후 PUT은 원자적 보장을 제공하지 않는다. 외부 작성자가 우회할 수 있는 계정/권한 범위도 고려해야 한다.
- 이미지/인계 객체와 Delta 커밋을 분리해서 판단한다. Delta는 지원되는 LogStore/조정 방식 또는 별도 검증된 저장소를 선택해야 한다. MongoDB lease 하나를 추가하는 것만으로 모든 Spark writer와 외부 쓰기를 자동 보호한다고 가정하지 않는다.

이번 작업은 원인 분석과 전용 객체 진단만 수행했다. 추가 NiFi 시험 객체도 삭제 후 HEAD 404를 확인했다. 저장소·프록시·파이프라인 업무 코드·권한·클러스터 설정은 변경하지 않았다.
