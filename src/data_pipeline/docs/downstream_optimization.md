# Silver·Gold·활성화 처리 비용 개선

## 적용 범위

2026-10-21 실제 운영 데이터 100개 배치 측정 후 개선했다. 수집기·원천 ID·평가 ID 생성 규칙·승인 판단·MySQL 스키마는 변경하지 않는다.

| 항목 | 적용 내용 | 유지하는 확인 |
|---|---|---|
| 활성화 반복 처리 | 동일 입력의 정규화 재사용에 더해 동일 고정 버전의 출력 검증을 Driver 내에서 재사용한다. 최초 게시 완료와 실제 상품 존재를 확인하면 활성화 때 검수 대기 적재를 반복하지 않는다. | 이미지 상태를 다시 읽고 변경을 확인한다. 승인 게시의 guard·트랜잭션·실제 저장 확인은 수행한다. |
| 출력 검증 | 경로·Delta table ID·고정 버전·행 키·record_hash가 일치하는 성공 증거만 실행 중에 재사용한다. 요청 중 이미 검증한 행을 제외하고 나머지를 검증한다. | 새 버전·다른 table ID·재시작 시 재검증한다. 누락 행은 캐시하지 않으며 실패한 묶음의 일부 증거도 승격하지 않는다. |
| 테이블 준비 | Bronze에서 검증한 DeltaLog의 최신 snapshot 메타데이터 조회를 Silver·Gold에도 적용한다. | 스키마·appendOnly·targetFingerprint를 검증한다. 조회 실패를 테이블 부재로 취급하지 않는다. |
| 검증 쿼리 | 임시 DISK_ONLY 캐시 생성·집계·collect 대신 용량 제한을 적용한 JSON 행 iterator를 사용한다. Gold 입력·게시 출력에도 적용한다. | 개별 초과 payload는 Python에 전달하지 않는다. 전체 행·바이트 한도를 넘으면 부분 결과를 사용하지 않는다. iterator를 모두 소비하고 검증한 뒤에만 결과를 반환한다. |
| 원격 입력 보존 | 최대 100개 입력을 약 8MiB 단위의 불변 bundle로 묶는다. 전체 bundle 저장 후 다시 읽어 확인한 뒤 개별 참조를 공개한다. | 각 입력의 SHA-256을 보존하고 bundle과 항목을 모두 검사한다. 기존 개별 파일 참조는 계속 지원하며 삭제·이관하지 않는다. |
| Delta 커밋 | 기존 행의 키·본문 충돌을 먼저 검사하고 실제 누락 행이 있는 테이블만 append한다. 변경 없는 테이블은 건너뛴 수를 계측한다. | 테이블별 저장 확인 후 완료 영수증을 기록한다. 부분 커밋은 다음 시도에서 실제 저장분을 다시 대조한다. 여러 테이블을 하나의 트랜잭션이라고 취급하지 않는다. |

## 묶음 입력 보존 계약

기존 참조: `<checkpoint>/inputs/<입력 SHA-256>.json`

새 묶음 참조: `<checkpoint>/inputs/<bundle SHA-256>.json#sha256=<입력 SHA-256>`

묶음 본문은 `contract_version=1`, `kind=PIPELINE_INPUT_BUNDLE`, `entries={입력 SHA-256: 입력 원문}`이다. `Checkpoint.read_input(reference)`는 두 형식을 모두 읽는다. 참조 경로·파일 해시·항목 해시가 다르면 실패한다. 파일 참조의 fragment는 원격 파일명에 포함되지 않는다.

묶음 참조는 Silver 평가 영수증의 `input_snapshot_refs_json.image_state_ref`와 정규화 입력 검증 로그의 `archive_ref`에 기록한다. Gold export 자체의 기존 개별 파일 참조는 유지한다. 한 입력이 묶음 목표 크기를 넘으면 기존 개별 보존 경로를 사용한다. 재시작 후에는 보존 파일을 다시 읽어 확인한다.

## 남겨 둔 처리

Gold는 Silver 버전·상품 상태·가격 유효 기간·검수 입력을 함께 판정한다. Silver 정규화를 생략했다는 이유만으로 Gold·승인 게시를 생략하지 않는다. 서로 다른 Delta 버전의 저장 증거도 같은 증거로 취급하지 않는다.

테이블별 append는 기존에도 신규 행만 대상으로 했다. 이번 변경은 불필요한 호출을 명시적으로 제외하고 계측하는 것이며, 필요한 8개 테이블의 커밋을 무조건 1개로 줄였다는 의미는 아니다.

## 간소화한 검증 절차

1. 로컬: 변경 부분 및 Silver·Gold·활성화·중복·복구 관련 핵심 테스트 93개 통과.
2. 서버: Driver·Worker 유휴 상태 확인 후 백업을 남기며 배포. 배포 런타임의 관련 테스트 90개 통과. 실제 100개 배치를 업무 DB·활성화까지 1회 실행해 측정한다.
3. 결과 확인: 오류·누락·중복·단계별 시간과 실제 업무 DB 건수를 확인한 뒤 연속 처리를 재개한다.

서버 테스트와 실제 운영 배치 시험은 구분한다. 대역 테스트 통과만으로 실서버 처리 완료를 선언하지 않는다.

### 실데이터 시험 중 발견한 입력 경계

epoch 7의 첫 시도는 `danawa_products.images=null`인 관측을 기존 대조기가 배열로 순회해 `TypeError`로 중단됐다. 이 시점에 새 묶음 보존은 아직 시작되지 않았고 업무 DB 건수는 변하지 않았다. 실패 기록을 `downstream-optimization-failed-null-gallery.json`으로 보존했다.

원천 `image_refs`도 비어 있을 때만 null을 빈 갤러리로 대조하도록 보완했다. 정규화 원문과 해시는 수정하지 않는다. 원천 갤러리가 있는데 정규화 갤러리가 비면 기존처럼 불일치로 차단하며, 배열이 아닌 잘못된 형식은 `CATALOG_GALLERY_INVALID`로 명시한다. 로컬·서버 각각 관련 테스트 6개 및 실패한 동일 100개 입력의 쓰기 없는 대조·묶음 구성 검증을 통과했다. 15:42:18 KST에 성공한 Bronze·선정 결과를 보존하고 Silver부터 재개했다.

동일 100개 관측을 읽어 확인한 결과, 99개는 갤러리 URL이 있었고 `20577071` 하나만 `images=null`·원천 갤러리 0개·`detail_status=request_failed`였다. 목록 썸네일은 있었다. 이 사례는 파일의 객체 저장소 적재 지연이 아니라 상세 요청 실패에 따른 갤러리 URL 부재다. 썸네일을 갤러리로 대체하거나 URL이 확보됐다고 기록하지 않는다. 원천 재수집은 수집기 담당이며, 새 확정 관측이 도착하면 기존 원천을 수정하지 않고 다시 처리한다.

## 갤러리 URL 대기 이력

시험 완료 후 기록 기능을 추가하고 관련 로컬·서버 테스트 각각 2개 및 같은 100관측의 실제 기록 경로를 확인했다. 이 작은 기록 기능은 위 성능 측정 뒤 추가된 것이므로 성능 시험 당시 코드와 구분해 검증 JSON에 해시를 남겼다.

갤러리 URL이 없는 관측은 Silver 실행 상태 디렉터리의 `input-waits/gallery-url/<observation_key>.json`에 불변 대기 이력을 남긴다. `SOURCE_DETAIL_REQUEST_FAILED`와 `SOURCE_GALLERY_URL_MISSING`을 구분하고 원천 ID·관측 키·정규화 해시·상품 URL·후속 수집 조치를 연결한다. URL은 있으나 파일 적재가 끝나지 않은 경우는 이 목록에 넣지 않으며 기존 이미지 상태 원장에서 관리한다. 원천이나 승인 상태를 바꾸지 않는다.

이번에는 `danawa:20577071` 1개가 해당됐다. 업무 DB의 실제 상태는 `ACTIVE`, `recommendation_ready=0`이다. 현재 계약은 상품 카탈로그 활성화와 이미지·추천 준비를 별도로 판단한다. 이 대기 이력을 상품 비활성화나 자동 수집 재시도로 설명하지 않는다. 새 확정 원천이 들어와도 과거 대기 이력을 덮어쓰지 않는다.

## 남은 개선 후보 — 논의 후 진행

1. 활성화 Silver의 기존 행 대조 60,816ms, 증거 검증 53,874ms를 줄이기 위해 영수증·출력 조회의 중복과 Spark 작업 수를 확인한다.
2. 스트리밍 조회는 임시 캐시를 제거했으나 일부 조회 시간은 직전보다 늘었다. 실행 작업·파티션 수를 비교해 기존 집계 후 수집 방식과 선택적으로 비교할 필요가 있다.
3. 활성화 Gold는 308,777ms다. 변경된 관측뿐 아니라 상품 상태·정책·승인·시간 경계를 포함해 재평가 영향 범위를 계산해야 하며, 정규화 생략 건수만으로 범위를 줄이지 않는다.
4. 활성화 게시의 Gold 읽기 56,141ms와 MySQL 승인 게시 55,589ms가 남아 있다. 고정 출력 읽기와 원장 사전 조회를 재사용하되 트랜잭션 내 guard 재검증은 유지한다.

위 목록은 epoch 7 완료 당시의 분석이다. 이후 구현·실행 상태는 다음 절을 기준으로 확인한다.

## Silver·Gold 조회 재사용 추가 개선 — 2026-10-21

1. Silver·Gold의 한 번의 `process_many` 안에서 같은 테이블·버전·키의 영수증 사전 조회를 재사용한다. 부재 확인도 해당 호출 범위에만 보존하며, 저장 시 해당 테이블의 조회를 무효화한다. 예외·호출 종료 시 캐시를 비운다.
2. Gold가 검증한 전체 Silver 입력을 같은 Driver 안에 보존한다. 이후 Silver 버전이 바뀌면, 자기 쓰기의 고유 transaction metadata·연속 버전·실제 저장 행의 해시 확인을 모두 통과한 append만 합쳐 재사용한다. 모르는 쓰기·테이블 교체·버전 역행·캐시 유실은 기존 전체 읽기로 돌아간다. 평가 ID·시간 조건·승인 판정·완료 영수증 순서는 유지한다.
3. 제한된 읽기의 스트리밍 방식과 집계 후 수집 방식을 실제 클러스터의 동일 고정 데이터로 ABBA 비교했다. 1,828행의 결과 해시는 모두 같았고, 두 회 합계는 스트리밍 47,346ms, 집계 42,589ms였다. 기본은 집계 방식이며, 행·바이트 제한을 통과하기 전에 전체 본문을 수집하지 않는다. 이 비교는 읽기 전용 시험으로 배치 전체 개선율을 뜻하지 않는다.

로컬 핵심 테스트 111개, 배포 서버의 관련 테스트 108개가 통과했다. 배포 파일 11개의 SHA-256을 대조했다. 서버 테스트에 없는 로컬 시험을 서버에서도 실행했다고 계산하지 않는다.

사용자의 연속 실행 요청에 따라 19:08:27 KST부터 **첫 실제 시도부터 연속 처리**를 시작했다. 기존 정지 설정은 서버의 `perf-20261020/layer-reuse-released-pause.json`에 보존한 뒤 해제했다. 100건 단위로 게시·활성화까지 완료한 후 다음 배치로 진행하며, 일부 단계 실패 시 기존 복구 규칙이 적용된다. 시험 1회 뒤 멈추는 설정이 아니다.

실행 직전 업무 DB는 상품 646건·ACTIVE 580건·PENDING_REVIEW 66건이었다. Worker 02(`192.168.0.123`)는 Master에서 DEAD, SSH는 `No route to host`로 확인됐다. 기존 Driver·활성 Spark 작업이 없고 나머지 두 Worker가 유휴 상태임을 확인하고 기존 Master로 실행했다. 클러스터 멤버 설정·원장 잠금·체크포인트를 강제 변경하지 않았다. 이 자원 조건을 이전 3개 Worker 배치와의 시간 비교에 반영해야 한다.

첫 배치의 실제 완료 시간·오류·후속 배치 결과는 별도 실행 증거로 확인한다. 위 테스트 통과와 실행 시작을 업무 DB 반영 완료로 해석하지 않는다.

## 17분대 목표의 후속 변경 — 실행 검증 중

첫 연속 100건 배치는 19:08:27→19:33:32 KST, 전체 경과 25분 5초에 완료됐다. 상품 +100·ACTIVE +88이며 업무 DB는 746상품·668 ACTIVE·78 대기였다. 다음 epoch 9는 Gold에서 Mongo 잠금 갱신 취소로 중단됐다. [제한된 자동 복구](automatic_recovery.md)를 추가하고 기존 장애를 감사 후 복구해 20:23:53 KST부터 Gold를 재개했다. 이 재개 소요 시간을 전체 100건의 처리 시간으로 비교하지 않는다.

추가한 최적화:

- `delta_key_index.py`: 전체 고정 버전의 키를 제한된 범위에서 읽어 Driver 수명의 Bloom 부재 필터를 만든다. 없는 키의 저장 전 재조회를 생략하고, 있을 가능성이 있는 키는 기존 원문·해시 대조를 수행한다. 일부만 읽었거나 예산을 넘으면 인덱스를 공개하지 않고 기존 경로로 돌아간다. 필터 양성은 저장 증거가 아니다.
- 검증한 자기 append만 인덱스를 다음 버전으로 갱신한다. table ID·연속 버전·고유 transaction metadata·실제 저장 행 확인이 모두 필요하다. Gold에도 소유 append 식별을 적용했다. 알 수 없는 버전이나 Driver 재시작에서는 조회를 다시 수행한다.
- 같은 조건의 append에서는 이전 고정 버전에서 확인한 행의 해시 증거도 새 버전에 전달한다. 기존 키의 상충 해시는 거절하며 신규 append 행의 실제 저장 확인을 생략하지 않는다.
- 부재 필터는 SHA-256을 확인하는 임시 디스크 캐시에 두어 큰 입력 캐시와 메모리에서 경쟁하지 않게 했다. 영속 원장이나 환경 이전 증거로 사용하지 않는다.

새 Gold 복구 시도는 352,831ms였다. 이 안에는 Spark 시작 49,356ms, 첫 키 인덱스 구성 54,563ms, Silver 고정 입력 읽기 71,531ms가 포함된다. 51,739개 키를 색인해 부재 키 대조 3,127개를 생략했고 자기 append 8개를 반영했다. 초기 구축 비용을 포함한 복구 배치와 캐시가 유지되는 다음 전체 배치를 구분해야 한다. 아직 17분대 달성을 선언하지 않는다.

캐시 누락·포화에 따른 false positive·500,000키/64MiB 조회 상한은 속도 효과를 제한할 수 있다. 이런 경우 원래 조회를 수행하며 임의로 데이터를 생략하지 않는다. 배치 규모·실제 노드 수·원천 구성·파일 누적이 다른 시험 간 시간 차이 전체를 코드 효과로 계산하지 않는다.
# 2026-10-22 배치 간 키 인덱스 재사용

OOM 방지용 epoch별 JVM 교체는 유지한다. 새 `PIPELINE_DELTA_KEY_INDEX_DIR`는 Driver의 보호된 로컬 derivative 캐시이며 원천·체크포인트를 대체하지 않는다. 동일 경로·Delta table ID·정확한 버전·형식·전체 체크섬·파일 소유자/권한이 일치한 완전한 Bloom 인덱스만 다음 JVM에서 읽는다. 훼손·유실·재생성·버전 차이는 cache miss로 처리하고 원래 저장소 조회로 돌아간다. 정확한 값의 내용 검증과 실제 저장 확인은 생략하지 않는다.

새 인덱스는 전체 키 읽기·예산·lease 확인이 모두 끝난 뒤에만 저장한다. 자기 append의 실제 저장 증거가 확인된 경우에만 인접 버전으로 전진한다. 경로/table ID별 최신 두 버전만 남긴다. 각 인덱스는 고정 128KiB bitset이며 양성은 단지 기존 행 후보이므로 본문·해시 검사를 계속한다. 캐시 초기 생성에는 기존 50만 키/64MiB 제한이 적용되고 초과 시 정상 조회로 돌아간다. 환경 이전 시 이 캐시는 생략할 수 있으며 성능에만 영향이 있다.

이번 유지보수는 기존 100건 배치를 보존하고 정리 후 정지 상태를 유지한다. 200건 논리 배치·50~100건 메모리 처리 묶음은 별도 설계·검증 대상이다. 새로운 전체 배치 시간 단축은 실제 재개 시험 전까지 확정하지 않는다.
