- 사용자 요청으로 조정기와 정확히 식별한 하위 JVM을 종료했다. JVM은 SIGTERM 후 12초간 종료되지 않아 해당 PID만 강제 종료했다. 전체 Worker 유휴 확인 후 만료 잠금 5개를 감사 절차로 해제했으며 체크포인트·원천·완료 결과를 보존했다.
- Bronze 쓰기는 큰 JSON `lit()` 대신 로컬 JSONL을 공유 저장소의 시도별 `_pipeline_inputs/<UUID>.json`로 전송하고 명시 스키마의 JVM JSON reader로 읽는다. 성공 쓰기·소유권 확인 후 자기 임시 객체만 삭제한다. 불확실한 쓰기의 입력은 진단용으로 남으며 재실행은 기존 행 검증 후 이어간다.
- 세션은 한 epoch의 Bronze→활성화 동안만 재사용한다. 완료 상태를 보존하고 Spark 정지·기존 gateway 종료를 확인한 뒤 조정기를 exec하여 다음 epoch를 새 JVM으로 시작한다. 종료 미확인 시 교체하지 않는다. Spark 실행 이력 보유 수를 제한하고 Driver에 `ExitOnOutOfMemoryError`를 적용한다. 힙은 768MB를 유지했다.
- 비정상 종료된 소유 gateway 프로세스가 실제 관측된 경우에만 `SPARK_DRIVER_JVM_EXITED`로 전달한다. PID·소유권·만료·전체 Spark 유휴가 확인돼야 기존 제한 자동 복구가 가능하다. 단순 RPC 타임아웃을 JVM 종료로 간주하지 않는다.
- 로컬 113개 및 서버 113개 회귀 시험 통과. 00:20:08 KST epoch 13부터 연속 처리를 재개했다. 배포 후 전체 배치 완료·다음 JVM 교체의 실제 운영 확인은 후속 기록으로 구분한다. Git 커밋·푸시는 수행하지 않았다.

### Garage 업로드 실제 시험 후 보완

첫 운영 시도에서 S3A `copyFromLocalFile`이 `AWSS3IOException`으로 실패했다. 재시도 중인 작업을 다시 종료하고 Garage에서는 기존 `garage_v241` SDK 프로필로 시도별 임시 객체를 업로드하도록 변경했다. SDK는 제한된 timeout·1회 전송 정책을 사용한다. Garage의 HEAD 응답에서 사용자 `sha256` 메타데이터를 확인할 수 없었으므로, 실제 GET 바이트를 64KiB씩 읽어 크기·SHA-256을 대조한 후 Spark reader에 경로를 넘긴다. 확인되지 않은 특정 S3A 내부 실패 원인을 확정한 것으로 표현하지 않는다.

격리 객체의 실제 업로드·GET 동일 바이트·삭제를 확인했고 최종 로컬·서버 회귀 시험은 각각 114개 통과했다. 최종 배포 후 00:29:55 KST에 epoch 13부터 다시 연속 처리를 재개했다. 체크포인트·원천·성공 결과를 보존했다. 공개 근거는 [OOM 보완 검증](verification/driver_oom_repair_20261022.json)이며, 운영 배치 완료·다음 epoch JVM 교체 확인은 별도다.
