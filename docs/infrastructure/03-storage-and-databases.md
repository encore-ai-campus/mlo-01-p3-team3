# 데이터 디스크·복제·Object Storage

[문서 목록](README.md) · 근거: [E07](07-evidence-and-handoff.md#e07), [E08](07-evidence-and-handoff.md#e08)

## 데이터 디스크 8대

| 논리 대상 | 수량 | 추가 가상 용량/대 | 실제 데이터 경로 |
|---|---:|---:|---|
| MySQL | 3 | 50 GiB | /var/lib/mysql |
| MongoDB | 3 | 50 GiB | /var/lib/mongodb |
| Object Storage | 2 | 100 GiB | 전용 객체 데이터 마운트 |

2026-10-18 작업 기록에서 8대의 GPT·ext4·UUID 기반 영구 마운트와 읽기·쓰기 검증을 확인했다. 장치 이름·용량만으로 대상을 정하지 않고 OS 디스크 계보, 모델·식별자·연결 경로, 파티션·서명·사용 흔적을 함께 확인했다.

기존 데이터가 없는 것으로 확정된 추가 디스크만 포맷했다. 공개 문서에는 실제 UUID·장치별 매핑·호스트 주소를 싣지 않으며 보호된 서버별 결과가 운영 원본이다.

## DB 이전과 보호

6대 DB는 기존 데이터 경로를 유지했다. 승인된 정상 종료 후 데이터 전체를 복사하고 소유권·권한·확장 속성·하드링크 및 해시를 대조했다. 독립 복구 엔진 기동을 통한 복구 점검과 MySQL 이전 전후 논리 덤프 비교를 기록했다. 기존 원본을 즉시 삭제하지 않았다.

서비스 의존성과 마운트 가드로 올바른 데이터 UUID가 없으면 DB가 루트 디스크에 쓰지 않도록 했다. 재마운트·누락 조건 검증을 수행했지만 실제 VM 재부팅 시험은 수행하지 않았다.

보존 원본과 검증용 복구본이 같은 VM·호스트에 있으므로 독립 재해복구 백업으로 간주하지 않는다. 운영 이전에는 별도 보호 저장소·복원 절차가 필요하다.

## MySQL GTID 복제

MySQL Server 8.4.11의 Primary 1대·Replica 2대에 고유 server_id, binary log, GTID, TLS 복제와 최소 권한 복제 계정을 구성했다. Replica 읽기 전용 상태를 확인했다.

기록된 검증 시점에 두 Replica의 IO·SQL thread가 정상이고 지연은 0초였다. 별도 시험 데이터 2개가 GTID 대기 후 양쪽에 복제됐다. 지연 0초는 해당 시점 값이며 지속적인 서비스 수준 보장은 아니다.

기존 Replica 측 시험 DB·독립 GTID는 보존했다. 향후 승격·장애조치 설계에서는 이 차이를 검토해야 한다. 자동 장애조치·기존 데이터 덮어쓰기·무단 재초기화는 포함하지 않는다.

## MongoDB 기존 Replica Set

MongoDB 9.0.4와 기존 3노드 Replica Set을 유지했다. TLS hello로 Primary 1·Secondary 2를 관측했고 기존 데이터·인증·설정을 보존했다. 복제를 새로 구축하거나 rs.initiate를 반복 실행한 것으로 기록하지 않는다.

인프라 인증 검증 실행에서는 승인된 인증정보 위치를 찾지 못해 인증된 쓰기·읽기·정밀 복제 지연 검증이 보류됐다. 계정 초기화·비밀번호 변경·인증 비활성화는 하지 않았다.

이후 팀원의 별도 인증 시험 보고가 있으나 그 시험 범위와 인프라 운영 검증은 [서비스·통합](02-services-and-integration.md#팀원의-후속-검증과-미완료-범위)처럼 구분한다. 기존 계정 권한을 변경하거나 시험 결과를 전체 장애조치 검증으로 확장하지 않는다.

## Garage S3

Garage 2.4.1 두 노드와 Caddy 2.11.7의 HTTPS 진입점을 구성했다. 전용 데이터 마운트의 메타데이터·객체 디렉터리를 사용하며 기존 디스크를 재포맷하지 않았다. Garage는 AGPLv3, Caddy는 Apache-2.0이다.

Linux 정적 바이너리의 실제 Ubuntu 실행을 확인했다. Garage 배포 파일은 다운로드 후 SHA256과 배포 노드 간 일치를 확인했으나 당시 공식 checksum sidecar를 받지 못했으므로 발행자 서명·체크섬까지 검증했다고 주장하지 않는다. Caddy는 공개 checksum을 대조했다.

프로젝트 전용 버킷과 최소 권한 클라이언트를 사용한다. 팀원은 보호된 안내서의 HTTPS endpoint·서명 region·path-style 설정·CA·Vault 전달 절차를 사용한다. AWS 대상 리전과 S3 서명 region을 혼동하지 않는다. 공개 문서에는 실제 키·버킷 주소·인증 경로를 포함하지 않는다.

실제 검증은 양쪽 endpoint의 PUT·GET·LIST·DELETE·SHA256, 5,373,952바이트 multipart, 미인가 요청 거절, NiFi 네이티브 프로세서, Worker 3대의 Spark S3A를 포함한다. NiFi 시험 객체는 8,074바이트였고 Spark는 Hadoop 3.4.2·AWS SDK v2 2.29.52 조합을 사용했다.

**두 노드 구성은 쓰기 고가용성을 보장하지 않는다.** 실제 단일 노드 중지 시험에서 다른 노드 GET은 200·해시 일치, PUT은 503이었다. 복구 후 256개 partition 정상 상태를 확인했다. 이 관측으로 모든 장애 상황의 읽기 가용성·내구성을 보장하지 않는다.

메타데이터 주기 snapshot과 설정 백업은 기존 보호 경로에 유지한다. 같은 데이터 디스크의 snapshot은 독립 재해복구 백업이 아니며 설정 백업에는 비밀정보가 포함될 수 있어 공개하지 않는다.
