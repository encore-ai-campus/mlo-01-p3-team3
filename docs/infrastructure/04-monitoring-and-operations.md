# 모니터링과 운영 경계

[문서 목록](README.md) · 근거: [E06](07-evidence-and-handoff.md#e06), [E07](07-evidence-and-handoff.md#e07), [E08](07-evidence-and-handoff.md#e08)

## 수집·대시보드

Prometheus 3.15.0·node_exporter 1.12.1·Grafana OSS 13.2.4를 사용한다. 기존 데이터 소스와 대시보드를 유지하며 PJ3 Infrastructure Health를 코드 기반으로 배포했다.

2026-10-17 API 검증에서 20대 모두 CPU·RAM·디스크 데이터가 있었고 서버 선택 목록 20개, 테이블 8개 query의 각 20행, 상세 15개 query와 새로고침 후 보존을 확인했다. 당시 정상 14·경고 6, 수집 실패·누락 0이었다. 이는 기록 시점 결과다.

후속 디스크·S3 작업에서 실제 데이터 파일시스템·Garage 패널을 추가했다. 최종 S3 보고서 기준 31개 패널과 18개 경고 규칙이다. API 검증을 실제 브라우저 육안 검사로 표현하지 않는다.

파일시스템 선택은 실제 데이터 mount를 포함하도록 하며 boot·가상 파일시스템을 데이터 디스크로 세지 않는다. UUID 마운트와 DB 디스크가 구성된 뒤 신규 mount 메트릭을 확인했다.

## 서버 응답과 서비스 건강

Exporter의 up은 수집 가능 여부다. 인증된 DB 읽기·쓰기, 복제, Kafka 메시지, Spark Job, S3 객체 시험의 성공과 동일하지 않다.

검사 미구성은 NOT CONFIGURED, 인증정보 부족·오래된 결과는 UNKNOWN으로 구분한다. 없는 지표를 0으로 채워 정상처럼 표시하지 않는다. MySQL 복제 실측과 MongoDB 미완료 인증 범위도 구별한다.

서비스 수집기는 읽기 전용 검사만 수행하며 업무 데이터 처리나 DB 사용자 권한을 변경하지 않는다. 300초 이상 오래된 결과는 정상으로 유지하지 않는다.

## 경고 규칙

| 영역 | 초기 기준 또는 범위 | 검증 경계 |
|---|---|---|
| 서버 수집 실패 | 2분 | 서비스 인증 실패와 구별 |
| CPU | 90% 이상 10분 | 단기 spike와 구별 |
| RAM | 90% 이상 5분 | VM 자원 제약 관찰 |
| 데이터 파일시스템 | 85% 이상 5분 | 실제 데이터 mount 대상 |
| 서비스 readiness 실패 | 2분 | 실제 검사 가능한 서비스만 |
| UNKNOWN | 5분 | 미검증을 정상 처리하지 않음 |
| 필수 메트릭 누락 | 2분 | 미수집 별도 표시 |
| 서비스 수집기 stale | 300초 초과 후 2분 | 오래된 정상값 방지 |
| 디스크·복제 확장 | 후속 6개 규칙 | 마운트·용량·수집 가능한 복제 상태 |
| Garage 확장 | 후속 4개 규칙 | S3 응답·저장소·수집 상태 |

최초 8개에 저장소 6개와 Garage 4개가 추가됐다. 규칙별 실제 표현식·평가 조건은 보호된 배포 코드가 원본이다. 알림 수신자가 정해지지 않아 외부로 임의 전송하지 않았다. 규칙 평가 시험과 알림 실제 전달·당직 대응은 별도이며 후자는 미완료다.

## 운영·복구 원칙

설정 변경 전에 원본·소유권·권한을 백업한다. 기존 서비스 상태와 재시작 수를 비교해 불필요한 재시작을 피한다. 모니터링 배포 당시 조사 대상 기존 서비스 17개의 상태·재시작 수를 대조했다.

DB 디스크 장애 시 서비스를 멈추고 원래 데이터 복구본·UUID·권한·설정을 검증한다. 빈 경로로 기동하거나 새 DB 초기화로 복구하지 않는다. MySQL 복제는 GTID·TLS·수신/실행 상태를 확인한 후 복구하고 기존 데이터를 덮어쓰지 않는다.

Garage 복구에서는 기존 node ID·데이터·메타데이터를 보존한다. Kafka는 기존 cluster ID·log를 보존한다. MongoDB는 기존 Replica Set과 사용자 권한을 유지하고 강제 재동기화·재초기화를 기본 조치로 삼지 않는다.

정확한 백업 위치·인증 접근 방식은 공개 문서 대신 승인된 운영자가 보호된 근거 목록에서 확인한다.
