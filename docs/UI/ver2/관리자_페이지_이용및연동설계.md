# SketchOn 운영 관리 페이지

기준: 2026-10-16 · 9차 · 브랜치 `feature/#17`

## 목적과 접속

서비스 행동 데이터, 생성 결과와 수집 원본의 상태를 확인하고 광고 등록·심사 흐름을 미리 검증한다. **광고 서버는 아직 개발·연결하지 않았다.** 이 관리 페이지가 광고 서버의 구현 완료를 의미하지 않는다.

접속 주소는 `/ops/`다. 기존 회원 `hilee`에 `SketchOn 운영자` 그룹과 `is_staff`를 연결한다. 비밀번호 변경이나 계정 신규 생성, superuser 부여는 하지 않는다. 서비스 상단의 `운영 관리`로 이동할 수 있다. 일반 회원·비회원은 주소를 직접 입력해도 접근할 수 없다.

## 권한과 데이터 보호

`operations.permissions.ops_required`는 활성 로그인·staff와 메뉴별 권한을 서버에서 검사한다. `OperatorAudit`의 custom permission은 대시보드/이용자/작업/행동/수집/민감 원본/Raw 검수/광고 초안/광고 심사/성과/감사로 나눈다. 운영자 그룹은 이 권한만 받으며 `auth.change_user` 같은 회원 관리 권한을 받지 않는다.

사진·결과·Raw·광고 소재는 보호된 운영 경로로 제공한다. 공개 media 디렉터리 경로를 화면에 전달하지 않는다. 운영 화면도 CSRF·no-store·기존 로그인 상태 재검증을 사용하고 광고 배너를 표시하지 않는다. 타 계정으로 바뀐 경우 캐시된 본문을 지운다. 원본 열람은 감사 이력으로 남긴다.

```powershell
Set-Location C:\mlo-01-p3-team3\src\demo_sketchon
.\.venv\Scripts\python.exe manage.py migrate
.\.venv\Scripts\python.exe manage.py configure_ops_roles --username hilee
.\.venv\Scripts\python.exe manage.py index_ops_raw --limit 1000
```

권한 설정 명령은 기존 활성 계정만 허용한다. Raw 색인은 파일을 읽고 검증 메타데이터만 만든다. 화면의 `기존 Raw 색인`도 동일하며, 일반 목록 요청마다 전체 파일을 읽지 않는다. 같은 파일을 다시 색인해도 파일이나 재전송 수를 변경하지 않는다. 한 번에 제한한 파일 수까지만 확인하므로 대량 보관 시 배치 색인으로 확장한다.

## 행동·생성·수집 추적

- `Project.flow_id`: 신규 Home → 편집 → 업로드 → 자르기 → 다시 그리기 흐름을 연결한다. 완전히 새 작업/저장 작업 복원은 새 흐름이다. 기존 데이터는 NULL로 보존한다.
- `SketchEvent.actor_kind/actor_account/visitor_id/flow_id`: 수신 시점의 서버 인증 스냅샷이다. 비회원 작업을 회원에게 연결해도 과거 스냅샷을 수정하지 않는다. 기존 이벤트는 unknown이다.
- `reported_actor_kind`: 클라이언트가 발생 시점에 신고한 이용 구분이다. 지연 전송 시 수신 시점과 다를 수 있으며 권한 판단에 사용하지 않는다.
- `GenerationAttempt`: 유효 요청 ID별 진행/성공/실패/제한/충돌, 경과시간과 일반 오류 코드. 재전송은 같은 행을 사용한다. 동시 재시도에서 성공 상태를 늦은 실패가 덮지 않는다. 도입 이전 성공 결과에 실패 이력을 소급해 만들지 않는다. 비정상 JSON/잘못된 요청 ID는 시도 집계 대상이 아니다.
- `RawReceipt`: 원본 JSON과 분리한 수집/검수 메타데이터. 체크섬은 정규화되어 저장된 원본 바이트 기준이다. 수집 제한/빈 문서 등은 자동 검증 경고로 표시하고 사람이 별도 검수한다. 잘못된 원본/저장 실패는 승인할 수 없다. 원본 내용은 바꾸지 않는다.

Raw 계약 `roompick-sketch-1.0.0`, 기존 쿠키·방문 ID·회원 작업 귀속은 유지한다. 브라우저에 남아 아직 서버로 전송되지 않은 데이터는 운영자가 확인할 수 없다. 생성 횟수 제한은 기존 IP별 한국 시간 하루 성공 3회 규칙을 유지한다.

## 광고 데모와 이후 연결 지점

실제 광고 서버 개발 전 준비 단계다. `operations/ad_gateway.py`는 미연결 상태만 반환하고 네트워크 요청을 하지 않는다. 캠페인은 SketchOn 로컬 DB에만 저장한다. 임의 노출·클릭·입찰·매출 이벤트를 만들지 않는다. `C:\CHAPTER3\ad_server` 실습 코드는 구조 참고용이며 이번 작업으로 변경하지 않는다.

향후 매체 ID는 `sketchon`, 위치 ID는 `editor-right`, `result-right`, `my-right`로 제안한다. Home·인증·운영 화면·배너가 숨겨진 좁은 화면은 송출 대상에서 제외한다. 실제 서버 계약에서 최종 확정해야 한다.

1. 광고 서버와 매체/위치/요청/응답 스키마를 확정한다. 서버 키는 서버 환경에만 두고 브라우저에 전달하지 않는다.
2. 정책 적합·심사 승인·활성·카테고리 적합·기간 조건을 먼저 검증하고 후보 안에서 입찰을 비교한다.
3. 실제 결정 ID와 소재/가격/정책 버전 스냅샷을 유지한다. 노출·클릭의 중복 키와 재전송 계약을 정하고, 화면에 실제 표시된 경우만 노출로 인정한다.
4. 광고임을 표시하고 상품 추천 세 칸과 분리한다. 회원 맞춤화는 동의·보관·삭제 정책을 정한 후 연결한다.
5. 광고 서버 장애 시 무광고로 서비스가 계속되게 하고, 실제 이벤트가 들어온 이후 성과 집계를 활성화한다. 가상 포인트 합계를 매출로 취급하지 않는다.

광고 소재·제목·문구·광고주·URL·분류·위치·기간 변경은 승인 상태를 PENDING으로 되돌린다. 집행 요청 활성과 가상 포인트 변경은 별도로 기록한다. 모든 변경은 revision을 검사해 오래된 운영 화면의 덮어쓰기를 막고 사유를 감사 이력에 남긴다. 이 규칙은 로컬 운영 흐름 검증용이며 광고 서버 API 호환을 보장하지 않는다.


## 9차 실제 적용 확인

2026-10-16 `feature/#17`의 실제 데모에 migration 3개를 적용하고 기존 `hilee`에 운영자 그룹을 연결했다. superuser는 부여하지 않았고 비밀번호를 변경하지 않았다. 기존 Raw 42개를 읽기 전용으로 색인했으며 검증 오류는 없었다.

적용 전 존재하던 작업 337개·결과 77개·행동 이벤트 3,524개·추천 실행 10개·검색 조건 수정 9개·저장 프로젝트/버전 각 1개·찜 2개·회원 1개의 ID가 모두 유지됨을 확인했다. 사진·결과·Raw 등 기존 파일 236개의 SHA256도 일치한다. 실제 DB에 브라우저 테스트 계정은 만들지 않았다. 이후 정상 이용이나 접속 확인으로 데이터 수는 증가할 수 있다.

`http://127.0.0.1:8003/`와 `http://192.168.0.44:8003/`는 HTTP 200, 운영 CSS는 HTTP 200이다. 비회원의 `/ops/` 요청은 로그인으로 302 이동한다. 서버는 `0.0.0.0:8003`에서 실행한다. 운영자 로그인 후 상단 `운영 관리`로 접속한다. 실제 광고 서버는 시작하거나 연결하지 않았다.
