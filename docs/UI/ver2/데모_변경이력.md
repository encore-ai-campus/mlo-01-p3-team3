# 스케치·온 SketchOn 데모 변경 이력과 설계 검토 사항

현재 기준: 2026-10-16 · **9차 운영 관리 콘솔 반영**. 8차 회원 기능과 기존 그림판을 유지하며 운영·광고 연결 준비 범위를 확장했다.

## 9차 — 운영 관리 콘솔과 광고 연동 준비

2026-10-16 · `feature/#17`. 운영 개요·이용자·작업/결과·행동 데이터·스케치 수집·광고 관리·광고 성과·감사 이력의 8개 메뉴를 `/ops/`에 구현했다. 일반 회원이 운영 경로로 접근하지 못하도록 메뉴별 권한을 검사하고, 개인 사진·요청·Raw는 별도의 민감 원본 권한과 열람 감사로 보호한다. 지정 계정 `hilee`는 기존 비밀번호를 유지하며 운영자 그룹을 사용한다.

신규 작업의 흐름 ID, 이벤트 수신 인증/클라이언트 발생 시점 신고, 요청 ID별 생성 성공·실패·제한·충돌과 시간 기록을 추가했다. 기존 이벤트는 알 수 없는 상태로 보존하고 회원 연결을 이유로 과거 이용 구분을 바꾸지 않는다. Raw 색인·체크섬·검증 경고·사람 검수는 원본 파일과 분리한다.

광고 서버는 아직 개발·연결 전이다. 광고 등록·이미지·HTTPS 주소·품목·위치·기간·가상 포인트·심사·활성/중지를 로컬 데모에서 검증한다. 소재 변경 시 재심사하며 오래된 화면의 수정을 revision으로 차단한다. 실제 송출·입찰·노출·클릭은 발생하지 않고 성과는 **미연결/—**로 표시한다. 관리 화면에는 광고를 노출하지 않는다.

세부 동작과 향후 연동 조건은 [관리자 페이지 이용 및 연동 설계](관리자_페이지_이용및연동설계.md)에 정리했다. 기존 회원·그림판·결과·사진/Raw 데이터는 유지한다.

저장 버전 수정 중 사진을 교체해도 같은 프로젝트 계보를 유지한다. 다른 계정으로 전환하면 저장 대화상자를 닫고 제목을 지운다. 미전송 Raw는 현재 계정의 프로젝트 접근 권한을 확인한 뒤 전송하며, 다른 계정에서 접근 거절됐다는 이유로 영구 거절하지 않는다.

## 최초 구현 사진 위에 그리는 기본 흐름

첨부된 Phase 1 내용에서 PC·모바일 공용 Django 웹서비스, 사진 위 Canvas, 마우스·손가락·펜 입력, 정규화 좌표, 펜·지우개·실행 취소와 행동 데이터 수집을 구현 범위로 잡았다. 기존 게임 서버의 JSON 이벤트와 트랜잭션·버전 관리, Python 게임 클라이언트의 CSRF·응답 검증 방식을 참고했다. 브라우저 JavaScript가 기존 Python 클라이언트의 화면·입력 역할을 담당했다.

그림판 영역에는 Pointer Events와 touch-action: none을 적용했다. 좌표를 사진 영역 기준 0~1로 보관하고, 화면 크기가 달라져도 같은 위치에 다시 그리도록 했다. 사진·스케치 문서는 SQLite에 기록하고, 익명 방문 ID와 작업 ID에 행동 이벤트를 연결했다. 미전송 이벤트는 브라우저에 임시 보관하고 이벤트 UUID로 중복 수집을 막았다.

당시에는 가구 카테고리를 고르고 샘플 가구를 직접 놓는 UI를 넣었다. 카메라 버튼은 모바일 브라우저의 capture 요청을 사용했으며 실기기 촬영 성공을 확인한 기능은 아니었다. 다운로드는 현재 편집한 그림을 내보내는 기능이었고 상품 예측·검색·합성의 결과를 내보내는 흐름은 없었다.

사용자는 현재 서비스를 일회성으로 이용하고, 추후 로그인 후 이력을 보관·불러오는 방향으로 확장한다고 설명했다. 이에 사용자 이력 목록과 로그인 UI를 만들지 않고 익명 행동 수집을 먼저 구현했다. 초기 API의 문서 기록 기능과 방문 소유권 구조는 이후 검색 입력 보관과 계정 연결의 기반으로 남겼다.

이 단계에서는 그림판의 기본 입력을 구현했지만, **사용자가 무엇을 그렸는지 예측하는 서비스에 사전 가구 힌트를 제공하고 있었다.** 상품 검색이 핵심이라는 점도 화면 흐름에 충분히 반영되지 않았다.

## 1차 수정 입력 방식 확장과 상품 검색 흐름

사용자는 카메라 촬영이 현재 불가능하고, 그림 외에 텍스트·기본 도형이 필요하며, 지우개 크기를 알아보기 어렵다고 지적했다. 또한 카테고리와 샘플 가구를 먼저 보여주면 예측 서비스가 사용자에게 답을 알려주는 문제가 생긴다고 설명했다.

카메라와 가구 카테고리 UI를 제거하고, 사진 드래그 앤 드롭, 텍스트, 사각형·타원·직선·화살표를 추가했다. 지우개는 펜과 별도의 크기 값을 사용하고 실제 범위를 보여주는 원형 커서를 표시했다. 텍스트는 이때 입력란에서 먼저 작성한 뒤 사진의 위치를 눌러 배치하는 방식이었다.

상품 검색과 이미지 생성 연결이 없는 상태에서 사용자가 **이번에는 모의 결과로 흐름만 검증**하기로 선택했다. 상품 검색하기 버튼을 추가하고, 입력 문서의 스냅샷과 합성 결과를 Composition으로 보관했다. 검색 전에는 상품을 보여주지 않고, 검색 후 같은 화면의 결과 영역과 편집·합성 결과 탭으로 확인했다.

다운로드는 작업 중인 그림이 아니라 검색 시점의 합성 PNG와 결과 JSON을 제공하도록 바뀌었다. 입력을 수정하면 이전 결과 다운로드를 비활성화하고 다시 검색하도록 했다. 텍스트는 단어 규칙으로, 도형은 임시 예시로 상품을 선택했다. 이때 도형마다 별도 배치를 만들고 자유 그림의 영역도 별도 배치로 처리한 구조가 남아, 뒤에 3차에서 제기된 중복 상품 문제의 원인이 됐다.

## 2차 수정 Home 편집 결과 페이지 분리

사용자는 처음부터 그림판을 보여주는 대신 깔끔한 Home에서 시작하고, Windows 그림판처럼 사진 위에서 직접 텍스트를 입력하고 싶다고 요청했다. 도형을 놓은 뒤 선택 도구를 다시 누르는 과정도 줄여야 했다. 검색 후에는 편집 UI가 없어지고 결과를 확인·조절하는 페이지로 이동해야 했다.

Home에는 소개 문구와 내 공간 꾸미러 가기 버튼을 두었다. 편집 도구는 이미지 위에 배치했다. 텍스트는 T 도구를 누르면 I 모양 커서를 보여주고, 사진 위치를 누르면 그 자리의 입력란에서 직접 타이핑하게 바꿨다. 입력 완료 후 이동할 수 있고, 더블클릭으로 수정할 수 있다. 한글 IME 조합 중 Enter는 입력 완료로 처리하지 않는다.

도형을 다시 누르면 선택 도구를 바꾸지 않고 이동·크기 조절할 수 있게 했다. 삽입 시 클릭·드래그·놓기를 실행 취소 한 번으로 묶었다. 다만 이 단계의 선택 검사는 도형의 사각 경계 상자를 사용했기 때문에, 도형 안의 빈 곳을 눌러도 도형이 선택되는 문제가 남았다.

검색하면 서버가 원래 입력 작업을 잠그고 별도 결과 페이지로 이동한다. 결과에는 익명 방문 ID의 앞 8자리와 예측 문구를 표시하며, 사진 업로드·스케치 도구는 표시하지 않는다. 가구 그래픽을 직접 이동·크기 조절할 수 있고, 조작 완료 시 합성 PNG와 결과 좌표를 함께 갱신한다. 저장 중에는 다운로드를 막고, 실패하면 마지막 저장 배치로 되돌린다.

다시 그리기는 같은 사진을 사용하는 새 빈 작업을 생성했다. 이전 결과를 지우지 않으면서 그림·텍스트·도형과 실행 취소 기록을 비웠다. 방문 ID는 유지하고 작업 ID만 새로 부여했다. 잠긴 편집 URL을 다시 열면 결과로 이동한다.

## 3차 수정 그림판 경계와 단일 상품 입력

### 사진 자르기

사진 자르기 도구로 남길 영역을 드래그하고 적용한다. 서버는 사진 내부 좌표와 최소 가로·세로 4픽셀을 검사해 새 잘린 사진을 만든다. 이미 표시한 스케치가 있으면 **자르기 적용 시 스케치가 비워진다**는 확인을 먼저 표시한다. 현재 데모에서는 사진 좌표계를 바꾸면서 기존 표시까지 변환하는 기능은 구현하지 않는다.

자른 사진은 새 작업에 연결하고 방문 ID는 그대로 유지한다. 원래 사진과 기존 결과를 덮어쓰지 않는다.

### 경계 기반 채우기

채우기는 사진 픽셀 대신 스케치 레이어의 연결 픽셀 영역을 탐색한다. 닫힌 사각형의 내부를 누르면 그 내부에만 채워지고, 가운데 선으로 영역이 닫히면 선을 넘지 않는다. 안쪽에 타원을 넣으면 타원 내부와 바깥쪽도 별도 영역으로 처리한다. 열린 경계에 틈이 있으면 다른 영역으로 이어져 퍼질 수 있다.

채우기 영역은 색상과 픽셀 행별 구간으로 저장한다. 최대 변 길이 1200인 스케치 렌더링을 기준으로 영역을 계산하고, 위치·크기는 사진 기준 상대 좌표로 저장한다. 현재 한도는 채우기 한 개당 100,000구간, 전체 200,000구간이다.

도형의 채운 영역을 도형에 연결한다. 바깥 도형을 이동·크기 조절할 때 도형 안에 포함된 채우기, 내부 도형, 분리선과 내부 획을 같은 그룹으로 변환한다. 복사·붙여넣기와 삭제도 이 그룹을 함께 처리한다. 부분적으로 겹친 다른 도형을 자동으로 전체 그룹에 포함하는 기능은 아니다.

### 외곽선 선택과 도형 내부 편집

사각형·타원·직선·화살표는 외곽선 근처에서만 선택한다. 도형 내부의 빈 곳은 이동 대상으로 잡지 않으므로 다른 도형을 넣을 수 있다. 선택한 도형의 크기 조절 손잡이는 계속 사용할 수 있다.

분리선을 그릴 때는 직선·화살표 도구가 바깥 사각형·타원의 선에서 시작해도 새 선을 그리도록 했다. 외곽선을 눌러 움직이려는 동작과 새로운 분리선을 시작하려는 동작이 충돌하지 않도록 한 처리다. 자유 획을 옮길 때는 선택 도구를 사용한다.

### 모든 표시를 하나의 상품 입력으로 처리

기존에는 여러 도형과 자유 그림 영역을 각각 별도 예시 상품으로 바꿨다. 한 가구를 여러 획과 도형으로 그려도 여러 상품이 겹쳐 배치될 수 있었다.

3차에서는 **사용자가 그린 전체 문서 한 개를 원하는 상품 한 개의 입력으로 취급한다.** 자유 획, 텍스트, 도형, 채우기를 모두 같은 입력에 포함하고 합성 가구는 한 개만 생성한다. 입력 전체의 영역을 합쳐 배치 위치·크기를 정한다. 실제 AI에서는 전체 스케치 이미지를 문맥과 함께 해석해야 하며, 획이나 도형 개수를 상품 개수로 사용하는 방식은 피해야 한다.

현재 모의 서비스는 전체 텍스트에서 단어 규칙으로 상품을 고르고, 해석할 단어가 없는 자유 그림에는 예시 상품을 사용한다. 여러 상품을 한 사진에서 독립적으로 요청하는 기능과 상품 영역을 분리하는 정책은 현재 범위에 포함하지 않는다.

### 결과 이후 세 가지 경로

| 버튼 | 사진 | 스케치 | 방문 ID | 작업 ID |
| --- | --- | --- | --- | --- |
| 처음부터 다시 그리기 | 이전 사진 재사용 | 비움 | 유지 | 새 작업 |
| 스케치 수정하기 | 이전 사진 재사용 | 상품 검색 직전의 입력 문서 복원 | 유지 | 새 작업 |
| 다른 상품 검색하기 | 사진 업로드 전 상태 | 비움 | 유지 | 새 작업 |

스케치 수정하기는 결과 가구를 움직인 좌표를 원래 그림으로 역변환하지 않는다. 검색 시 보관한 원본 스케치·텍스트·도형·채우기를 복원한다. 새 편집 작업의 Undo/Redo 기록은 새로 시작하지만 원래 입력 내용은 유지한다. 이전 결과의 PNG·JSON은 보존한다.

### 단축키와 복사 단위

Ctrl+Z는 실행 취소, Ctrl+Y와 Shift+Ctrl+Z는 다시 실행이다. Ctrl+C와 Ctrl+V는 그림판에서 선택한 요소와 포함된 채우기·내부 표시를 복사·붙여넣는다. 복사 버튼·붙여넣기 버튼도 제공한다. 복제 요소에는 새로운 요소 ID를 부여하되 방문 ID는 바꾸지 않는다.

현재 복사 버퍼는 해당 그림판 페이지 안에서 사용한다. 다른 앱이나 다른 브라우저 탭으로 이미지·요소를 복사하는 OS 클립보드 연동은 구현하지 않았다. 텍스트 입력란에 포커스가 있을 때는 브라우저의 기본 텍스트 복사·붙여넣기를 유지한다.

## 4차 수정 부분 지우기와 편집 단위 분리

3차에서 도형 내부의 요소를 위치만으로 자동 묶었던 방식은 사용자가 별도로 그린 내부 획·도형까지 이동시키는 문제가 있었다. 지우개도 닿은 요소를 통째로 삭제했다. 4차에서는 **채우기와 원래 윤곽의 연결 / 겹친 펜 획의 자동 연결 / 사용자가 지정한 그룹**을 기준으로 편집 단위를 바꿨다. 3차 설명은 당시 구현 기록이며 현재 동작은 아래 내용을 따른다.

### 업로드 제한과 사진 복귀

파일 선택과 드래그 앤 드롭 모두 10MB 초과 시 **10MB 이하의 파일을 업로드해주세요.**라는 안내창을 표시하고 업로드하지 않는다. 서버에서도 파일 크기를 다시 검사한다.

4차에서는 사진 업로드·교체·자르기와 스케치 편집을 하나의 작업 흐름으로 관리하도록 **실행 취소·다시 실행을 통합**했다. 사진 조작을 위한 별도 복귀 버튼 대신 그림판 전체에서 공통으로 사용하는 작업 기록을 적용했다.

현재는 별도 사진 복귀 버튼을 제거하고 도구 목록 위에 공통 **실행 취소 / 다시 실행** 영역을 둔다. **첫 사진 업로드가 첫 작업 단계**이며 업로드 직후 실행 취소 버튼이 활성화된다. 스케치 편집과 사진 교체·자르기를 같은 최근 20단계 기록에 넣어 순서대로 되돌리고 다시 적용한다. 예를 들어 업로드 → 사각형 → 자르기 후 취소 한 번은 자르기 이전의 사진과 사각형, 다음 취소는 사각형 이전 상태, 다음 취소는 업로드 이전 상태다. 다시 실행은 그 반대 순서로 동일한 저장 사진을 복원한다. 재업로드나 재자르기를 호출해 새 작업을 중복 생성하지 않는다.

Undo/Redo는 사진·사진 크기·스케치 문서를 함께 저장한다. 취소 뒤 새 편집을 하면 기존 다시 실행 기록을 비운다. 다른 사진으로 복원할 때 서버에서 소유권·검색 잠금·작업 버전을 확인하고, 다른 탭에서 변경됐거나 읽기·이미지 로딩이 실패하면 현재 상태와 기록을 소모하지 않는다. 원본 사진 파일을 덮어쓰지 않고 방문 ID도 유지한다.

현재 스케치와 통합 기록은 같은 탭의 sessionStorage에 보관해 동일한 작업 URL의 새로고침 후 복원한다. 탭 종료·저장 공간 차단/부족 시 복구를 보장하지 않는다. 서버의 작업 버전과 임시 기록의 버전이 다르면 기존 서버 상태를 우선한다. 계정별 작업 이력은 후속 설계다. 결과 이후 스케치 수정하기/처음부터 다시 그리기/새 사진 시작은 기존처럼 새로운 편집 작업의 기록을 시작한다.

### 지우개를 부분 지우기로 변경

이전에는 지우개 범위가 도형이나 채우기의 경계 상자에 닿으면 요소 전체를 삭제했다. 현재는 펜·도형·채우기·텍스트 각각에 지운 경로를 연결하고 Canvas의 destination-out으로 해당 경로의 픽셀만 지운다. 사진은 지우지 않는다.

지운 경로는 이동·크기 조절·복사 시 함께 변환하며 Ctrl+Z/Y로 지우기 전후를 복원한다. 검색 입력 스냅샷과 결과 JSON, 스케치 수정하기에도 유지한다. 새로 그린 선에는 이전 지우기 경로를 적용하지 않는다. 부분 지우기는 요소당 100회, 전체 점과 중복 보관된 지우기 점을 합쳐 100,000점으로 제한하고 서버가 좌표·폭·중첩 형식을 검증한다.

### 채운 윤곽, 자동 연결, 명시적 그룹

| 편집 단위 | 묶는 기준 | 따로 유지하는 요소 |
| --- | --- | --- |
| 채운 도형 | 도형 ID에 연결된 채우기 영역 | 안쪽에 별도로 삽입한 다른 도형·선·펜 획 |
| 채운 펜 윤곽 | 연결된 펜 윤곽 ID와 해당 영역의 채우기 | 주변의 떨어진 획 |
| 자동 연결 펜 획 | 새 펜 획이 기존 펜 획에 닿거나 교차 | 도형은 펜과 겹쳤다는 이유만으로 연결하지 않음 |
| 명시적 그룹 | 영역 선택으로 전체를 둘러싸고 그룹화 클릭 | 선택 범위 밖의 독립 요소 |

외곽선과 채운 부분을 클릭하면 같은 편집 단위를 선택한다. 펜 도구에서는 계속 그릴 수 있고 펜 윤곽을 옮길 때는 선택 도구를 사용한다. 빈 도형 내부에는 다른 도형을 삽입할 수 있다. 채우기 선택은 사각 경계 상자만 검사하지 않고 실제 저장된 마스크 구간과 지운 경로를 검사한다.

겹친 펜 획은 하나의 그룹 ID로 연결해 함께 이동·크기 조절한다. 여러 획의 점 목록을 억지로 이어 붙여 원래 없던 연결선을 만들지 않는다. **영역 선택 → 전체를 둘러싸도록 드래그 → 그룹화**로 떨어진 획과 도형도 묶을 수 있으며, 그룹 해제 시 독립 요소로 돌아간다. 각 윤곽에 연결된 채우기는 그룹을 해제해도 해당 윤곽과 함께 움직인다.

복사·붙여넣기·삭제·방향키·크기 조절도 같은 편집 단위를 사용한다. 복제에는 새 요소·그룹 ID를 부여해 원본과 복제가 함께 이동하지 않게 한다. 방문 ID는 유지한다.

### 선택한 선 두께와 채우기 가장자리

요소를 선택한 상태에서 크기 슬라이더를 바꾸면 새로 그릴 펜 설정뿐 아니라 선택한 펜·도형의 실제 선 두께도 바뀐다. 그룹은 그룹 안의 펜·도형 선을 함께 바꾼다. 한 번의 슬라이더 조절을 실행 취소 한 번으로 기록한다. 텍스트·채우기에는 선 두께를 직접 부여하지 않는다.

채우기는 여전히 픽셀 영역 탐색이다. 마스크를 선 밑으로 1픽셀 확장하고 이미지 보간을 적용해 윤곽과 채운 영역 사이의 투명한 틈과 크기 변경 시 거친 가장자리를 줄였다. 선 자체는 기존 Canvas의 벡터 경로와 둥근 끝 처리를 유지한다. 추가 패키지 설치 없이 수정했다.

완전한 일러스트 편집기 수준의 벡터 영역 연산으로 바꾼 것은 아니다. 최대 변 1200픽셀 기준 채우기이므로 크게 확대하거나 얇고 복잡한 경계에서 픽셀 한계가 남을 수 있다. 벡터 경계 추적·Boolean 연산, 더 높은 해상도의 마스크·보관 비용 검토는 정식 설계 때 판단한다. 열린 경계의 틈을 넘어 색이 퍼지는 동작은 계속 적용된다.

### 고정 제목과 상품 카드 자리

툴 아래 입력란은 초기 작업 제목을 바꾸기 위한 input이었다. 일회성 데모 흐름에서는 제목 수정이 필요하지 않아 **나의 공간 스케치**라는 고정 문구로 바꾸고 오른쪽 획·표시 개수만 갱신한다.

결과 다운로드 버튼 위에 상품 이미지용 카드 3칸을 마련했다. 현재 카드에는 상품 이미지 자리와 연결 준비 중 문구를 보여주고 가짜 판매 링크는 넣지 않는다. 실제 상품 API 연결 시 상품 이미지·상품명·판매 URL을 연결할 위치다. 합성 결과의 가구 한 개와 추천 후보 상품 카드 세 개는 다른 개념이며, 카드 수 때문에 합성 상품 수를 늘리지 않는다.

### 팀원 접속을 위한 내부망 공유

팀원들이 같은 내부망에서 데모를 확인할 수 있도록 현재 Wi-Fi IPv4 **192.168.0.44**를 Django 기본 허용 주소에 추가하고 서버 수신 주소를 **0.0.0.0:8003**으로 변경했다. 공유 URL은 **http://192.168.0.44:8003/**, 기존 PC의 localhost 접속도 유지한다.

Windows 공용 네트워크와 기존 Python TCP 차단 규칙 때문에 허용 주소 설정만으로 원격 접속을 보장할 수 없다. 관리자용 Allow-RoomPick-LAN.ps1은 현재 IP의 TCP 8003 포트만 같은 서브넷에 허용하고 기존 Python TCP 차단에서는 이 포트만 제외한다. 다른 Python 포트와 UDP 차단은 유지한다. IP가 바뀌면 허용 주소·방화벽 설정도 갱신해야 한다. 관리자 권한으로 전용 허용 규칙 적용을 완료하고 TCP 8003·로컬 IP·원격 서브넷과 기존 다른 포트/UDP 차단 유지 상태를 조회해 확인했다. 같은 PC의 내부망 IP를 사용해 브라우저에서 접속·사진 업로드·검색·다운로드까지 검증했다. 실제 팀원 장치와 네트워크의 기기 간 통신 정책은 별도 확인 대상이다.

### 휴대폰 JPG 업로드 호환성 개선

10MB 이하의 휴대폰 JPG가 업로드되지 않는 사례를 원본 파일로 재현했다. 원본은 5,580,645바이트(약 5.32MiB), 5712×4284픽셀(24,470,208픽셀)로 용량과 해상도 제한을 통과했지만 Pillow가 실제 내부 형식을 MPO로 인식했다. 기존 서버는 JPEG·PNG·WebP만 허용해 이를 형식 오류로 거부했고 용량/해상도 안내와 합쳐진 메시지 때문에 원인을 구분하기 어려웠다.

MPO는 여러 이미지를 담는 JPEG 계열 형식으로, 현재는 첫 번째 사진을 읽어 기존 EXIF 회전·최대 2048픽셀 리사이즈·단일 JPEG 변환 흐름에 넣는다. 추가 이미지와 메타데이터는 서비스 사진에 보관하지 않는다. 원본 파일은 변경하지 않는다. 10MB·2,500만 픽셀 제한과 소유권 검사는 유지하고 용량·해상도·형식 오류 메시지를 구분했다. 합성·상품 해석 동작과는 관계없는 사진 입력 호환성 수정이다.

실제 제보 파일 **KakaoTalk_20261013_153801607.jpg**로 수정 전 HTTP 400 형식 오류를 재현하고, 수정 후 같은 원본의 업로드가 HTTP 201로 성공하는 것을 확인했다. 서비스에 저장된 사진은 **2048×1536픽셀의 단일 JPEG**로 화면에 정상 표시됐다. 사진 업로드 실행 취소·다시 실행, 동일한 방문 ID 유지와 브라우저 오류가 없는 것까지 확인했다. 따라서 이 사례의 원인은 파일 용량 초과가 아니라 JPG 내부 형식에 대한 서버의 허용 검사였다.

### 4차 검증과 남은 범위

- Django 테스트 29개: 기존 소유권·CSRF·검색 잠금·단일 상품·자르기·결과 버전 검증과 부분 지우기/그룹 데이터 저장 및 잘못된 입력 거부, 10MB 초과 서버 오류 안내, 부분 지우기 마스크가 이후 새 획에 영향을 주지 않는 처리, MPO JPG의 첫 프레임만 JPEG로 저장하고 소유권 유지, 해상도 제한 안내 구분.
- JavaScript 계산 테스트 11개: 기존 좌표·채우기 경계 검증과 내부 요소의 독립 이동, 연결 획/명시적 그룹 선택, 채우기 마스크의 빈 부분·지운 부분 선택 제외, 지우기 경로 좌표 변환.
- 실제 Edge 자동화: 내부망 IP로 실행한 10MB 안내창, 첫 업로드 취소/재실행, 업로드·자르기·스케치의 순차 취소/재실행, 새로고침 후 통합 기록, 사진 교체 복원, 다른 탭의 버전 충돌 시 현재 상태와 Undo 기록 보존, 취소 후 새 편집 시 Redo 제거, 펜 폐곡선 채우기·자동 연결·이동, 영역 그룹화/해제, 내부 도형 독립 이동, 선택 선 두께, 부분 지우기와 이동 후 마스크, Ctrl+C/V/Z/Y, 결과 입력의 지운 경로 복원, 상품 카드 3칸, PNG/JSON, 방문 ID 유지, 모바일 화면의 터치 채우기.
- 실제 스마트폰·태블릿 실기기와 대규모 장시간 편집은 확인하지 않았다. AI 인식·실제 상품 이미지·판매 링크·로그인 이력은 기존 모의 검증 범위에 따라 연결하지 않았다.

## 5차 수정 참고 버전의 기능을 기존 데모에 확장

기준은 기존 `roompick`으로 두고 `roompick_ver0.2`는 참고 소스로만 사용했다. 기존 DB·방문 ID·그림판과 직접 가구 이동을 유지하면서 Home의 사진 중심 구성, 중앙 사진 선택·예시 공간 체험, 설명과 스타일 입력, 그림 없이 생성하는 경로를 추가했다. 설명과 스타일도 사진·스케치와 같은 실행 취소 기록에 포함하고 사진 교체·자르기에서 유지했다. 스케치 수정은 생성 직전 설명과 스타일을 복원하고 빈 작업·새 사진 경로는 이를 비웠다.

공간 만들기와 상품 찾기를 분리했다. 결과에서 생성된 물체를 고르면 기존 상품 이미지 세 칸에 모의 추천을 표시하고 노출·선택·비선호를 수집한다. 배치 실행 취소·다시 실행·처음 배치로, 원본 비교, 품목·검색 영역 수정도 추가했다. 당시 검색 영역은 실제 가구 배치와 별도로 수정하는 사각형으로 구현했다.

신규 업로드는 원본 바이트와 SHA-256을 파생 JPEG와 따로 보관한다. Project 요청 입력, Composition 생성 입력·최초 배치, RecommendationRun 추천 실행·임대 상태, SceneObjectRevision 검색 조건 변경을 확장 migration으로 추가했다. 이전 DB와 기존 미디어 파일을 보존했고, 레거시 결과 가구는 기존 렌더링을 유지했다. 이벤트별 브라우저 저장 키, 요청 ID·입력 해시·임대 토큰, 배치 버전 검사로 덮어쓰기와 중복 반영을 방어했다. SQLite IMMEDIATE 트랜잭션과 대기 시간을 적용했으며 외부 제공자 호출은 트랜잭션 밖에서 실행한다.

이 단계에서 Django 67개·Node 26개, 격리 서버의 PC·모바일 흐름과 작은 동시 요청 회귀 검사를 확인했다. 실제 AI·광고 서버·판매 상품 API나 운영 처리량 검증은 포함하지 않았다.

## 6차 수정 모던 UI 통일

PC·모바일의 Home·편집·결과 화면, 첫 사진 선택 버튼, 가로 넘침과 생성·추천을 브라우저에서 확인했다. 기존 그림판·실행 취소·원본 수집 회귀 검사와 Django 67개·Node 26개도 통과했다.

### 서비스 이름과 브랜드

서비스 표시명을 RoomPick에서 **스케치·온 SketchOn**으로 변경했다. 방 선택보다 사진 위에 아이디어를 그려 공간을 바꾸는 서비스 의도를 담았다. 확정 로고는 검정 영문 한 줄 **Sketch · On**과 가운데 점을 콕 찍는 기하학적 연필로 구성한다. Home·편집·결과 헤더와 기존 푸터 로고를 같은 이미지로 통일하고 사이트 아이콘에도 검정 연필·점을 사용한다. 선택한 생성 이미지 원본은 `sketch/static/sketch/assets/sketchon-logo-approved.png`에 보관하며 원본과 복사본의 SHA-256 일치를 확인했다. 웹에서는 이미지 자체를 변형하지 않고 CSS로 바깥 흰 여백만 숨겨 PC·모바일 헤더에서 선명하게 보이게 했다. 브라우저 탭 제목·모의 상품 브랜드·사용자 안내와 PNG 다운로드 파일명에도 서비스명을 반영했다. 프로젝트는 `C:\mlo-01-p3-team3\src\demo_sketchon`으로 이동했다. 서버 주소·브라우저 저장소 키·작업 및 익명 방문 ID는 유지해 기존 작업과 이력을 이어간다.

### 사진 표시와 중복 입력 버튼

편집 사진의 표시폭을 100%로 복원하고 사진 비율에 따라 높이를 결정한다. editor와 result는 동일한 PC 열 너비·간격·안쪽 여백을 사용해 같은 화면에서 사진 표시 크기가 일치하게 했다. 합성 PNG의 픽셀 크기는 편집용 사진과 동일하게 유지한다. 업로드 원본은 별도 보관하며 기존 최대 2,048px 파생 이미지 처리 정책을 바꾼 것은 아니다. 사진 파일 10MB·2,500만 픽셀 제한도 유지한다.

사진 선택·예시 체험 버튼은 하나의 DOM 요소 쌍으로 유지한다. 업로드 전에는 그림판 중앙, 업로드 후에는 그림판 제목 옆으로 이동하며 아래쪽 중복 버튼을 제거했다. 동일 버튼으로 사진 교체와 예시 재체험, 통합 실행 취소를 계속 사용할 수 있다.

### 도구별 설정과 텍스트 색상

별도 선택 버튼을 제거하고 영역 선택 도구에 개별 요소 클릭·이동과 빈 곳 드래그 영역 선택을 통합했다. 사각형·타원 등의 외곽선 자동 선택, 연결 펜 획, 그룹화, 부분 지우기, 복사·붙여넣기와 단축키는 유지한다.

지우개에는 크기만, 채우기에는 색상만, 텍스트 입력·다시 편집 중에는 색상·글자 크기만 표시한다. 영역 선택 중에는 기본 색상·선 크기를 숨기되, 기존 텍스트를 선택하면 해당 글자의 색상만 표시한다. 글자 크기는 텍스트를 더블클릭해 입력 상태로 연 뒤 조절한다. 색상 변경은 새 글자의 기본색만 바꾸던 방식에서 선택한 텍스트에도 적용되도록 바꾸었고, 실행 취소·다시 실행 및 행동 기록에 포함했다. 선택한 펜 획의 두께는 펜 도구, 선택한 도형 선 두께는 해당 도형 도구에서 조절할 수 있다.

### 결과 버튼과 가구 선택

결과 제목을 `[사용자 ID] 님이 원하시는 “품목”을 생성하였습니다.`로 변경한다. 별도 가구 크기 조절 버튼은 제거하고 가구 모서리 드래그와 키보드 조절을 유지한다. 배치 실행 취소·다시 실행·처음 배치로 아래에 이미지 내려받기·처음부터 다시 그리기·스케치 수정하기·다른 상품 검색하기를 모았다. 아래쪽 중복 합성 이미지 버튼과 개발자 확인용 결과 작업 데이터 내려받기(JSON) 버튼은 제거했다. 사용자 화면에서는 합성 PNG만 내려받으며 입력 문서·배치·행동 데이터와 기존 데이터 조회 API는 내부 검증을 위해 유지한다.

품목·가구 배치 수정 토글을 열면 실제 생성 가구를 선택한다. 별도 주황색 사각형, 박스 조작 안내와 가로·세로 시작 위치 수치 입력은 제거했다. 가로 크기(%)·세로 크기(%) 입력으로 사진 대비 가구 규격을 조절할 수 있다. 입력을 마치면 실제 가구 이미지와 합성 PNG를 자동 저장하며 배치 실행 취소·다시 실행·처음 배치로에도 반영한다. 사진 범위를 벗어나는 수치는 저장하지 않고, 저장 실패 시 마지막 저장 크기로 되돌린다. 가구를 직접 이동·크기 조절한 경우에도 수치와 배치 버전이 갱신되고 그 실제 배치 좌표를 검색 조건에 사용한다. 품목 변경은 생성 가구 이미지를 다른 상품 이미지로 바꾸는 기능이 아니며 추천 조건을 수정한다. 품목이 현재 값과 다를 때만 검색 품목 적용을 활성화하고, 기본값으로 되돌리면 다시 비활성화한다. 가로·세로 변경은 품목 적용과 별도로 자동 저장한다.

가로·세로 규격은 사진 대비 2D 배치 비율이며 실제 상품의 cm 치수나 3D 규격을 뜻하지 않는다. 내부 위치·너비·높이는 정규화 좌표로 보관해 화면 조작과 합성, 추천 대상 영역을 맞춘다. 잘못된 좌표·범위, 다른 방문자의 작업 접근, 버전 충돌 검증은 유지한다.

## 비회원 식별의 현재 구현과 향후 정책

**익명 방문 ID와 작업 ID는 다른 개념이다.** 한 방문자가 사진을 여러 번 올리고 검색·재시작하더라도 여러 작업과 결과를 같은 방문 ID에 연결한다. 사진 자르기, 처음부터 다시 그리기, 스케치 수정하기, 다른 상품 검색하기, Home 이동, 새로고침 때문에 새로운 방문 ID를 만들지 않는다.

현재는 Django 세션에 무작위 UUID를 보관하고 브라우저 쿠키로 이어간다. 기본 쿠키 유효기간은 1년이다. 새 기기·새 브라우저·시크릿 모드·쿠키 삭제·만료는 기존 세션과 연결되지 않아 새로운 방문 ID가 생길 수 있다. 현재 방식은 같은 브라우저에서의 연속 사용을 연결하는 구현이지, 로그인 없이 동일한 사람을 영구 식별하는 정책은 아니다.

| 정식 설계에서 결정할 사항 | 판단 기준 |
| --- | --- |
| 방문 ID를 유지할 기간 | 분석 기간, 사용자 기대, 쿠키 만료와 재방문 정의 |
| 동일 브라우저의 여러 탭 | 같은 방문자에 여러 작업이 동시에 연결되는 규칙 |
| 쿠키 삭제·시크릿 모드 | 새 방문자로 처리할지, 사용자가 다시 연결할 수단을 제공할지 |
| 기기 간 연결 | 로그인·사용자 동의 없이 어떤 수준까지 연결할 것인지 |
| 향후 계정 연결 | 기존 익명 작업을 로그인 계정으로 귀속하는 시점과 동의 |
| 이벤트·사진 보관 기간 | 보관·삭제·재처리 정책과 사용자 요청 처리 |
| 분석용 식별자 노출 | 화면에는 짧은 표시 ID, 분석에는 충돌을 피할 전체 ID 사용 |
| 비회원 서비스의 남용 방지 | IP·세션별 요청 제한과 정상 사용자 영향 |

ID 유지 정책을 확대하기 위해 브라우저 지문 수집이나 숨은 기기 추적을 도입하지 않았다. 정식 서비스 정책은 이 데모의 세션 기본값을 그대로 확정한 것으로 취급하지 않는다.

## 현재 데이터와 확장 경계

Project는 사진·원본 참조와 체크섬·입력 문서·요청 설명과 스타일·검색 잠금 상태를 보관한다. SketchEvent는 방문자의 작업에 연결된 행동을 기록한다. Composition은 생성 시점 입력 스냅샷과 요청, 최초·현재 결과 배치, 합성 PNG, 배치 저장 버전을 보관한다. RecommendationRun은 추천 실행·재시도·결과를, SceneObjectRevision은 수정한 검색 조건을 보관한다. 결과 배치가 바뀌어도 원래 입력 스냅샷은 유지한다.

초기 수집 대상인 업로드·획·버튼 클릭에 텍스트·도형 조작을 추가했고, 이후 결과 이동·크기 조절·다운로드·재시작, 3차에는 자르기·채우기·복사·붙여넣기, 4차에는 사진·스케치 통합 실행 취소·다시 실행, 영역 선택·그룹화·그룹 해제와 선택 선 두께 조절을 추가했다. 기록을 이용할 때 방문·작업·검색 결과·개별 편집 요소·이벤트의 ID를 구분해야 한다.

실제 AI 입력에는 전체 스케치 이미지와 좌표·텍스트를 함께 전달하는 설계가 필요하다. 실제 상품 검색과 생성 합성은 모의 상품 규칙을 대체할 별도 연결이다. 광고 서버, Kafka 전송, Spark 처리, 공개 서비스 배포는 별도 설계 범위다. 계정과 개인 이력은 8차, 운영 관리와 광고 데모는 9차에 반영했다.

실행 방법과 현재 사용법은 [README](../../README.md)를 참고한다. 입력·렌더링은 editor.mjs와 paint.mjs, 문서 검증은 validation.py, 단일 상품 모의 배치는 mock_composition.py, 사진·결과·재시작 API는 views.py에서 관리한다.


## 9차 검증 기록 (2026-10-16)

- Django 106개, JavaScript 26개 테스트 통과. 운영 신규 테스트는 19개다.
- 격리된 DB·media·Raw의 Edge 브라우저에서 운영자 로그인·8개 메뉴·보호된 스케치 미리보기·광고 등록/승인/수정 후 재심사·1440px/390px·로그아웃 후 뒤로가기를 확인했다.
- 기존 회원 가입/작업 연결/찜/저장 버전/사진 교체/이미지 비교, 광고 배너 배치·스크롤·320~1920px 화면 회귀를 확인했다.
- 동시 요청 검증: 비회원 생성 8건 중 성공 3건·제한 5건, 같은 생성 요청 ID 8건에서 결과 한 건, 같은 저장 요청 8건에서 버전 한 건. 재전송은 생성 횟수를 추가 차감하지 않았다.
- 실제 광고 서버 통신·송출·성과는 검증 대상이 아니며 구현하지 않았다. 사용 중인 실제 DB에는 브라우저 검증용 계정을 넣지 않는다.
