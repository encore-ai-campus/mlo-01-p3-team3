## 3. 현재 화면에서 유지할 계약

### Home·편집

Home의 큰 시작 버튼으로 편집에 들어가고 사진 선택·예시 버튼은 한 쌍만 사용한다. 업로드 전에는 중앙, 업로드 후에는 그림판 제목 옆으로 같은 요소가 이동한다. 사진은 가로 100%, 비율에 따라 높이가 달라지며 편집·결과 표시 크기를 맞춘다.

펜·부분 지우개·채우기·사진 위 직접 텍스트·사각형·타원·직선·화살표를 지원한다. 빈 도형 내부는 다른 요소 삽입에 사용하고 외곽선이나 채운 부분으로 선택한다. 내부의 별도 요소는 명시적으로 그룹화하기 전까지 독립적으로 움직인다. 닿거나 겹친 펜 획은 자동 연결된다.

별도 선택 버튼은 없고 영역 선택에서 개별 클릭·이동과 빈 곳 드래그 선택을 함께 한다. 지우개는 색상을 숨기고, 채우기·텍스트·영역 선택은 도형 선 크기를 숨긴다. 기존 텍스트를 선택해 색상을 바꿀 수 있으며 글자 크기는 다시 편집 상태에서 조절한다.

사진 업로드·교체·자르기·그림·설명·스타일은 통합 Undo/Redo에 들어간다. 자르기는 새 사진 작업이며 기존 스케치를 새 좌표로 변환하지 않는다. 설명·스타일은 유지한다. 모바일은 사진·스케치 / 설명·스타일 탭과 하단 고정 생성 버튼을 사용한다.

### 결과

제목은 `[ID] 님이 원하시는 “품목”을 생성하였습니다.`다. 생성된 가구를 직접 이동·모서리/키보드/가로·세로(%) 입력으로 조절하고 성공한 저장만 배치 이력에 반영한다. 크기 %는 사진 대비 2D 비율이며 실물 cm 규격이 아니다.

배치 기록 아래에는 이미지 내려받기·처음부터 다시 그리기·스케치 수정하기·다른 상품 검색하기가 있다. 사용자 작업 JSON 버튼과 별도 결과 크기 조절 모드 버튼은 없다. JSON data API와 내부 보관은 유지한다.

품목·가구 배치 수정은 실제 생성 가구를 선택한다. 독립된 주황색 사각형은 만들지 않는다. 품목은 기본값과 달라야 적용 가능하고 품목 변경은 추천 조건만 바꾸며 새 가구 이미지를 생성하지 않는다. 크기 입력은 실제 PNG·배치와 연결된다.

## 5. 서로 구분해야 하는 기록

사진 바이트 원본은 media/originals, 화면용 JPEG는 media/rooms, 합성 PNG는 media/results다. 스케치 Raw는 data/sketch_raw JSON이며, 현재 작업 상태는 Project, 생성 당시 입력은 Composition, 추천 실행은 RecommendationRun, 검색 품목 수정은 SceneObjectRevision에 있다. 행동 이벤트는 SketchEvent이고 HTTP·오류 로그는 서버 터미널/리다이렉션 파일이다.

일반 행동과 상품 반응은 서로 다른 localStorage 큐를 쓰고 Raw는 별도 IndexedDB drafts/outbox/failed를 쓴다. 같은 origin에서 전송 대기·실패·서버 결과를 함께 확인한다. localhost와 내부망 IP는 서로 다른 origin이다.

행동의 서버 저장 성공과 Raw 파일 저장 성공은 별도다. sample_id는 편집 구간이며 원본 획 수나 이벤트 수와 같지 않다. Raw 정합성 pass도 라벨 정답·동의·학습 사용 허가를 뜻하지 않는다.

## 6. 실패·복구에서 이미 고려한 부분

- Raw 시작 문서에 patch를 재생해 최종 문서·대상 ID·Undo 수·시간·포인터 순서가 일치하는지 검사한다.
- Raw는 임시 파일·flush/fsync·동일 파일시스템 hard link로 확정한다. 같은 ID·같은 내용은 재사용하고 다른 내용은 거절한다.
- 영구 오류 이벤트는 rejected, 잘못된 Raw는 failed로 분리해 뒤의 정상 전송을 막지 않는다. 저장 전 데이터 보관과 성공 확인을 구분한다.
- Web Locks가 있는 localhost/HTTPS에서 작성자 종료·복제 탭 복구를 제어한다. 일반 LAN HTTP의 작성 중 초안 자동 확정은 제한된다.
- Raw는 서버 4MiB보다 작은 약 3MiB·900획·90,000점·950 operation에서 수집을 종료한다. limited 이후의 편집은 원본에 없을 수 있다.
- 결과 배치는 version 조건부 갱신, 편집은 revision·locked 검사, 추천은 request ID·입력 해시·임대 토큰·만료 시각으로 중복·늦은 응답을 방어한다.
- 제공자 호출은 DB 트랜잭션 밖에서 한다. 이 코드 경계가 실제 광고 API 연결·운영 동시성 검증까지 완료됐다는 의미는 아니다.

## 7. 검증 이력과 이번에 확인한 것

원본 수집 최초 확장 당시 37 Django·17 JavaScript 기록이 있고, 이후 선택 확장 및 7차에서 Django 67개·Node 26개와 PC/모바일 브라우저 회귀를 확인한 기록이 있다. 작은 동시 요청 회귀·기존 DB/미디어 보존 검사도 당시 수행 기록이다. 문서마다 적힌 서로 다른 테스트 수는 시점 차이를 확인한다.

2026-10-16에는 최신 소스와 기존 문서를 읽고 기본 DB를 read-only로 집계했다. Project 291개·SketchEvent 3,309개·Composition 71개·RecommendationRun 7개·SceneObjectRevision 9개·Raw 29파일이라는 조회 스냅샷을 남겼다. 실제 사용자 수·학습용 완성 데이터 수가 아니다.

이번 문서 작업에서 서비스 서버·전체 테스트·마이그레이션을 새로 실행하지 않았다. 실물 스마트폰·태블릿·장기 고부하·강제 종료·디스크 장애·공개 운영 성능까지 검증했다고 쓰지 않는다.

## 9차 운영 관리 결정

사용자는 feature/#17에서 행동 데이터 확인과 이후 광고 서버 연결을 준비하는 관리 페이지를 요청했고, 운영 계정은 기존 `hilee`로 지정했다. 광고 서버는 아직 시작하지 않았으므로 이번에 호출하지 않고 연결 준비용 데모만 만든다는 점을 확정했다. 실습 ad_server는 참고만 한다. 광고 초안/심사와 실제 집행/성과를 구분하고 회원/방문 원본 접근 권한을 나눈다. 이전 비회원 기록을 회원 행동으로 소급해 해석하지 않는다.
