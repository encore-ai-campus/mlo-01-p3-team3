# 운영 관리 페이지와 광고 연동 준비

기준일 2026-10-18 · `/ops/` · [현재 작업현황](../작업현황.md)

## 1. 현재 운영 범위

운영 콘솔은 실제 작업·행동·원본 수집 상태와 로컬 광고 초안/심사 흐름을 확인하는 데모다. 광고 서버는 아직 개발·연결하지 않았으며 관리 페이지가 존재한다고 실제 송출·집행·성과가 있는 것은 아니다. [ad_gateway.py](../../../operations/ad_gateway.py)는 미연결 상태만 반환하고 네트워크 호출을 하지 않는다.

## 2. 계정과 권한

기존 지정 계정은 `hilee`이며 2026-10-16 적용 기록에서 staff와 `SketchOn 운영자` 그룹을 연결하고 superuser는 부여하지 않았다. 이번 문서 작업에서는 권한·암호를 변경하지 않았다. 계정이 유효한지는 실행 시 서버 인증이 판단한다.

활성 로그인 + is_staff + 메뉴별 operations permission을 모두 검사한다. 단순 staff만으로 통과하지 않는다. 상단 운영 관리 링크는 접근 가능한 첫 메뉴로 이동하고, 각 운영 페이지는 현재 메뉴 권한을 계정 상태 API에서 재검증한다. 일반 회원·비회원의 직접 URL 접근도 차단한다.

| 권한 | 허용 범위 |
| --- | --- |
| view_console | 운영 개요 |
| view_people | 회원/방문/한도 메타데이터 |
| view_projects | 작업·결과 메타데이터와 상세 진입 |
| view_behavior | 행동 이벤트 |
| view_collection | Raw 수집 메타데이터 |
| view_sensitive | 개인 사진·결과 이미지·요청/Raw·IP 등 민감 원본 |
| review_raw | Raw 사람 검수와 명시적 색인 |
| manage_ads | 광고 초안 등록/수정·활성/중지·소재 조회 |
| review_ads | 광고 심사 변경 경로 |
| view_ad_reports | 미연결 성과 화면 |
| view_ops_audit | 운영 감사 이력 |

기본 운영 그룹은 이 custom permission 묶음을 사용한다. 광고 목록/폼 접근에는 manage_ads가 필요하므로 심사 담당 역할을 따로 운영하려면 UI 진입 권한 조합까지 정해야 한다. 이 데모는 역할 설정 UI·회원 삭제/암호 초기화·외부 조직 SSO를 제공하지 않는다.

## 3. 8개 메뉴

| 메뉴/경로 | 구현 | 해석/제한 |
| --- | --- | --- |
| 운영 개요 `/ops/` | 기간별 결과·이벤트·방문 식별자·검수 대기·생성 상태·flow별 사건 | 방문 ID는 사람 수 아님, flow별 횟수는 완전한 전환율 아님 |
| 이용자 `people/` | 회원·닉네임·방문별 작업·오늘 IP 한도 | 상위 방문/한도 40건. 원 IP는 민감 권한과 감사 적용 |
| 작업 `projects/` | 검색·상태·결과 수·상세·사진·스케치·타임라인 | 민감자료 분리. 상세 결과 최신 30·이벤트 시간순 300·시도 최신 40 |
| 행동 `events/` | 날짜/q·수신 actor·flow 필터 | 서버 수신과 클라이언트 신고를 구분, 과거는 unknown |
| 수집 `collection/` | 크기·획/점·체크섬·경고·재전송·검수·보호된 Raw | 브라우저 미전송은 볼 수 없음. 자동 상태와 사람 상태 분리 |
| 광고 `ads/` | 초안/소재/기간/심사/활성 요청/중지 | 로컬 DB만 변경, 모든 항목 미송출 |
| 성과 `ad-reports/` | 연동 안내·지표 자리 | 노출/클릭/CTR/매출은 `—`, 임의 0/성과 생성 없음 |
| 감사 `audit/` | 운영 변경·검수·민감 열람과 사유/전후 값 | 이 화면에서 수정/삭제 없음. DB 관리자까지 막는 불변 저장소 아님 |

날짜는 KST 기본 최근 7일, 기간 필터는 최대 366일, 일반 목록은 40건 페이지 구분이다. 메뉴마다 동일 필터를 전부 제공하는 것은 아니다. 타임라인 전체 추출/장기간 분석은 별도 집계가 필요하다.

## 4. 원본 보호·검수

개인 사진·결과·Raw는 운영 전용 보호 경로로 열고 원본 경로를 공개하지 않는다. 원본 열람/IP 확인과 운영 변경은 감사에 남긴다. CSRF·no-store·계정 변경 시 본문 숨김/제거를 사용한다. 운영 화면에는 광고가 없다.

Raw 목록은 DB 메타데이터를 조회한다. ‘기존 Raw 색인’과 `index_ops_raw`만 파일을 명시적으로 읽는다. 화면 실행은 최대 1,000개, CLI limit은 최대 10,000까지 허용하는 bounded scan이다. 매번 정렬한 앞쪽 파일부터 보므로 그 이상 자료는 별도 배치 설계가 필요하다. 같은 파일을 재색인해도 원문/재전송 수를 바꾸지 않는다.

사람 검수는 승인/반려/보류와 사유를 별도 저장한다. PASS/REVIEW이고 파일이 보존된 샘플만 승인할 수 있다. 원문 label_status나 quality_status를 수정하지 않는다. 검수 승인만으로 학습 정답·개인정보 동의가 생기지 않는다.

## 5. 광고 데모의 상태 전이

캠페인 ID·제목·문구·광고주·10MiB 이하 JPG/PNG/WebP 소재·HTTPS 목적지·품목·위치·기간·1~10,000 가상 포인트·활성 요청·변경 사유를 입력한다. 지원 위치는 editor-right/result-right/my-right다. 날짜 종료는 시작 뒤여야 한다.

등록 → PENDING → 운영자 APPROVED/REJECTED/HOLD → 활성 요청/중지 흐름이다. 심사와 active는 독립이다. 승인해도 실제 송출은 없다. 제목·문구·소재·URL·분류·위치·기간·광고주가 바뀌면 승인 무효/PENDING 재심사가 필요하다. 활성/가상 포인트 변경은 별도로 감사한다. revision 검사로 오래된 운영 화면의 덮어쓰기를 409로 막는다.

이 UI는 운영자의 수동 심사 도구다. 자동 AI 심사·외부 랜딩 페이지 실시간 검사·실입찰·과금·광고주 셀프서비스·재고/예산 차감은 구현하지 않았다. 소재 미리보기는 보호 경로를 사용한다.

## 6. 이후 실제 광고 서버 연결

현재 media_id=sketchon과 세 위치 ID는 제안/준비 값이다. 실제 서버와 매체/위치/광고주 역할, 요청·응답·실패 스키마를 확정해야 한다. 실습 `C:\CHAPTER3\ad_server`의 게임 매체/광고주 API를 그대로 연결한 상태가 아니다.

1. 실제 광고 서버를 구현하고 운영자/광고주/매체 권한·정책 버전을 정한다.
2. 적합성·승인·활성·기간·품목을 먼저 확인하고 적격 후보 안에서 입찰을 비교한다.
3. 서버 키는 브라우저 밖 서버 환경에 둔다. 장애/timeout 때 서비스는 무광고로 계속되게 한다.
4. 광고 결정 ID·소재/가격/정책 snapshot과 실제 노출·클릭의 중복/재전송 계약을 만든다.
5. 실제 보이는 배너에 광고 표시를 하고 추천 상품 세 카드와 분리한다. Home/인증/운영/숨겨진 좁은 화면은 대상에서 제외한다.
6. 개인정보 동의·기록 보관·삭제·개인화 근거와 지표 정의를 확정한 뒤 데이터를 보낸다. 가상 포인트를 매출로 표시하지 않는다.
