# SketchOn ver5 슬라이드별 발표 대본

24장 발표자료의 순서에 맞춘 발표 연습용 문서입니다. 각 장의 핵심 메시지, 말할 대본, 화면에서 짚을 부분과 다음 장 연결 문장을 정리했습니다. 서비스의 중심은 사진·스케치·텍스트를 실제 상품 탐색으로 연결하는 것이며, 데이터 품질과 복구 설계가 이를 뒷받침합니다.

## 발표 진행 안내

- 권장 구성은 설명 약 15~18분과 시연 약 3~5분입니다. 아래 시간은 연습용 배분이며 실제 발화 속도에 따라 조정합니다.
- 17~19장은 Gold·광고 서버, 광고 브랜딩, 사용자 MVP를 보여주는 시연 구간입니다. 17~18장은 제목만 있으므로 실제 시연 화면으로 전환하며 사용합니다.
- 19장 뒤에는 20~23장 기술 설명이 이어집니다. 19장의 기존 발표자 노트에 있는 ‘다음 장은 Q&A’ 안내는 현재 24장 순서에 맞지 않습니다.
- 수동 가중치, 추천 점수, 확인되지 않은 규격을 학습 결과·확률·설치 가능 보증으로 표현하지 않습니다. 서버 구성도와 연결 설계는 실제 시연에서 확인한 동작 범위와 구분합니다.

## 1장 SketchOn 소개

**핵심 메시지** 공간에 대한 의도를 실제 판매 상품 탐색으로 연결하는 서비스입니다.

**발표 대본 약 25초**

안녕하세요. MLOps 3차 프로젝트 3팀의 SketchOn을 소개하겠습니다. SketchOn은 방 사진에 스케치를 더하거나 원하는 조건을 글로 입력하면, 공간과 요청을 해석해 실제 판매 중인 가구를 탐색하도록 돕는 서비스입니다. 사용자가 떠올린 배치와 취향을 상품 비교와 다나와 상품 확인까지 연결하는 데 초점을 맞췄습니다.

**화면에서 짚을 부분** 서비스명과 ‘공간의 의도를, 실제 상품으로’ 문구를 짚습니다.

**다음 장 연결** 먼저 이 서비스를 함께 만든 팀과 담당 영역을 소개하겠습니다.

## 2장 팀 소개와 역할

**핵심 메시지** 인프라부터 수집·추천·화면까지 다섯 영역을 나누어 협업했습니다.

**발표 대본 약 30초**

팀은 다섯 명으로 구성했습니다. 신성민은 서비스와 데이터 인프라를, 김영주는 설계 검토와 검수 및 사용자 설계를 담당했습니다. 이여찬은 입력 해석과 임베딩 검색, 조건 검증과 CPU 기반 추천 순위를 담당했습니다. 김세진은 상품·이미지 수집과 Bronze부터 Gold, MySQL 게시까지의 데이터 파이프라인을 맡았습니다. 이형인은 사진·스케치 입력과 회원·이력·운영 화면을 담당했습니다.

**화면에서 짚을 부분** 다섯 이름을 왼쪽에서 오른쪽으로 짚고 세부 업무는 한 문장씩 설명합니다.

**다음 장 연결** 이 역할들이 서비스 안에서 어떻게 연결되는지 세 가지 흐름으로 말씀드리겠습니다.

## 3장 발표 순서

**핵심 메시지** 사용자 경험에서 출발해 데이터와 인프라, 구현과 검증으로 설명합니다.

**발표 대본 약 20초**

발표는 세 부분입니다. 먼저 사용자가 사진과 스케치로 요구를 전달하고 상품을 탐색하는 경험을 설명하겠습니다. 다음으로 추천에 필요한 상품 데이터의 준비 과정과 인프라를 소개하겠습니다. 마지막으로 시연과 주요 구현을 통해 어디까지 연결했고 어떤 검증이 더 필요한지 말씀드리겠습니다.

**화면에서 짚을 부분** 01 서비스 경험, 02 데이터와 인프라, 03 구현과 검증 순서입니다.

**다음 장 연결** 먼저 이 서비스를 기획한 문제 상황부터 보겠습니다.

## 4장 기획 배경과 서비스

**핵심 메시지** 검색어로 표현하기 어려운 위치와 취향을 사진·스케치·텍스트로 전달합니다.

**발표 대본 약 40초**

가구를 찾을 때 원하는 느낌은 있어도 정확한 상품명이나 검색어를 정하기는 어렵습니다. 특히 어디에 놓을지, 주변 가구와 어떤 분위기를 만들고 싶은지는 검색어만으로 설명하기 어렵습니다. SketchOn에서는 방 사진에 위치를 그리거나 원하는 가구와 조건을 적습니다. 시스템은 품목과 명시 조건, 공간 맥락을 구분해 해석하고 실제 상품 후보를 제시합니다. 사용자는 후보를 비교한 뒤 다나와에서 상세 정보를 확인합니다.

**화면에서 짚을 부분** ‘표현 → 해석 → 탐색’의 세 단계를 짚습니다.

**다음 장 연결** 이 과정을 사용자 화면 기준으로 네 단계로 나누면 다음과 같습니다.

## 5장 서비스 사용 흐름

**핵심 메시지** 공간 입력부터 상품 확인까지 이어지고, 수정 시 기존 입력을 복원합니다.

**발표 대본 약 40초**

사용자는 먼저 방 사진과 스케치 또는 텍스트를 입력합니다. 다음으로 시스템이 원하는 가구의 품목과 필요한 조건을 해석합니다. 그 결과를 바탕으로 상품 후보와 조건 확인 내용, 추천 근거를 보여줍니다. 사용자가 상품을 선택하면 다나와의 해당 상품 상세 페이지로 이동합니다. 결과가 마음에 들지 않으면 기존 입력을 복원해 수정하고 새 요청으로 추천받을 수 있습니다. 변경한 요청과 동일 작업의 실패 재시도는 구분해 관리합니다.

**화면에서 짚을 부분** 공간 입력, 요청 해석, 상품 추천, 상품 확인을 차례로 짚습니다.

**다음 장 연결** 이 사용자 흐름을 처리하는 서비스와 데이터 준비 구조를 보겠습니다.

## 6장 아키텍처

**핵심 메시지** 온라인 추천 경로와 상품 데이터를 미리 준비하는 경로를 분리합니다.

**발표 대본 약 50초**

구조도는 위아래 두 경로로 나누어 보시면 됩니다. 위쪽은 사용자 요청 경로입니다. 사용자 웹에서 입력을 보내면 Django Webapp이 입력과 작업을 관리하고, 추천을 담당하는 Ad 서버와 결과를 주고받는 구조입니다. 아래쪽은 상품 준비 경로입니다. 원문과 이미지를 보존한 뒤 Kafka, Spark, Delta를 거쳐 정제하고, 검증된 상품을 MySQL 카탈로그에 게시합니다. 추천 경로는 이 준비된 상품을 조회합니다. Ad 서버는 상품 추천을 담당하는 논리 영역이며, 이 구조도가 모든 서버 간 운영 통합 완료를 뜻하지는 않습니다.

**화면에서 짚을 부분** 위쪽 사용자 웹↔Webapp↔Ad 서버, 아래쪽 원문·이미지→정제→MySQL, 사용자 상품 선택 후 다나와 이동입니다.

**다음 장 연결** 아래쪽 상품 준비 경로를 조금 더 자세히 보겠습니다.

## 7장 상품 데이터 파이프라인

**핵심 메시지** 원천 보존부터 검증된 버전 게시까지 데이터의 단계를 구분합니다.

**발표 대본 약 50초**

수집한 원문은 MongoDB에, 이미지는 Garage에 보존하고 Kafka로 보존된 원천의 참조를 전달합니다. Spark는 이를 Delta Bronze로 수렴시키고, Silver에서 값과 출처를 정제합니다. Gold에서는 현재 상품 구성과 추천 준비 상태를 만듭니다. 서비스에 반영할 때는 고정한 Gold 버전을 staging에서 검증한 뒤 MySQL에 게시합니다. Garage S3는 이미지와 Delta 파일의 저장 기반입니다. 사용자와 작업 원장은 이 상품 게시 흐름과 별도로 유지합니다.

**화면에서 짚을 부분** 원천 보존→Kafka→Bronze→Silver→Gold→MySQL, 마지막 staging 검증 구간을 강조합니다.

**다음 장 연결** 이 역할들을 어떤 인프라에 나누었는지 보겠습니다.

## 8장 인프라

**핵심 메시지** 5대 호스트와 VM 20대를 역할별로 배치한 구성입니다.

**발표 대본 약 50초**

자료의 구성은 5대 호스트에 VM 20대입니다. 운영 영역은 Bastion과 Monitoring으로 2대, 사용자 서비스는 Webapp 1대와 Ad 서버 1대, MySQL 3대로 5대입니다. 수집·처리 영역은 NiFi 1대, Kafka 3대, Spark·Delta 4대로 8대입니다. 보존 영역은 MongoDB 3대와 Garage S3 2대로 5대입니다. Gemini는 외부 API이므로 VM 수에 포함하지 않습니다. 역할 분리는 장애 영향과 운영 책임을 나누기 위한 것이며, 이 대수만으로 처리량이나 고가용성을 보장하는 것은 아닙니다.

**화면에서 짚을 부분** 2+5+8+5=20, Spark Master 1·Worker 3, 오른쪽 외부 API를 짚습니다.

**다음 장 연결** 이제 수집한 데이터를 각 단계에서 어떻게 다루는지 설명하겠습니다.

## 9장 Bronze 수집과 원천 적재

**핵심 메시지** 상품 정보와 이미지의 원천을 연결해 나중에 추적할 수 있게 합니다.

**발표 대본 약 40초**

수집은 카테고리 목록에서 품목별 상품 주소를 확인한 뒤 상품 상세와 갤러리로 확장하는 흐름입니다. 상품명, 가격, 규격과 주소는 원문 및 관측 시각과 함께 보존합니다. 이미지는 대표·갤러리 구분과 출처 URL, 저장 파일, 해시를 연결합니다. 중요한 것은 파일 개수만 늘리는 것이 아니라 어떤 이미지가 어떤 상품에서 왔는지 유지하는 것입니다. 그래야 정제 오류나 연결 문제를 원천까지 되짚어 확인할 수 있습니다.

**화면에서 짚을 부분** 상단 수집 순서와 하단 상품 정보·상품 이미지의 보존 항목입니다.

**다음 장 연결** 보존한 정보를 바로 추천에 사용하지 않고 Silver에서 값과 확인 상태를 정리합니다.

## 10장 Silver 값과 확인 상태

**핵심 메시지** 값뿐 아니라 출처와 확인 상태를 함께 관리합니다.

**발표 대본 약 45초**

Silver에서는 품목 분류를 맞추고 규격의 단위와 축, 옵션을 확인합니다. 가격은 판매 조건과 관측 시각을 구분하고, 이미지는 상품 및 링크와 제대로 대응하는지 확인합니다. 이때 값이 비어 있다는 사실만으로 모두 같은 상태로 취급하지 않습니다. 원천 미제공인지, 추출 실패인지, 정보 충돌인지, 아직 미확인인지 구분합니다. 확인되지 않은 값을 정상 값으로 채우지 않아야 추천 화면에서도 조건 충족 여부를 정확하게 안내할 수 있습니다.

**화면에서 짚을 부분** 품목·규격, 가격, 이미지의 세 영역과 하단 ‘값·출처·확인 상태’입니다.

**다음 장 연결** 이렇게 정리한 정보를 Gold에서 서비스 조회와 반응 분석에 사용할 형태로 준비합니다.

## 11장 Gold 서비스 활용과 반응 분석

**핵심 메시지** 검증된 상품을 게시하는 흐름과 실제 사용자 반응을 집계하는 흐름을 연결합니다.

**발표 대본 약 50초**

위쪽은 서비스 활용 경로입니다. 상품·이미지·벡터·링크를 Gold 구성으로 묶고 고정 버전을 검증해 MySQL에 게시하면, 준비된 벡터로 추천 순위를 계산하고 상품을 탐색할 수 있습니다. 아래쪽은 반응 분석 경로입니다. 실제 노출, 선택, 명시적 거절, 링크 클릭을 기록하고 중복과 연결 관계를 검사해 기간·상품·품목별로 집계합니다. 후보를 계산한 것만으로 노출로 세지 않고, 클릭을 구매 완료로 해석하지도 않습니다. 게시 검증과 실제 업무 상품 추천까지의 통합 인수는 구분해서 확인합니다.

**화면에서 짚을 부분** 위쪽 서비스 활용, 아래쪽 반응·품질 집계 순서입니다.

**다음 장 연결** 준비한 상품 후보의 순위는 다음 점수 구조로 정합니다.

## 12장 콘텐츠 기반 추천 순위

**핵심 메시지** 의미 유사도를 기본으로 명시 선호와 지원되는 방 특징을 조건부 반영합니다.

**발표 대본 약 60초**

추천은 먼저 명시 조건을 대조하고, 요청과 상품의 임베딩 유사도를 계산합니다. 사용자의 색상 선호가 있으면 유사도 85퍼센트와 색상 일치 15퍼센트로 기본 점수를 만듭니다. 색상 선호가 없으면 유사도만 사용합니다. 여기에 지원되는 방 특징이 있을 때는 기본 점수 80퍼센트와 방 특징 점수 20퍼센트를 결합합니다. 방 특징이 없으면 기본 점수를 그대로 씁니다. 방에서 관찰한 색을 사용자의 필수 색상으로 강제하지 않으며, 이 가중치는 수동 초기 정책입니다. 점수는 구매 확률이나 설치 가능 확률이 아닙니다.

**화면에서 짚을 부분** 기본 점수식과 방 특징 확장식을 나누어 짚고 각각의 적용 조건을 설명합니다.

**다음 장 연결** 추천에 쓰는 상품 이미지도 상품 관계와 공통 파일을 나누어 관리합니다.

## 13장 상품 이미지 연결과 자산 공유

**핵심 메시지** 동일 파일은 재사용하면서 상품별 출처와 판매 링크는 유지합니다.

서로 다른 상품에서 같은 이미지가 사용될 수 있습니다. 이때 상품 A와 B를 하나의 상품으로 합치지 않고 각각의 원천 ID와 출처, 판매 링크를 유지합니다. 상품별 이미지 관계는 product_images로 관리하고, 동일한 이미지 자산은 assets를 통해 공유하는 구조입니다. 저장 파일은 checksum으로 대조해 같은 파일의 중복 저장을 줄이고 임베딩도 재사용합니다. 공통 파일을 공유하더라도 상품별 이미지 순서와 검수 상태는 별도로 유지합니다.

## 19장 MVP 시연

**핵심 메시지** 입력 저장부터 추천 결과와 상품 확인까지 사용자 흐름을 보여줍니다.

**발표 대본 시연 전 약 20초**

실제 사용자 흐름을 보여드리겠습니다. 시작 화면에서 내 공간 꾸미기로 들어가 방 사진과 원하는 조건을 입력합니다. 추천 요청을 보낸 뒤 상품 후보와 확인 상태를 비교하고, 선택한 상품의 상세 페이지로 이동하겠습니다.

**시연 진행안 약 90~150초**

1. 첫 화면에서 입력 화면으로 이동하고 방 사진을 엽니다.
2. 원하는 가구 위치를 스케치하거나 품목과 조건을 입력합니다.
3. 추천을 요청하고 진행 상태가 표시되는 것을 보여줍니다.
4. 완료 결과에서 상품 이미지와 추천 근거, 규격 확인 상태를 짚습니다.

**시연 중 설명** ‘사진과 요청을 해석한 뒤 준비된 상품 후보의 순위를 계산합니다. 규격과 설치 가능성은 별도로 확인해야 합니다.’ 고정 데모나 저장된 결과를 사용하면 그 모드를 먼저 밝힙니다. 선택형 미리보기는 준비된 결과가 있을 때 추가로 보여주며, 반복 시연을 위해 유료 생성을 새로 실행할 필요는 없습니다.

**화면에서 짚을 부분** 첫 화면의 ‘내 공간 꾸미기’부터 시작합니다. 중간 결과와 최종 상품 링크가 같은 상품인지 짚습니다.

**다음 장 연결** 지금 보신 흐름이 반복 요청과 실패 상황에서도 이어지도록 설계한 핵심을 설명하겠습니다.

## 20장 접수와 중복 방지

**핵심 메시지** 같은 요청은 기존 작업으로 연결하고 파일 저장 장애는 상태로 복구합니다.

**발표 대본 약 55초**

사용자가 버튼을 여러 번 누르거나 네트워크 문제로 요청을 다시 보내면 같은 작업이 중복으로 만들어질 수 있습니다. 이를 막기 위해 요청 ID로 기존 작업을 찾고 입력 해시를 비교합니다. 같은 요청과 입력이면 기존 작업을 반환하고, 같은 ID에 다른 입력이면 거절합니다. 신규 요청만 접수 상한을 확인하고 STAGING 상태로 예약합니다. 코드에서 파일 저장이 트랜잭션 밖에 있는 점이 중요합니다. DB를 오래 잠그지 않고, 중간 장애는 STAGING 상태와 manifest, checksum을 대조해 복구합니다. DB와 파일이 하나의 원자적 저장으로 묶였다는 뜻은 아닙니다.

**화면에서 짚을 부분** existing 검사, STAGING 예약, 들여쓰기 바깥 preserve_original_and_manifest 순서입니다. 코드는 설계 설명용 의사코드입니다.

**다음 장 연결** 접수한 작업은 별도 워커가 실행하고 성공한 외부 응답은 복구에 재사용합니다.

## 21장 비동기 실행과 실패 복구

**핵심 메시지** 웹의 접수 응답과 장시간 실행을 분리하고 성공 응답부터 이어서 복구합니다.

**발표 대본 약 65초**

웹은 입력과 권한을 확인해 작업을 접수한 뒤 HTTP 202로 응답합니다. 해석과 임베딩처럼 오래 걸리는 처리는 별도 워커가 수행합니다. 외부 API 응답은 비동기로 기다리고 이미지·파일 처리 같은 동기 작업은 제한된 공유 풀에서 수행합니다. 동시에 실행 수와 제공처 호출률을 각각 제한합니다. 아래 코드는 실패 복구입니다. 외부 응답을 받았지만 후처리에서 실패할 수 있어 성공 응답을 receipt로 보존합니다. 재시도할 때 단계와 입력, checksum이 맞는 응답이 있으면 다시 호출하지 않고 후처리부터 이어갑니다. 다만 제공처 처리 후 응답이 유실되거나 receipt 저장 전에 종료되면 외부 호출과 과금이 정확히 한 번만 발생한다고 보장할 수는 없습니다.

**화면에서 짚을 부분** 위 코드는 실행 경계, 아래 코드는 receipt 존재 여부에 따른 재호출 생략을 짚습니다.

**다음 장 연결** 복구 과정에서 이전 워커가 늦게 돌아오는 문제와 관리자 수정 충돌도 제어해야 합니다.

## 22장 실행권과 변경 충돌 제어

**핵심 메시지** 현재 실행권과 최신 수정 버전을 확인해 오래된 결과의 덮어쓰기를 막습니다.

**발표 대본 약 60초**

워커가 멈춘 것으로 판단해 다른 워커가 작업을 회수했는데 이전 워커가 늦게 완료될 수 있습니다. 왼쪽 SQL은 RUNNING 상태, 자신의 실행 토큰, 유효한 lease를 모두 만족할 때만 완료를 확정하는 구조입니다. 정상 실행 중에는 heartbeat로 실행권을 갱신하고 작업별 파일 잠금으로 파일 접근도 보호합니다. 관리자 수정은 revision으로 충돌을 확인합니다. 읽었던 버전과 현재 서버 버전이 다르면 HTTP 409로 막아 오래된 화면의 덮어쓰기를 방지합니다. 메뉴와 민감자료 권한은 서버에서 검사하고 열람·변경은 감사 이력으로 남깁니다.

**화면에서 짚을 부분** SQL WHERE의 세 조건과 오른쪽 워커 token·관리자 revision의 차이를 짚습니다.

**다음 장 연결** 마지막으로 AI 해석, 추천 판단, 선택형 생성의 책임을 정리하겠습니다.

## 23장 추천과 선택형 생성

**핵심 메시지** 실제 상품을 먼저 추천하고 사용자가 선택한 뒤 별도 미리보기를 생성합니다.

**발표 대본 약 65초**

멀티모달 API는 공간과 요구사항을 해석하고 임베딩 API는 검색 벡터를 만듭니다. 명시 조건을 검사하고 최종 순위를 정하는 것은 자체 코드입니다. 점수는 앞서 설명한 기본 유사도와 색상 선호, 지원되는 방 특징을 반영하며 수동 가중치를 사용합니다. 상품 추천이 끝나면 사용자가 선택한 상품 한 개로 배치 미리보기를 요청할 수 있습니다. 이 생성은 추천과 분리된 자식 작업이며 원래 상품 정보와 링크를 유지합니다. 생성된 이미지를 다시 분석해 상품을 찾는 흐름은 아닙니다. 미리보기는 AI 시안으로, 상품의 완전한 동일성이나 실제 설치 가능성을 보증하지 않으며 유료 생성 품질과 지연 검증은 별도입니다.

## 예상 질문과 답변

### 직접 학습한 추천 모델인가요

초기 추천은 scikit-learn의 코사인 유사도와 수동 가중합을 사용합니다. 멀티모달 해석과 임베딩은 외부 API를 사용하며 현재 가중치는 학습 결과가 아닙니다. 반응 데이터를 충분히 확보한 뒤 지도학습을 별도로 평가하는 방향입니다.

### 85 대 15와 80 대 20의 근거는 무엇인가요

의미 유사도를 중심에 두고 색상 선호와 방 특징을 보조적으로 반영하기 위한 수동 초기 정책입니다. 최적 가중치라는 의미는 아니며 추천 적합성과 순위 평가를 통해 조정해야 합니다. 실행별 정책을 고정해 결과를 추적합니다.

### 방 사진만으로 가구 크기와 설치 가능성을 알 수 있나요

크기 근거의 수준과 불확실성을 구분합니다. 통상 치수나 상대 비례만으로 실측을 확정하지 않으며 상품 규격이 없으면 미확인으로 둡니다. 추천과 배치 미리보기 모두 실제 설치 가능성을 보증하지 않습니다.

### 이미지 생성 서비스인가요

기본 흐름은 공간과 요구사항을 해석해 실제 상품을 먼저 추천하는 것입니다. 10월 18일 추가된 선택형 기능에서는 사용자가 추천 상품을 고른 뒤 별도 배치 미리보기를 생성합니다. 추천을 시작하기 위해 이미지 생성이 필요하지는 않습니다.

### 중복 API 비용을 완전히 막을 수 있나요

동일 요청과 입력은 기존 작업으로 연결하고 보존된 성공 응답은 재사용합니다. 다만 제공처에서 처리했지만 응답이나 receipt가 남지 않은 경우까지 중복 호출·과금을 완전히 막을 수는 없습니다.

### 모든 서버가 운영 통합된 상태인가요

현재 시연한 경로를 기준으로 설명해야 합니다. 로컬 작업 원장·워커·파일 카탈로그 추천, 서버 카탈로그 연결 코드와 일부 검증, 실제 업무 데이터 게시·운영 추천, 독립 광고 서버 HTTP 통합은 서로 다른 범위입니다. 구성도만으로 전체 운영 배포 완료라고 답하지 않습니다.

### 성과는 무엇으로 측정하나요

입력 조합별 해석 적합성, 후보와 순위 품질, 상품·이미지·링크 대응, 실제 노출·선택·명시적 거절·클릭, 복구 성공 여부와 응답 시간으로 평가합니다. 클릭은 구매나 매출로 계산하지 않습니다.

## 발표 전 확인 사항

- 17~18장에 사용할 실제 시연 화면을 준비하고 화면 전환 순서를 맞춥니다.
- 19장 시연이 고정 데모, 저장 결과, 실제 API 요청 중 무엇인지 정합니다. 실패 시 사용할 저장 화면도 같은 실행 모드로 설명합니다.
- 인프라 설치·게시 시험·실제 추천 성공은 각각의 확인 범위로 답합니다. 과거 시험 기록을 당일 새로 검증한 결과처럼 말하지 않습니다.
- 선택형 생성은 기존 결과와 정책을 먼저 확인합니다. 시연 준비를 이유로 완료 결과나 상품 임베딩을 재생성하지 않습니다.
- 팀원 간 발표 인계는 8장 인프라, 9~11장 데이터, 12장 추천, 15~16장 UI 등 실제 담당과 발표 시간에 맞춰 정합니다.
